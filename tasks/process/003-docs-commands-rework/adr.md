# Architecture decision — process/003

## Контекст

Brief фиксирует два сцепленных дефекта: команда определена в нескольких местах одновременно, и факт документации не имеет единственного дома. Оба решаются введением слоёв владения — исполняемого для команд и декларативного для содержимого. Ниже — решения, определяющие эти слои, и отвергнутые варианты.

Существенные ограничения контекста:

- проект собран на npm workspaces; `node_modules/.bin` наполняет именно npm, и без него `tsp`, `tsc`, `jest` не вызываются по имени;
- на macOS доступна GNU Make 3.81 (Apple не обновляет из-за GPLv3), на CI-раннерах — 4.x; писать надо в пересечении возможностей;
- CLI задач (`tasks/tools/task.ts`) имеет 13 команд с позиционными аргументами и флагами;
- авточекер Hexlet (`hexlet-check.yml`) исполняет закрытый бандл и его требования к репозиторию непрозрачны;
- `tasks/**` — исторический протокол, переписыванию не подлежит.

## Решение

### Р1. Строка команды принадлежит Makefile; `package.json` перестаёт быть слоем команд

Единственное определение каждой команды — рецепт цели в `Makefile`. Секции `scripts` очищаются полностью, кроме корневого `"test": "make test"`, оставленного страховкой для непрозрачного авточекера Hexlet.

Обоснование выбора между «Makefile владеет» и «Makefile отражает» — в альтернативах А1. Ключевой довод: два работающих входа воспроизводят ту самую неоднозначность, ради устранения которой вводится Makefile, а в `tasks/**` останутся десятки документов, обучающих старому входу.

Отказ от `npm run X` делает эту команду ошибкой вида «Missing script», к которой npm печатает список доступных скриптов. Отказ громкий, а не молчаливый, и это принимается сознательно: тихая деградация была бы хуже.

### Р2. Три уровня: `make/common.mk` → корневой `Makefile` → `Makefile` зоны

`make/common.mk` содержит только то, что общее для всех: вычисление корня репозитория относительно себя, `export PATH := $(REPO_ROOT)/node_modules/.bin:$(PATH)`, механику `help` и `.DEFAULT_GOAL := help`. Подключается директивой `include` из каждого `Makefile`.

PATH задаётся один раз здесь. Это заменяет ту услугу, которую раньше оказывал `npm run`, и снимает необходимость в `npx` — без чего рецепты пришлось бы писать как `npx tsc --noEmit`, добавляя разрешение пакета в каждый вызов.

Корневой `Makefile` владеет операциями уровня репозитория и фан-аутом. Зональный — глаголами своей зоны.

### Р3. Фан-аут по зонам вычисляется, а не перечисляется

```make
ZONES := $(patsubst %/Makefile,%,$(wildcard apps/*/Makefile packages/*/Makefile infra/Makefile tasks/Makefile))
```

Появление зоны с `Makefile` включает её в фан-аут само; список не отстаёт от репозитория. Это сохраняет свойство, которое сегодня даёт `npm run typecheck --workspaces --if-present`, и не переносит в Makefile ручной перечень, способный разойтись.

### Р4. Зона обязана определять полный стандартный набор глаголов

Каждый зональный `Makefile` определяет `typecheck`, `test` и `gates` — даже если в зоне нечего запускать: тогда цель имеет пустой рецепт и описание, объясняющее, почему она пуста.

Причина: у `make` нет аналога `--if-present`. Пропуск отсутствующей цели пришлось бы делать через подавление ошибки (`|| true`), а это скрывает и настоящие падения. Обязательный полный набор превращает «в зоне нет такой цели» в ошибку конфигурации, видимую сразу, и заодно механически обеспечивает единообразие имён (FR4).

`dev`, `start`, `web`, `up` и прочие специфические глаголы определяются только там, где осмысленны, и в фан-аут не входят.

### Р5. Механизмы Р2–Р4 проверены прототипом на GNU Make 3.81

Решения выше опираются на поведение конкретной версии make, поэтому проверены до принятия — на GNU Make 3.81 этой машины, на макете из корня и двух зон:

| Механизм | Результат |
|---|---|
| `.DEFAULT_GOAL := help` | `make` без цели печатает справку |
| `REPO_ROOT := $(abspath $(dir $(lastword $(MAKEFILE_LIST)))..)` | корень вычислен верно и из корневого `Makefile`, и из зонального с `include ../../make/common.mk` |
| `export PATH := $(REPO_ROOT)/node_modules/.bin:$(PATH)` | PATH виден в рецептах зоны |
| `$(patsubst %/Makefile,%,$(wildcard …))` | список зон вычислен верно |
| `help` на `awk` по `## описание` | список целей печатается в корне и в зоне |
| вложенный `$(MAKE)` внутри рецепта | `gates` последовательно выполняет `typecheck` и `test` |

Проверка заодно подтвердила Р4: зона без цели `typecheck` роняет фан-аут сообщением `No rule to make target 'typecheck'`. Отказ громкий и указывает на конкретную зону — то поведение, ради которого полный набор глаголов сделан обязательным.

### Р6. Аргументы CLI не проходят через `make`: вводится `scripts/task`

CLI задач получает исполняемый вход — двухстрочный POSIX-shell скрипт, передающий аргументы без разбора:

```sh
#!/bin/sh
exec node --experimental-strip-types "$(dirname "$0")/../tasks/tools/task.ts" "$@"
```

`Makefile` не знает грамматики CLI: единственная связанная с ним цель — `task-check`, вызывающая `scripts/task check` как часть гейтов.

Обоснование отказа от двух других способов — в альтернативах А2. Коротко: перечислить 13 команд целями значит завести второй список, расходящийся с `task.ts`; идиом `$(filter-out $@,$(MAKECMDGOALS))` противоречит прямому указанию manual («this variable should be used only in special circumstances») и требует catch-all `%`, из-за которого опечатка в имени цели завершается успехом вместо ошибки.

### Р7. Контракт размещения фиксируется в существующем источнике правды

Новый мета-документ не заводится. `docs/sources-of-truth.md` уже отвечает на вопрос «кто чем владеет» и уже содержит строку про команды — она правится, а недостающие виды дописываются в ту же таблицу.

Шесть видов содержимого и их дома:

| Вид | Дом |
|---|---|
| Команда | `Makefile` корня или зоны |
| Правило зоны | `AGENTS.md` — корневой для глобального, зональный для локального |
| Архитектура репозитория | `docs/architecture.md` |
| Архитектура зоны | `<зона>/architecture.md` |
| Домен | `docs/domain-model.md`, `docs/domain-rules.md` |
| Эксплуатация | `README.md` зоны-владельца |

Инвариант: факт записан один раз, остальные упоминания — ссылка.

### Р8. Три файла на зону с фиксированными именами

`AGENTS.md` — правила, `architecture.md` — устройство, `README.md` — эксплуатация. Файл заводится только при наличии содержимого.

Имена подобраны так, чтобы каждый вид данных находился одним фильтром (`find . -name architecture.md`). Полного единообразия регистра достичь нельзя: `AGENTS.md` распознаётся харнессами по этому имени, `README.md` рендерится GitHub при просмотре каталога — оба заданы извне. Достижимое и достаточное свойство — одинаковое имя во всех зонах; `architecture.md` пишется строчными по образцу уже существующего `docs/architecture.md`, что заодно избавляет от переименования и правки всех ссылок на него.

### Р9. `docs/` вносится в git

Строка `/docs/` удаляется из `.gitignore`. Проверено: локальных абсолютных путей и секретов в `docs/**` нет, объём 5,2 МБ (в основном четыре PNG reference-кадров), `uispec:validate` на текущем содержимом зелёный — 40 файлов, `errors=0`.

Следствие: защиты вида `test ! -d docs ||` становятся мёртвым кодом и снимаются, а валидация UISpec начинает выполняться в CI по-настоящему. Защита `test ! -d tasks ||` сохраняется: у CLI есть команда `init` «для нового проекта», то есть переносимость инструмента заявлена намеренно.

`.opencode/`, `CLAUDE.md`, `.mcp.json` и `opencode.json*` остаются вне git — они содержат локальную конфигурацию харнессов и MCP.

### Р10. Защита от возврата — гейт, а не договорённость

`make lint-docs` реализуется скриптом в `scripts/`, вызывается целью и входит в `make gates` и в CI. Проверяет два инварианта FR17. Лазейка FR18 — маркер-комментарий перед блоком.

Вторая проверка (каждая упомянутая цель `make <имя>` существует) важнее первой: она превращает связь «документация → команда» из обещания в проверяемый факт и ловит обратный дрейф — переименование цели без правки документации.

Решение соответствует сложившейся практике проекта: тот же класс задач уже закрыт валидаторами UISpec (V1–V11), `contract-validation.test.ts` и `task check`.

### Р11. Дубли в `docs/` устраняются через нумерацию инвариантов

Механизм уже наполовину существует: `docs/domain-model.md` §10 содержит полный нумерованный список инвариантов, и ссылки на номера уже используются (каталог ошибок ссылается на I11). Решение — довести его до правила: инвариант формулируется один раз в `domain-model.md` под номером, остальные документы ссылаются на номер, а не пересказывают.

Граница между двумя доменными документами закрепляется так: `domain-model.md` — что существует (сущности, поля, инварианты), `domain-rules.md` — что происходит (сценарии, поведение onboarding, окно записи). Слияние документов не выполняется: разделение отвечает разным вопросам и разным читателям.

## Последствия и компромиссы

**Приобретаем.** Одно определение на команду. Единый словарь глаголов, одинаковый во всех зонах. Корневой `AGENTS.md` в контексте каждой сессии — ~110 строк вместо 255; `apps/api/AGENTS.md` при работе над backend — ~75 вместо 208. Документация проекта доступна в клоне. Возврат дублирования ловится гейтом.

**Платим.** `npm run X` перестаёт работать — привычка и мышечная память ломаются разово. Появляется зависимость от `make` как инструмента разработки (на macOS и Linux он есть из коробки; Windows вне поддерживаемых платформ проекта и раньше). Makefile ограничен подмножеством 3.81: многошаговые рецепты пишутся через `&&` или `$(MAKE)`, `help` собирается `awk`, а не `column`. Суммарный объём документации не уменьшается — содержимое переезжает, и появляются четыре новых файла; выигрыш только в том, что грузится без явного запроса.

**Риск и его удержание.** Главный риск — потеря содержания при переносе: README и `apps/api/AGENTS.md` содержат знание, добытое отладкой (почему Prism отдаёт 200 вместо 201, зачем `--clear`, почему заголовки стоят до парсера тела, ограничения strip-only). Удерживается тем, что перенос выполняется блоками по явному списку, зафиксированному в `plan.md`, и сверяется по нему (AC17), а не пересказывается по памяти.

Второй риск — битые ссылки: переезд содержимого между файлами ломает относительные пути. Удерживается NFR7 и AC7 (проверка разрешимости ссылок выполняется и фиксируется).

Третий риск — непрозрачность авточекера Hexlet. Удерживается сохранением корневого `npm test` и требованием NFR3 не трогать его файлы.

## Рассмотренные альтернативы

### А1. Кто владеет строкой команды

- **Makefile как фасад над npm-скриптами** (`test: npm test -w @minical/api`). Ничего не ломает, PATH решён npm-ом. Отвергнуто: каждая команда описана дважды, дрейф не исчезает, а переезжает в пару Makefile/package.json. Структурной причины для постоянных переходников не нашлось — машинных потребителей npm-скриптов в репозитории всего два, `ci.yml` и скиллы, и оба наши.
- **Раздел по типу**: npm держит вызовы инструментов, make — только композицию и операции, 1:1 обёрток нет. Дублирования тоже нет. Отвергнуто: нет единого словаря — в одной зоне `make dev`, в другой `npm run dev -w …`, то есть главная польза для агента (не угадывать способ запуска) не достигается.
- **Постоянные тонкие переходники** (`"test": "make test"` во всех манифестах). Отвергнуто как вариант по умолчанию по причине из Р1; сохранено ровно в одном месте и по названной причине.

### А2. Как передавать аргументы CLI задач

- **`make task ARGS='approve front/owner/001 plan'`.** Штатный механизм GNU Make: «An argument that contains `=` specifies the value of a variable». Работает, но добавляет кавычки в каждый вызов и оставляет `make` посредником без пользы.
- **Идиом `$(filter-out $@,$(MAKECMDGOALS))` с catch-all `%:; @:`.** Отвергнуто: manual прямо предупреждает — «Note that this variable should be used only in special circumstances», и единственный пример его применения в manual касается условного подключения зависимостей, а не разбора аргументов. Побочный эффект catch-all дисквалифицирует вариант для входа, которым пользуется агент: опечатка в имени цели завершается успехом вместо ошибки.
- **Цель на каждую из 13 команд CLI.** Отвергнуто: пересказ грамматики `task.ts` в `Makefile` — второй список, расходящийся при первом же изменении CLI.
- **Смена раннера на `just`**, где параметры рецептов есть штатно (`task *args: … {{args}}`). Отвергнуто по NFR2: новая зависимость ради одного случая, при наличии решения без неё.

### А3. Куда переносить выселенное из зональных `AGENTS.md`

- **В `docs/architecture.md`.** Отвергнуто: документ описывает контур репозитория, и 130 строк внутренностей `apps/api` сделали бы его тем же, чем сейчас является `AGENTS.md` — контейнером вместо карты.
- **В зональный `README.md` вместе с эксплуатацией.** Отвергнуто: смешивает два разных вопроса — «как устроено» и «как пользоваться», — и лишает смысла фильтр по имени файла.

### А4. Объём работы по `docs/`

- **Не трогать `docs/`, ограничиться переносом.** Отвергнуто владельцем: перекладывать текст в каталог, внутри которого те же дубли, — половинчато.
- **Слить `domain-rules.md` и `domain-model.md` в один документ.** Отвергнуто: устраняет границу вместо того, чтобы её починить; документы отвечают на разные вопросы (Р11).

## Совместимость и миграция

Изменение ломающее для способов запуска и нейтральное для поведения кода: ни один артефакт приложений, контракта и БД не меняется, `API impact = NONE`.

Порядок миграции обеспечивает работоспособность репозитория на каждом шаге: сначала появляются `Makefile` и `scripts/task` рядом с существующими npm-скриптами (оба входа временно живы), затем на новый вход переводятся CI и скиллы, и только последним шагом очищается `package.json`. Промежуточное состояние с двумя входами существует внутри задачи и не выносится в `main` как результат.

Обратная совместимость для внешнего мира не требуется: пакеты репозитория приватные (`"private": true`), публикации в npm нет, потребителей скриптов вне репозитория нет. Единственный внешний потребитель — авточекер Hexlet, и для него сохранён корневой `npm test`.

Откат: удаление `Makefile`, `make/`, `scripts/` и восстановление секций `scripts` из истории git. Документационная часть откатывается независимо от командной — они связаны только тем, что документация ссылается на цели.
