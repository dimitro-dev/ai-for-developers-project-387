# process/003 — Единый вход команд и контракт размещения документации

## Контекст и проблема

Документация проекта выросла до состояния, в котором один и тот же факт записан в нескольких местах, и места эти расходятся.

**Команды определены в десяти местах.** Реальные строки живут в корневом `package.json` (20 скриптов) и четырёх workspace-манифестах (13 скриптов: `apps/api` — 4, `apps/client` — 7, `packages/api-client` и `packages/backend-contract` — по одному). Их пересказывают: таблица «Команды» и одиннадцать bash-блоков в `README.md`, блок «Обязательные проверки» в корневом `AGENTS.md`, секция «Команды» и Definition of Done в `apps/api/AGENTS.md`, навигационная таблица в `tasks/AGENTS.md` (15 упоминаний `npm run task`), отдельные упоминания в `packages/contracts/AGENTS.md`, `infra/AGENTS.md`, `tests/AGENTS.md`, семь шагов в `.github/workflows/ci.yml` и команды в скиллах `taskmaster` и `worktree-isolated-agent`. Полный набор гейтов фазы «Проверка» выписан дословно четыре раза: `README.md`, корневой `AGENTS.md`, `ci.yml`, DoD зоны `apps/api`. Изменение одной команды требует правки в нескольких файлах, и ничто не гарантирует, что правку сделают везде.

**Корневой `AGENTS.md` грузится целиком в каждую сессию.** `CLAUDE.md` содержит `@AGENTS.md`, поэтому все 255 строк попадают в контекст независимо от задачи. Из них ~75 — дерево структуры репозитория с аннотациями, дублирующее «Целевую структуру» в `docs/architecture.md` и уже разошедшееся с ней; ~20 — блок команд; ~50 — разделы «Локальные каталоги AI-процесса» и «Как скиллы и MCP попадают в сессию», нужные редко.

**Зональный контракт существует, но нарушен.** Шесть зон из семи следуют одинаковой структуре: `Читать → Разрешено менять → Обязан → Запрещено → При недостающем решении → Definition of Done`. `apps/api/AGENTS.md` добавляет к ней 130 строк архитектуры (фреймворк, слои, точка валидации, таблица ошибок, middleware-цепочка, ограничения strip-only), `apps/client/AGENTS.md` — 49 строк процедуры работы с UISpec. В результате при работе над backend в контекст грузится 208 строк там, где правил — 75.

**Ролевые формулировки описывают несуществующий механизм.** Корневой `AGENTS.md` утверждает: «Отдельного механизма ролей нет: правила доставляются положением файла», каталог `.opencode/agents/` удалён. При этом все семь зональных файлов открываются строкой «Зона X Agent» (Backend, Frontend, Contract, Database, Infrastructure, QA), а `apps/api/AGENTS.md` описывает согласование Repository API «между Database Agent и Backend Agent» — процедуру, которой не существует.

**`docs/` вне git — причина части дублирования.** Каталог в `.gitignore`, поэтому в клоне его нет, и знание, которому место в `docs/`, оседает в `README.md` (настройка colima, устройство контура PostgreSQL, повадки Prism-мока, семантика `EXPO_PUBLIC_*`), а дерево структуры дублируется в корневом `AGENTS.md`. Проект учебный, работу проверяют — недоступность проектной документации в клоне является дефектом сама по себе.

**Внутри `docs/` тоже есть дубли.** Правило занятости записано дважды почти дословно: `domain-rules.md` §7 и `domain-model.md` §7 (инварианты 1–3). Разделение domain / transport / persistence — трижды: `domain-model.md` §13, `sources-of-truth.md` «Разделение моделей», плюс как правила в `apps/api/AGENTS.md`. При этом содержательно документы актуальны: каталог доменных ошибок точно совпадает с `DomainErrorCode` и контрактом (11 кодов), поля `Booking` — с `apps/api/src/domain/model.ts`.

**Возврата к прежнему состоянию ничто не мешает.** Класс задач «документация разошлась с кодом» в проекте уже решается валидаторами (UISpec V1–V11, `contract-validation`, `task:check`), но для команд и размещения такого механизма нет.

## Цель

Каждая команда определена ровно один раз — в `Makefile` своей зоны или корня; каждый факт документации имеет ровно один дом, определённый видом содержимого; `docs/` доступен в клоне; возврат дублирования ловится автоматической проверкой в составе обязательных гейтов.

## Зависимости

- `infra/006` (CI на GitHub Actions, завершена) — `ci.yml` переписывается на вызов `make`.
- `process/001` (переработка процесса задач, завершена) — вход CLI задач меняется с `npm run task --` на `scripts/task`.
- Ни одну задачу очереди не блокирует. Пересечение с будущими `back/002`, `back/003`, `infra/002` — только в том, что их зональные `AGENTS.md` после этой задачи следуют новому контракту; содержательных требований к ним не добавляется.
- Организационных зависимостей и прав нет.

## Пользовательские сценарии

1. Агент начинает сессию: в контекст грузится корневой `AGENTS.md`, содержащий глобальные правила, bootstrap и маршруты, без дерева структуры и списка команд.
2. Агенту нужно запустить тесты зоны, в которой он работает: он выполняет `make help` в её каталоге и получает список целей с описаниями, вместо того чтобы угадывать способ запуска или искать его в тексте.
3. Агент завершил пункт плана: выполняет `make gates` в затронутой зоне; в фазе «Проверка» — `make gates` в корне. Список проверок не переписан ни в одном документе.
4. Владелец меняет способ запуска (флаг раннера, версия команды): правит одну строку в одном `Makefile`; ни один `.md` править не нужно.
5. Разработчик или проверяющий клонирует репозиторий: `docs/` на месте, ссылки из `README.md` и `AGENTS.md` ведут в существующие файлы.
6. Сессия вписывает `npm run typecheck` обратно в текст `AGENTS.md` или переименовывает цель, не поправив документацию: `make lint-docs` краснеет локально и в CI.
7. Агенту нужна операция CLI задач с нестандартными аргументами: он вызывает `scripts/task <команда> <аргументы>` — грамматику CLI не пересказывает ни `Makefile`, ни документация.

## Функциональные требования

### Команды

- **FR1.** В репозитории появляются `Makefile` в корне и в каждой зоне, где есть своя запускаемая работа: `apps/api`, `apps/client`, `packages/contracts`, `packages/api-client`, `packages/backend-contract`, `infra`, `tasks`. Два generated-пакета включены наравне с прочими, хотя вся их работа — `tsc --noEmit`: исключение из общего механизма потребовало бы особого случая в корневом `Makefile` и нарушило бы единообразие фан-аута (FR4). Зоны без запускаемой работы (`packages/slot-engine`, `packages/database`, `tests`) `Makefile` не получают. Общее (PATH до `node_modules/.bin`, корень репозитория, механика `help`, `.DEFAULT_GOAL := help`) вынесено в `make/common.mk` и подключается директивой `include`.
- **FR2.** Строка команды определена ровно один раз. Корневой `Makefile` владеет операциями уровня репозитория (`setup`, `generate`, `generate-check`, `typecheck`, `test`, `gates`, `lint-docs`, `db-*`) и фан-аутом по зонам; зональный — глаголами своей зоны. Полный набор фазы «Проверка» определён единственный раз — цель `gates` корневого `Makefile`.
- **FR3.** Каждая цель, предназначенная для вызова человеком или агентом, снабжена описанием в формате `цель: ## описание`; `make help` без аргументов печатает список таких целей. `make` без цели эквивалентен `make help`.
- **FR4.** Имена глаголов одинаковы во всех зонах. Стандартный набор `typecheck`, `test`, `gates` определён в каждой зоне обязательно — там, где запускать нечего, цель имеет пустой рецепт и описание, объясняющее пустоту. Специфические глаголы (`dev`, `start`, `web`, `up`) определяются только там, где осмысленны, и в фан-аут не входят. `make -C <зона> <глагол>` работает единообразно.
- **FR5.** Скрипты `package.json` вычищены: строк команд в них не остаётся. Единственное исключение — корневой `"test": "make test"` как страховка для непрозрачного авточекера Hexlet. Причина исключения фиксируется в манифесте верхнеуровневым ключом `"//"` (JSON комментариев не имеет; ключ штатно игнорируется npm, читается через `npm pkg get '//'` и переживает запись версии release-please — проверено). Ключ-комментарий внутри секции `scripts` для этого непригоден: `npm run` печатает его в списке доступных скриптов как настоящий. То же обоснование дублируется в `result.md`.
- **FR6.** CLI задач получает исполняемый вход `scripts/task` — passthrough-обёртка (`exec node --experimental-strip-types tasks/tools/task.ts "$@"`), не знающая грамматики CLI. Строка справки внутри `tasks/tools/task.ts` («Использование: `npm run task -- <команда>`») приводится в соответствие.
- **FR7.** `.github/workflows/ci.yml` вызывает `make`-цели вместо перечисления команд. Job `compose` может продолжать вызывать `docker compose` напрямую либо через цели `infra`, но список шагов не является вторым определением набора гейтов.

### Размещение документации

- **FR8.** `docs/` вносится в git: строка `/docs/` удаляется из `.gitignore`. `.opencode/`, `CLAUDE.md`, `.mcp.json` и `opencode.json*` остаются вне git.
- **FR9.** Контракт размещения фиксируется в `docs/sources-of-truth.md`: для каждого вида содержимого назван единственный дом. Строка «Требования к окружению и команды → `README.md` и корневой `package.json`» заменяется на актуальную. Виды: команда → `Makefile`; правило зоны → `AGENTS.md`; архитектура репозитория → `docs/architecture.md`; архитектура зоны → `<зона>/architecture.md`; домен → `docs/domain-rules.md` и `docs/domain-model.md`; эксплуатация → `README.md` зоны-владельца.
- **FR10.** Корневой `AGENTS.md` содержит только глобальные правила, bootstrap, маршруты и карту зон. Дерево структуры репозитория переносится в `docs/architecture.md` (там уже есть раздел «Целевая структура репозитория» — переносимое сливается с ним, а не дописывается рядом); блок команд заменяется ссылкой на цели; разделы «Локальные каталоги AI-процесса», «Пакеты и границы» и «Как скиллы и MCP попадают в сессию» переезжают в `docs/`.
- **FR11.** Зональный `AGENTS.md` содержит только контракт зоны: `Читать → Разрешено менять → Обязан → Запрещено → При недостающем решении → Definition of Done`. Содержимое сверх контракта переносится: устройство зоны — в `<зона>/architecture.md`, эксплуатация — в `<зона>/README.md`. Файл заводится только при наличии содержимого.
- **FR12.** Имена файлов единообразны во всех зонах, чтобы каждый вид данных находился одним фильтром: `AGENTS.md`, `architecture.md` (строчными, как `docs/architecture.md`), `README.md`, `Makefile`.
- **FR13.** Из `README.md` уходят: таблица команд (заменяется ссылкой на `make help`), настройка colima и Docker (в `infra/README.md`), устройство контура PostgreSQL (в `infra/README.md`), повадки Prism-мока (в `infra/README.md`), семантика `EXPO_PUBLIC_*`, режимы запуска клиента и сборка APK (в `apps/client/README.md`). Остаётся человеческий вход: что это за проект, требования к машине, установка, как запустить, структура, ссылки.
- **FR14.** Ролевые формулировки удалены из всех семи зональных `AGENTS.md`: вводные «Зона X Agent» и описания взаимодействия ролей заменяются формулировками через границы зон и файлов. Правило «отдельного механизма ролей нет» из корневого `AGENTS.md` соблюдается всеми зонами.
- **FR15.** Дубли внутри `docs/` устранены: каждый инвариант формулируется один раз в `docs/domain-model.md` под своим номером (механизм уже существует — §10 «Инварианты (полный список)», на них уже ссылаются), остальные документы ссылаются на номер. Разделение domain / transport / persistence описано один раз; два других места ссылаются. Проход выполняется по всем пяти файлам `docs/*.md`, найденные дубли перечисляются в `result.md`.
- **FR16.** Скиллы `taskmaster` и `worktree-isolated-agent` (`.opencode/skills/`, доступны в сессии через симлинк `.claude/skills`) переводятся на `scripts/task` и `make`.

### Защита от возврата

- **FR17.** Появляется проверка `make lint-docs`, входящая в `make gates` и в CI. Область проверки: все файлы с именами `AGENTS.md`, `architecture.md` и `README.md` в репозитории, плюс `docs/*.md`. Зональные `README.md` входят в область обязательно — иначе команды просто переедут в них. Исключены `tasks/**` (исторические документы задач не переписываются), `docs/ui-spec-kit/**` (собственный валидатор) и `.github/workflows/README.md` (файл Hexlet, NFR3). Проверяемые инварианты:
  - **(а)** нет сырых вызовов инструментов: `npm run`, `npm test`, `npm ci`, `npx`, `docker compose`, `node --`, `tsc --`, `jest`;
  - **(б)** каждая упомянутая в документации цель вида `make <имя>` существует в одном из `Makefile`.
- **FR18.** У проверки (а) есть явная лазейка для случаев, где сырой вызов уместен: разовые операции исследования, не являющиеся проектными (например произвольный SQL-запрос к контейнеру), и примеры того, как делать не надо. Лазейка открывается маркером-комментарием непосредственно перед блоком и требует однострочного обоснования рядом. Каждое использование маркера перечисляется в `result.md`; их количество на момент закрытия задачи — не более трёх.

## Нефункциональные требования

- **NFR1.** Makefile'ы совместимы с GNU Make 3.81 — версией, поставляемой с macOS: без `.ONESHELL`, `undefine`, `::=`, без зависимости от `column`. На CI-раннерах используется make 4.x; поведение обеих версий одинаково.
- **NFR2.** Новых зависимостей в `dependencies`/`devDependencies` не добавляется. Альтернативные раннеры (`just`, `task`) не вводятся.
- **NFR3.** `.github/workflows/hexlet-check.yml` и `.github/workflows/README.md` не изменяются.
- **NFR4.** `tasks/**` (кроме документов этой задачи) не переписывается: документы завершённых задач — исторический протокол, упоминания старых команд в них корректны для своего времени.
- **NFR5.** Generated-каталоги не затрагиваются; `.tsp` не меняется.
- **NFR6.** Суммарный объём документации сокращать не требуется — содержимое переезжает, а не удаляется. Измеряется и ограничивается только объём, попадающий в контекст без явного запроса: корневой `AGENTS.md` — не более 130 строк (AC9), каждый зональный `AGENTS.md` — только разделы контракта зоны (AC9).
- **NFR7.** Ни одна ссылка между документами не остаётся битой: перенос содержимого сопровождается правкой ссылающихся мест.

## Acceptance criteria

- **AC1.** `make help` в корне и в каждой зоне с `Makefile` печатает список целей с описаниями; `make` без аргументов делает то же самое.
- **AC2.** Полный набор проверок фазы «Проверка» запускается одной командой `make gates`, и перечень входящих в него проверок присутствует ровно в одном месте — теле цели `gates` корневого `Makefile`. В `.github/workflows/ci.yml` job проверок содержит один шаг запуска гейтов вместо семи; в `README.md` и `AGENTS.md` перечня нет.
- **AC3.** Проверка отсутствия сырых вызовов зелёная:
  ```bash
  grep -rnE "npm (run|test|ci)|npx |docker compose|node --|tsc --|jest " \
    --include='README.md' --include='AGENTS.md' --include='architecture.md' . \
    | grep -vE 'node_modules|^\./tasks/'
  grep -nE "npm (run|test|ci)|npx |docker compose|node --|tsc --|jest " docs/*.md
  ```
  Обе команды не дают совпадений; `make lint-docs` зелёный. (Форма записи важна: шаблон `'**/AGENTS.md'` в аргументах `grep` не раскрывается и приводит к ложно-зелёному результату — использовать `--include`.)
- **AC4.** `make lint-docs` краснеет на искусственном нарушении обоих видов: (а) строка `npm run typecheck` вписана в любой проверяемый `.md`; (б) в документации упомянута несуществующая цель `make nonexistent`.
- **AC5.** `make gates` в корне зелёный целиком, включая `lint-docs`; CI на PR зелёный.
- **AC6.** `scripts/task status`, `scripts/task list --type infra`, `scripts/task approve <id> <гейт>` работают идентично прежним `npm run task -- …`; `Makefile` не содержит ни одной из 13 команд CLI, кроме `check` как части гейтов. Справка самого CLI печатает `scripts/task`.
- **AC7.** Свежий клон репозитория содержит `docs/`; все относительные ссылки на `docs/**` из `README.md` и `AGENTS.md` разрешаются в существующие файлы. Проверка битых ссылок выполнена и зафиксирована.
- **AC8.** Валидация UISpec выполняется в CI по-настоящему — не скипается за отсутствием `docs/` — и зелёная. Защита вида `test ! -d docs ||` в определении этой проверки более не нужна и снята.
- **AC9.** Корневой `AGENTS.md` не превышает 130 строк и не содержит дерева структуры репозитория и списка команд. Каждый зональный `AGENTS.md` состоит только из разделов контракта зоны.
- **AC10.** Ролевых формулировок не осталось: `grep -rn "Agent" --include='AGENTS.md' . | grep -vE 'node_modules|^\./tasks/'` не даёт совпадений.
- **AC11.** `find . -name architecture.md -not -path './node_modules/*'` находит `docs/architecture.md` и зональные файлы; регистр имён единообразен.
- **AC12.** Ни в одном из шести `package.json` репозитория не осталось строк команд. Единственная запись в секции `scripts` — корневой `"test": "make test"`; причина зафиксирована верхнеуровневым ключом `"//"` того же манифеста.
- **AC13.** Дубли в `docs/`: правило занятости и разделение domain / transport / persistence сформулированы по одному разу; остальные места ссылаются. Полный список найденных и устранённых дублей — в `result.md`.
- **AC14.** `npm test -w @minical/api` и `npm test -w @minical/client` более не упоминаются как способ запуска ни в одном документе вне `tasks/**`; их место заняли цели `make`.
- **AC15.** В каждой зоне с `Makefile` работают одноимённые глаголы: `make -C <зона> typecheck`, `make -C <зона> test` и `make -C <зона> gates` выполняются успешно везде, где соответствующая работа существует. Расхождений в именах между зонами нет.
- **AC16.** `docs/sources-of-truth.md` содержит контракт размещения: для каждого вида содержимого назван единственный дом, строка про команды указывает на `Makefile`, а не на `package.json`. Контракт не противоречит остальной таблице источников правды.
- **AC17.** `README.md` не содержит таблицы команд, инструкции по установке colima и Docker, описания контура PostgreSQL, повадок Prism-мока и режимов запуска клиента. Всё перенесённое присутствует в `infra/README.md` и `apps/client/README.md` без потери содержания: сверка выполнена по списку переносимых блоков, зафиксированному в `plan.md`.
- **AC18.** Скиллы `taskmaster` и `worktree-isolated-agent` не содержат вхождений `npm run task`; используемые ими команды — `scripts/task` и цели `make`.

## Non-goals

- Внесение `.opencode/` в git. Каталог остаётся локальным; вопрос решается отдельно, если появится необходимость.
- Переход на альтернативный раннер (`just`, `task`, `mise`). Ограничение GNU Make принимается сознательно.
- Переписывание документов завершённых задач в `tasks/**`.
- Изменение самого процесса задач: гейты, треки, команды CLI и `tasks.config.json` не трогаются. Меняется только вход к CLI.
- Изменение поведения приложений, контракта, схемы БД и generated-артефактов.
- Написание новых тестов приложений. `lint-docs` — проверка документации, а не кода.
- Пересмотр содержания доменных документов по существу: устраняется дублирование, а не доменные решения.
