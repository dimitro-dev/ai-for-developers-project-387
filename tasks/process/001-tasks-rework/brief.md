# TASK-process-001 — Переработка процесса задач: структура, стадии, CLI

## Контекст и проблема

Каталог `tasks/` вырос до 19 плоских директорий трёх поколений именования (числовые
`000`–`006`, типизированные `task-<тип>-<номер>`, легаси `task-front-001`). Состояние задачи
непрозрачно — вычисляется головой из четырёх frontmatter. Полный цикл из четырёх документов и
четырёх согласований избыточен для мелких задач. `tasks/README.md` (35KB) смешивает lifecycle,
реестр, очередь, снимок состояния и шаблоны разделов — тяжело читать и поддерживать, реестр
дрейфует от факта. Фиксация этапов и bootstrap новой сессии — ручные. Роли `.opencode/agents/`
в Claude Code не подхватываются и систематически не используются.

Согласованное решение зафиксировано в [design.md](design.md) (brainstorming 2026-08-15);
этот brief — его постановочная часть.

## Цель

Единая структура `tasks/` по типам, прозрачное состояние задач с каноном в `task.yaml`
(единственный писатель — CLI), облегчённый трек для мелких задач, компактная документация
процесса (маршрутизатор + flows + генерируемый реестр) и инструмент `task` + скилл `taskmaster`
для фиксации этапов и быстрого включения сессии в работу.

## Зависимости

- Нет блокирующих задач. Работа не пересекается с кодом приложений; параллельна
  `front-owner-001` и `infra-001`.
- Прецеденты, на которые опирается решение: валидатор UISpec (инструмент при данных,
  guard-скип в CI), контрактный gate (`node --experimental-strip-types`), пакет `yaml`
  в корневых devDependencies.

## Пользовательские сценарии

1. **Возврат в работу**: владелец (или агент по триггер-фразе) вызывает `/taskmaster` или
   `npm run task -- status` — видит активную задачу, стадию, прогресс пунктов, ветку/worktree,
   связанные спеки; агент открывает flow трека и активный документ без повторной разведки.
2. **Создание задачи**: `task new <тип> <слаг> [--lite]` — CLI выдаёт номер, скаффолдит из
   шаблона трека; агент обосновывает выбор трека по критериям; владелец утверждает трек вместе
   с постановкой.
3. **Согласование этапа**: владелец говорит «согласовано» → агент выполняет
   `task approve <id> <gate>` — статус, дата и checksum фиксируются атомарно.
4. **Мелкая задача**: один `task.md`, два гейта (setup/result) — два круга согласования
   вместо четырёх; при разрастании — `task promote`.
5. **Контроль целостности**: `task check` в «Обязательных проверках» ловит правки согласованных
   документов, ручные правки task.yaml, дрейф реестра и структурные нарушения.

## Функциональные требования

- FR1. Структура `tasks/<тип>/<номер>-<слаг>/` (front — с подтипами `ui|guest|owner`),
  тип `process`; канонический task-id = путь без слага; `archive/` для `000`–`006`;
  `task-front-001` удаляется; стабы `back/002`, `back/003`.
- FR2. `task.yaml` — канон состояния (гейты, checksum, depends, queue, workspace/links/uispec,
  legacyId, meta.selfHash); документы без frontmatter; single writer — CLI.
- FR3. Два трека: full (brief/adr/plan/result, 4 гейта) и lite (task.md, гейты setup/result);
  критерии выбора и `promote` — по design.md.
- FR4. CLI `tasks/tools/` (TS, strip-types, только `yaml` из devDeps), config-driven
  (`tasks.config.json`), команды: init, new, status, list, approve, draft, promote, set/unset,
  check, registry, migrate, repair; npm-скрипты `task`, `task:check`, `task:test` с guard.
- FR5. Документация процесса: `tasks/AGENTS.md` (маршрутизатор), `flows/full.md`,
  `flows/lite.md`, генерируемый `REGISTRY.md` (реестр + очередь + legacy-id);
  `tasks/README.md` удаляется.
- FR6. Скилл `taskmaster` с триггер-фразами в description; регистрация в таблице скиллов.
- FR7. Роли `.opencode/agents/` растворяются во вложенные AGENTS.md (в git):
  apps/api, apps/client — дополняются; packages/contracts, packages/database, infra, tests —
  создаются; `.opencode/agents/` удаляется.
- FR8. Правки: корневой AGENTS.md (проход вглубь по AGENTS.md, Bootstrap через `task status`,
  раздел «Навигация», гейты + `task:check`, класс «изменяется только инструментом», карта
  AGENTS.md вместо таблицы ролей), `docs/sources-of-truth.md`, скилл `worktree-isolated-agent`,
  живые ссылки в `docs/domain-model.md` и `docs/ui-spec-kit/AUDIT.md`.
- FR9. Миграция существующих задач: перенос, task.yaml из frontmatter (legacyId, даты из
  снимка README где известны, sha256 с текущего содержимого), удаление frontmatter;
  критерий — зелёный `task check`.

## Нефункциональные требования

- NFR1. Инструмент project-agnostic: вся специфика MiniCal — в `tasks.config.json`;
  вынос в отдельный проект не требует правок кода.
- NFR2. `tasks/` входит в git (решение владельца 2026-08-16): `task:check` в CI выполняется
  по-настоящему. Guard-скрипты сохраняются для клонов без `tasks/`; `docs/` остаётся локальным,
  поэтому `uispec:validate` в CI скипается (переезд `docs/ui-spec-kit/` в git — будущая
  отдельная задача, вне scope этой).
- NFR3. Тесты CLI на фикстурах (node:test) + интеграционный smoke `check` по живому дереву;
  `task:test` обязателен при изменениях `tasks/tools/`.
- NFR4. Каждый шаг внедрения оставляет репозиторий рабочим (порядок — в design.md).
- NFR5. Правило 11 сохраняется: `согласовано` — только по явному подтверждению владельца;
  CLI фиксирует, а не решает.

## API impact

`NONE` — HTTP-контракт, generated-пакеты и код приложений не затрагиваются.

## Acceptance criteria

- AC1. `npm run task -- status` без аргументов показывает незавершённые задачи со стадиями;
  с id — стадию, активный гейт, прогресс пунктов, workspace с живой проверкой.
- AC2. Все существующие задачи мигрированы: лежат по новой схеме, task.yaml корректны,
  `task check` зелёный, REGISTRY.md сгенерирован и содержит реестр, очередь и таблицу legacy-id.
- AC3. `task new` создаёт задачу обоих треков из шаблонов; `task approve`/`draft` соблюдают
  порядок и каскад гейтов; ручная правка task.yaml и правка согласованного документа ловятся
  `task check`.
- AC4. `npm test` и полный набор «Обязательных проверок» (включая новый `task:check`) зелёные
  локально; в клоне без `tasks/` шаги скипаются.
- AC5. `npm run task:test` зелёный: фикстурные тесты CLI + smoke по живому дереву.
- AC6. Скилл `taskmaster` работает в живой сессии Claude Code: по id и по автоподхвату
  выводит стадию и открывает нужные документы.
- AC7. Роли растворены: шесть вложенных AGENTS.md на местах, `.opencode/agents/` удалена,
  корневой AGENTS.md обновлён (навигация, bootstrap, карта AGENTS.md, гейты).
- AC8. Ссылки на старые пути задач в `docs/domain-model.md` и `docs/ui-spec-kit/AUDIT.md`
  ведут на новые пути.

## Non-goals

- Интерактивный визард `task init` и вынос инструмента в отдельный проект/пакет —
  будущая отдельная задача.
- Интеграция с внешними трекерами (Jira и др.) сверх поля `links.tracker`.
- Формальные evals скилла (`claude plugin eval`).
- Изменение процесса согласования (правило 11) и словаря статусов.
- Пересмотр содержимого архивных задач; переименование старых id задним числом.
