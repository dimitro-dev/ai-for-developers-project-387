# Дизайн: переработка процесса задач (task-process-001)

Согласованный результат brainstorming-сессии 2026-08-15. Документ — вход для `brief.md`
(постановка) и будущих `adr.md`/`plan.md`; сам статусную механику не проходит.

> **Поправка 2026-08-16 (ADR §10):** `tasks/` включён в git по решению владельца — все
> утверждения ниже вида «tasks/ вне git» и «в CI-клоне нет tasks/» считать историческими.
> `task:check` в CI выполняется по-настоящему; `docs/` и `.opencode/` остаются локальными.

## Боли, которые решаем

1. Плоский каталог `tasks/` из 19 директорий: базовые числовые id, типизированные и легаси вперемешку.
2. Статус задачи непрозрачен: состояние вычисляется головой из четырёх frontmatter.
3. Процесс тяжёл для мелких задач: четыре документа и четыре круга согласования для правки на час.
4. `tasks/README.md` (35KB) тащит всё сразу: lifecycle, реестр, очередь, снимок, шаблоны разделов.
5. Нет инструмента: фиксация этапов и bootstrap сессии — ручные и медленные.
6. Роли `.opencode/agents/` доставляются плохо: в Claude Code не подхватываются, «вызов роли» = «вспомни прочитать файл».

## 1. Структура директорий

```text
tasks/
├── AGENTS.md            # маршрутизатор: карта файлов/скриптов, таблица команд CLI,
│                        #   роутинг «нужно X → зайди в Y / запусти Z», словарь статусов и треков
├── REGISTRY.md          # генерируется CLI целиком: реестр по типам + очередь работ + legacy-id
├── flows/
│   ├── full.md          # полный трек: 4 файла, 4 гейта, фазы, минимальные разделы, правила отката
│   └── lite.md          # lite-трек: task.md, гейты setup/result, критерии выбора, promote
├── tasks.config.json    # конфиг CLI — ручной файл владельца
├── _template/full/  _template/lite/
├── tools/               # CLI + tests/
├── archive/             # дотиповая эпоха как есть: 000/ 001/ 002/ 003/ 006/
├── contract/  infra/  back/
└── front/
    ├── ui/  guest/  owner/
```

Правила:

- тип — директория (front — с вложенными подтипами `ui|guest|owner`); задача — `<номер>-<слаг>`;
- номер трёхзначный, сквозной внутри типа, выдаёт CLI;
- **канонический task-id = путь без слага**: `front/guest/002`; слаг — украшение, CLI резолвит по номеру;
- старые id (`front-guest-002`) не переписываются задним числом: остаются в истории git и текстах,
  соответствие — поле `legacyId` в task.yaml → таблица в REGISTRY.md;
- `000`–`003`, `006` переезжают в `archive/` без переименования; `task-front-001` удаляется
  (декомпозирована, содержимое распределено — запись о декомпозиции остаётся в REGISTRY);
- будущие задачи очереди (`back-002`, `back-003`) заводятся стабами: директория + минимальный
  task.yaml, стадия «заявлена»;
- ручного ROADMAP/очереди нет: данные очереди — в `task.yaml` (`queue.*`), документ генерируется;
- нарратив «с чего начать сессию / приёмы» отдельным файлом не ведётся: источник — `result.md`
  закрываемых задач; «где мы» отвечает `task status`.

Тип `process` (процессные задачи, эта — первая) входит в конфиг.

## 2. task.yaml — канон состояния задачи

`.md`-файлы задач теряют frontmatter и остаются чистым содержанием. Канон — манифест:

```yaml
id: front/guest/002              # CLI сверяет с фактическим путём
slug: guest-screens
title: Гостевой сценарий — четыре экрана и сквозная проверка
track: full                      # full | lite
legacyId: front-guest-002        # только у мигрированных
depends: [front/ui/002, front/guest/001, infra/004, back/001]
queue:
  after: [back/001]
  parallel: [front/owner/001, infra/001]
  rationale: Вертикальная задача — экраны + сквозная проверка против реального API
gates:
  brief:  {status: согласовано, approvedAt: 2026-08-13, sha256: "…"}
  adr:    {status: согласовано, approvedAt: 2026-08-15, sha256: "…"}
  plan:   {status: согласовано, approvedAt: 2026-08-15, sha256: "…"}
  result: {status: черновик}
# --- опциональный рабочий контекст (hints для возврата в задачу) ---
workspace:
  branch: feat/front-guest-002
  worktree: ../minical-front-guest-002
  mr: https://github.com/…/pull/7
links:
  tracker: https://…              # внешний трекер, если задача ведётся ещё и там
uispec:
  - specs/ui/screens/guest-catalog.screen.md
meta: {rev: 12, selfHash: "…"}    # служебный блок CLI
```

### Гейты — единая модель треков

Гейт = именованная точка согласования, привязанная к документу. Словарь статусов прежний:
`черновик`/`согласовано`. Full: `brief → adr → plan → result` (четыре файла). Lite: `setup → result`
(оба на один `task.md` с секциями Контекст и цель / Решение / Чеклист / Результат и проверки).
Правило 11 в силе: `task approve` запускается только после явного подтверждения владельца.

### Checksum согласованных документов

`approve` записывает sha256 содержимого; `check` ловит «правили после согласования» —
автоматизация правила «правка согласованного возвращает документ в черновик». Легитимные
исключения объявляются стратегией хэширования в конфиге: `plan.md` хэшируется без колонки
«Состояние» (перевод пунктов — не правка плана); setup-гейт lite хэширует файл до `## Чеклист`.

### Стадии — вычисляются, не хранятся

| Стадия | Признак |
|---|---|
| заявлена | есть только task.yaml-стаб |
| постановка | первый гейт (brief/setup) в черновике |
| проектирование | brief согласован, adr или plan в черновике (только full) |
| реализация | постановочные гейты согласованы, пункты не все «завершено» (прогресс N/M) |
| результат | пункты завершены, result в черновике; сюда входит фаза «Проверка» (quality gates до согласования result) |
| завершена | все гейты согласованы |

Пять фаз старого README сворачиваются в эти стадии; «Проверка» — не машинная стадия, а
обязательный шаг внутри «результата», порядок — в flow.

### Правила треков

Критерии lite («если хоть одно "да" — full»): меняется контракт/generated? схема БД? есть
архитектурное решение? больше одной роли/зоны? работа больше ~дня? Решение: агент предлагает трек
с однострочным обоснованием при `task new`, владелец утверждает вместе с постановкой (первый гейт).
`task promote` эскалирует lite→full (секции разъезжаются по файлам); если setup уже был согласован —
все гейты full становятся черновиками (постановка сменила форму). Обратного пути full→lite нет.

### Рабочий контекст (workspace/links/uispec)

- Это hints, не канон: `check` на них не падает; `status` показывает их с живой проверкой
  («worktree: отсутствует»).
- Заполняются в момент возникновения: ветка/worktree — при старте реализации (шаг протокола
  скилла worktree-isolated-agent), mr — при открытии MR, uispec — на постановке/проектировании.
- При согласовании result CLI предупреждает о неубранных ветке/worktree и вычищает `workspace`
  (остаётся `mr` как история).
- `uispec` для CLI — просто список путей от корня репо (валидируется только существование).

### Single writer

`task.yaml` руками (и агентским Edit) не редактируется никогда — все мутации через CLI.
Защита: `meta.selfHash` — хэш нормализованного содержимого; ручная правка ломает его, `check`
сообщает; аварийный люк — `task repair <id>` (осознанное принятие состояния после ревью).
Выгоды: валидация в момент записи, канонический формат, атомарные связки (approve = статус +
дата + checksum одной операцией). Неизвестные схеме поля запрещены (расширение схемы = правка
конфига/инструмента).

## 3. CLI

Расположение: `tasks/tools/` (вне git, как весь tasks/ — прецедент uispec). TypeScript под
`node --experimental-strip-types`, из зависимостей — только `yaml` из корневых devDependencies.

```json
"task":       "test ! -d tasks || node --experimental-strip-types tasks/tools/task.ts",
"task:check": "test ! -d tasks || npm run task -- check",
"task:test":  "test ! -d tasks || node --experimental-strip-types --test tasks/tools/tests/"
```

### Команды

| Намерение | Команда |
|---|---|
| Инициализация каталога (для нового проекта) | `task init` — дефолтный конфиг + скелеты шаблонов; существующее не перезаписывает |
| Создать задачу / стаб | `task new <тип> <слаг> [--lite] [--stub]` |
| Стадия и контекст задачи | `task status [id]` — без id: незавершённые задачи; одна активная — сразу она |
| Сводка | `task list [--type X]` |
| Согласовать / откатить гейт | `task approve <id> <gate>` / `task draft <id> <gate>` (каскад: brief → adr, plan, result) |
| Сменить трек | `task promote <id>` |
| Поля манифеста | `task set <id> <путь> <значение>` / `task unset <id> <путь>`; списки — CSV и `+`/`-`; статусы/гейты через set нельзя |
| Инварианты | `task check` — схема всех task.yaml, id↔путь, дубли номеров, порядок гейтов, checksum-дрифт, selfHash, свежесть REGISTRY, lite с признаками full, межзадачная инвалидация по depends+датам |
| Реестр | `task registry` (генерация REGISTRY.md) / входит в `check` как drift-проверка |
| Разовая миграция | `task migrate` — код остаётся как документация процесса |
| Аварийный люк | `task repair <id>` |

### Структура и конфиг

`task.ts` (argv → диспетчер) + `lib/`: `config`, `manifest` (чтение/запись yaml, selfHash,
каноническая сериализация), `resolve` (id↔путь, номера), `stage`, `gates` (approve/draft,
каскады, checksum), `registry`, `check`. Вся проектная специфика — в `tasks.config.json`:
типы (включая вложенные `front/*`), пути, словарь статусов, состояния пунктов, треки с гейтами
и стратегиями хэширования (`ignore-state-column`, `until:<маркер>`). Инструмент про MiniCal не
знает ничего — вынос в отдельный проект не потребует правок кода. Конфиг — ручной файл владельца,
меняется только по его явному поручению; CLI валидирует его схему при каждом запуске.

### Тесты

`tasks/tools/tests/` (node:test, фикстурные мини-деревья): резолв и номера (дубли — негатив),
матрица стадий обоих треков, порядок гейтов, каскадный draft, checksum-дрифт и легитимные
исключения, selfHash, детерминизм REGISTRY, new/stub/init, promote. Плюс интеграционный smoke:
прогон `check` по живому дереву tasks/, когда оно есть. `npm run task:test` обязателен при
изменениях в `tasks/tools/` (аналог backend-гейта).

### Гейты качества

`npm run task:check` добавляется в «Обязательные проверки» и в корневой `npm test` рядом с
`uispec:validate`; в CI-клоне без `tasks/` guard штатно скипает.

## 4. Скилл, документы, роли, миграция

### Скилл `taskmaster`

`.opencode/skills/taskmaster/` (в Claude Code — через существующий симлинк). Тонкая обёртка:
`npm run task -- status [id]` → `tasks/AGENTS.md` (если не в контексте) → flow трека → активный
документ → работа в границах зоны. Таблица «намерение → команда»; запрет Edit на
`task.yaml`/`REGISTRY.md`. Frontmatter-description — с триггер-фразами для автозапуска
оркестратором: «продолжи задачу», «что по задаче X», «статус задач», «заведи задачу»,
«согласуй brief/plan/result», «что дальше по проекту», паттерн id `тип/номер`.
Регистрируется в таблице скиллов корневого AGENTS.md.

### Растворение ролей

`.opencode/agents/*.md` (структура «Назначение / Читать / Разрешено менять / Обязан / Запрещено»)
растворяются во вложенные AGENTS.md по месту работы; содержимое — в git; `.opencode/agents/`
удаляется:

| Роль | Куда |
|---|---|
| Backend | `apps/api/AGENTS.md` (дополняется) |
| Frontend | `apps/client/AGENTS.md` (дополняется) |
| Contract | `packages/contracts/AGENTS.md` (новый) |
| Infrastructure | `infra/AGENTS.md` (новый) |
| QA | `tests/AGENTS.md` (новый) |
| Database | `packages/database/AGENTS.md` (новый) |

Правило 10 «границы роли» переформулируется в «границы места». Таблица «Специализированные
агенты» корневого AGENTS.md заменяется картой вложенных AGENTS.md.

### Правки существующих документов

| Документ | Что меняется |
|---|---|
| корневой AGENTS.md | правило прохода вглубь по вложенным AGENTS.md; Bootstrap через `task status`/скилл; раздел «Что читать и когда» → «Навигация» в формате роутинга; дерево tasks/; «Обязательные проверки» + task:check; класс «изменяется только инструментом» (task.yaml, REGISTRY.md) рядом с «Generated: read-only»; таблица скиллов + taskmaster; карта AGENTS.md вместо таблицы ролей |
| docs/sources-of-truth.md | task.yaml — источник правды состояния задачи; REGISTRY.md — генерат |
| скилл worktree-isolated-agent | шаг «создал ветку/worktree → `task set <id> workspace.*`» |
| docs/domain-model.md, docs/ui-spec-kit/AUDIT.md | живые ссылки на старые пути задач → новые |
| tasks/README.md | удаляется (содержимое распределено: AGENTS/flows/REGISTRY/task.yaml) |

### Миграция (`task migrate`, разовая)

1. Перенос директорий по таблице соответствия; слаги существующих задач согласуются списком
   перед запуском; `front-001` удаляется.
2. task.yaml из текущих frontmatter: status → гейты; legacyId; даты согласований из снимка
   README, где известны (иначе поле опускается); sha256 с текущего содержимого (текущее =
   согласованное); depends/queue.* — из таблиц README.
3. Удаление frontmatter из всех .md.
4. Стабы back/002, back/003.
5. `task registry`; критерий завершения — зелёный `task check`.

### Порядок внедрения (каждый шаг оставляет репо рабочим)

CLI + тесты + конфиг + шаблоны (на фикстурах) → flows + tasks/AGENTS.md → миграция → правки
корневого AGENTS.md, растворение ролей, sources-of-truth, ссылки docs/ → скилл taskmaster →
полный набор «Обязательных проверок».

## Ключевые принципы (сводка)

- Канон состояния — task.yaml; писатель один — CLI; документы — чистый Markdown без frontmatter.
- Всё, что можно вычислить, — вычисляется (стадии, REGISTRY); всё, что решает человек, —
  фиксируется один раз рядом с задачей (queue.rationale, трек).
- Инструмент project-agnostic: специфика в tasks.config.json.
- Правила доставляются позиционно: вложенные AGENTS.md вместо ролей по вызову.
- CI-клон без tasks/ и docs/ — штатный случай: guard-скипы, как у uispec.
