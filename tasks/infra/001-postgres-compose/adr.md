# Architecture decision — infra/001

## Контекст

Согласованный `brief.md` требует контур из одного сервиса `postgres` с healthcheck, env-конфигурацией, двумя базами (`minical` и `minical_test`), интеграцией в npm scripts и проверкой в CI. Решение не отклоняется от `docs/architecture.md`: там локальный runtime описан как `web` + `api` + `postgres`, и задача реализует третий сервис из трёх, не меняя целевой контур. Отдельного пункта на правку `docs/architecture.md` не требуется.

Ограничения, зафиксированные измерением на хосте 2026-08-16:

- архитектура `arm64`, Homebrew 6.0.17 в `/opt/homebrew`;
- Docker Engine и Compose plugin отсутствуют; `colima` тоже нет;
- `psql` на хосте отсутствует — и задача не должна его требовать;
- порты 5432, 3001, 4010, 8081 свободны;
- PostgreSQL 18.6 — текущий стабильный минор (13 августа 2026); PostgreSQL 19 в бете, релиз запланирован на сентябрь 2026;
- CI существует с `infra/006`: `.github/workflows/ci.yml`, job `checks` на `ubuntu-latest`, где Docker предустановлен.

## Решение

### Р1. Провайдер — colima + docker CLI + Compose plugin из Homebrew

```bash
brew install colima docker docker-compose
```

На момент решения формулы дают colima 0.10.3 (зависимость — lima), docker 29.7.2, docker-compose 5.4.0.

**Обязательный шаг после установки**, иначе `docker compose` не находится: формула `docker-compose` ставит плагин мимо стандартного пути и в caveats требует прописать в `~/.docker/config.json`

```json
"cliPluginsExtraDirs": ["/opt/homebrew/lib/docker/cli-plugins"]
```

Шаг легко пропустить, а проявляется он невнятной ошибкой «docker: 'compose' is not a docker command», поэтому попадает в README дословно, а не пересказом.

Запуск VM — `colima start` с явно заданными ресурсами. Дефолтов достаточно для одиночной PostgreSQL, но параметры фиксируются явно ради воспроизводимости на другой машине.

Официальный образ PostgreSQL публикуется в том числе под `linux/arm64`, поэтому на этом хосте контейнер идёт нативно, без QEMU. Это принципиальное отличие от `infra/002`, где эмуляция неизбежна из-за x86_64-only Android SDK build-tools.

### Р2. Образ — `postgres:18`, Debian-based

Мажор фиксируется, минор — нет: патчи безопасности приезжают сами, мажорная версия внезапно не сменится. Требование brief «зафиксированный тег, не `latest`» выполняется.

Не `alpine`: musl и другая сборка ICU дают отличия в collation, а следующая работа над этим контуром — exclusion constraint и обращение со временем, где ближе к «обычному» PostgreSQL безопаснее. Выигрыш в размере локально не окупает риск.

Не `19`: на момент решения бета, релиз через месяц.

### Р3. Размещение — `infra/`

```text
infra/
├── compose.yml
├── .env.example
└── postgres/initdb/01-test-database.sh
```

Файл живёт в зоне, которая им владеет по `infra/AGENTS.md`. Следствие: project directory для Compose — `infra/`, оттуда же читается `.env`, туда же кладётся `.env.example`.

Имя проекта задаётся явно (`name: minical`). Без этого Compose берёт имя от каталога — получилось бы `infra`, и volume назывался бы `infra_...`, что при нескольких проектах на машине читается плохо.

### Р4. Сервис `postgres`

- единственный сервис;
- порт `${POSTGRES_PORT:-5432}:5432`;
- именованный volume под `/var/lib/postgresql/data`;
- healthcheck через `pg_isready` с явными `interval`, `timeout`, `retries`, `start_period`;
- политика перезапуска не задаётся (остаётся `no`): учебный контур не должен подниматься сам после перезагрузки хоста.

### Р5. Две базы

Основную создаёт штатный entrypoint официального образа из `POSTGRES_DB`. Вторую создаёт скрипт `infra/postgres/initdb/01-test-database.sh`, смонтированный в `/docker-entrypoint-initdb.d/`.

Скрипты из этого каталога исполняются **только при инициализации пустого каталога данных**. Это штатное поведение образа и одновременно ловушка: правка скрипта поверх существующего volume ничего не сделает. Фиксируется в README как следствие, а не как дефект.

### Р6. Переменные и значения по умолчанию

| Переменная | Значение по умолчанию | Назначение |
|---|---|---|
| `POSTGRES_USER` | `minical` | владелец обеих баз |
| `POSTGRES_PASSWORD` | `minical` | пароль локального контура |
| `POSTGRES_DB` | `minical` | база разработки |
| `POSTGRES_TEST_DB` | `minical_test` | база для проверок `back/002` |
| `POSTGRES_PORT` | `5432` | порт на хосте |

Все подставляются формой `${VAR:-default}`, поэтому `docker compose config` проходит из чистого checkout без `.env`. Слабый пароль по умолчанию — осознанное решение в рамках security boundary из `docs/architecture.md`: в MVP нет auth, контур пригоден только для локальной учебной среды и наружу не публикуется.

`.env.example` документирует набор переменных. Правок `.gitignore` не требуется: блок `.env` / `.env.*` / `!.env.example` там уже есть.

### Р7. npm scripts

| Скрипт | Команда |
|---|---|
| `db:up` | `docker compose -f infra/compose.yml up -d --wait` |
| `db:down` | `docker compose -f infra/compose.yml down` |
| `db:logs` | `docker compose -f infra/compose.yml logs -f postgres` |
| `db:reset` | `docker compose -f infra/compose.yml down -v` |

Флаг `--wait` у Compose v2 сам дожидается состояния healthy — собственный скрипт-поллер не нужен. Имена свободны: скриптов с префиксом `db:` или `docker` в проекте нет. Guard вида `test ! -d` не нужен — в отличие от `tasks/` и `docs/`, каталог `infra/` есть в git и приезжает с любым клоном.

### Р8. Проверка подключения — изнутри контейнера

`psql` на хосте отсутствует, и задача его туда не ставит: это была бы зависимость хоста ради одной проверки. Все обращения к базам идут через `docker compose exec -T postgres psql -U … -d …`. Acceptance criteria 5 и 6 выполняются этим способом.

### Р9. CI — отдельный job рядом с `checks`

В существующий `.github/workflows/ci.yml` добавляется job `compose` на `ubuntu-latest`, **параллельный** `checks`: критический путь проверок не удлиняется, растёт только расход минут раннера. Docker на GitHub-hosted Linux-раннерах предустановлен, ставить нечего.

Шаги: `checkout` → `docker compose -f infra/compose.yml config -q` → `up -d --wait` → `exec -T postgres psql` с тривиальным запросом к обеим базам → `down -v`.

Бюджет — 2–3 минуты; фактическое время фиксируется в `result.md`. `.github/workflows/hexlet-check.yml` не редактируется.

### Р10. Точка расширения — в `infra/AGENTS.md`

Описание того, как в контур позже добавляются сервисы `api` и `web`, шаг применения миграций и e2e-прогон (`infra/008`), кладётся в `infra/AGENTS.md`: это инструкция тому, кто будет менять зону, а не пользователю проекта. README получает команды и ссылку.

## Затронутые компоненты

| Компонент | Что происходит |
|---|---|
| `infra/` | новые `compose.yml`, `.env.example`, `postgres/initdb/01-test-database.sh` |
| `infra/AGENTS.md` | снимается утверждение о пустом каталоге, разводятся DoD зоны и scope задачи, добавляется точка расширения |
| `package.json` (корень) | четыре скрипта `db:*` |
| `.github/workflows/ci.yml` | job `compose` |
| `README.md` | разделы «Требования к окружению», «Команды», «Запуск», «Структура» |
| `.gitignore` | правок не требует — нужный блок уже есть |
| `apps/api`, `apps/client`, `packages/**`, контракт | не затрагиваются |

## Последствия и компромиссы

- `back/002` разблокирована: обе базы готовы, зона `infra/` закрыта заранее, и правки `compose.yml` из чужой зоны не потребуется.
- **Мажор сменится вскоре после закрытия задачи.** PostgreSQL 19 выходит в сентябре 2026, то есть примерно через месяц. Переход 18 → 19 требует `pg_upgrade` или dump/restore и остаётся отдельным решением. Это принятая цена за то, чтобы не строить учебный контур на бете.
- Ручные вызовы требуют `-f infra/compose.yml`; шпаргалки из интернета не работают дословно. Смягчается тем, что штатный путь — npm scripts.
- Init-скрипт не переигрывается на существующем volume: изменение набора баз потребует `db:reset`.
- Пароль по умолчанию слабый. Осознанно и ограничено локальной средой; любая публикация контура наружу требует отдельного решения по доступу.
- CI прибавляет job: wall-clock не растёт за счёт параллельности, расход минут растёт.
- Шаг с `cliPluginsExtraDirs` — единственное место, где установка требует ручной правки файла вне проекта. Он обратим и в файлы проекта не вмешивается.

## Рассмотренные альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| Docker Desktop, OrbStack | Работоспособны, но имеют лицензионные ограничения для коммерческого использования; тот же аргумент зафиксирован в ADR `archive/000` |
| Podman + podman-compose | Ещё один диалект CLI и отдельный слой compose-совместимости; выигрыша против colima нет |
| `postgres:18-alpine` | musl и другая сборка ICU дают отличия в collation — рискованно перед работой с ограничениями и временем; экономия размера локально не окупает |
| Пин по digest | Максимальная воспроизводимость ценой нечитаемого тега и ручных обновлений; для учебного контура избыточно |
| PostgreSQL 19 | На момент решения бета; релиз в сентябре 2026 |
| `compose.yml` в корне репозитория | Конвенционально и не требует `-f`, но выносит инфраструктурный файл за пределы владеющей им зоны; отклонено владельцем в пользу `infra/` |
| Отдельный сервис `postgres-test` на tmpfs | Полная изоляция тестовой базы ценой второго сервиса, порта и набора переменных; вторая база в том же инстансе решает задачу дешевле |
| Собственный скрипт ожидания healthy | `docker compose up --wait` уже делает ровно это |
| `psql` на хосте для проверок | Лишняя зависимость хоста; проверки идут через `docker compose exec` |

## Совместимость и миграция

Мигрировать нечего: данных нет, контур создаётся с нуля.

Существующие способы запуска не меняются и базы не требуют — `npm start -w @minical/api` (in-memory), `npm run web -w @minical/client`, `npm run mock:prism` работают как раньше. Обязательный набор проверок не приобретает зависимости от Docker: локальный полный прогон на машине без Docker остаётся возможным, а CI-job `compose` изолирован от job `checks`.

`back/002` получает готовые параметры подключения; конкретную форму строки (`DATABASE_URL` целиком или набор переменных) выбирает она сама — этот ADR её не предопределяет.

Откат: `npm run db:reset` удаляет данные и volume, `brew uninstall colima docker docker-compose` снимает провайдер. Установка файлы проекта не изменяет.
