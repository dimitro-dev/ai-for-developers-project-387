# infra/001 — PostgreSQL runtime-контур на Docker Compose

## Контекст и проблема

`docs/architecture.md` фиксирует локальный runtime MiniCal как три контейнера: `web`, `api`, `postgres`. Ни одного из них сейчас не существует: `infra/` содержит только `AGENTS.md` и `.gitkeep`, `Dockerfile` и `compose.yml` в репозитории отсутствуют, скриптов с префиксом `db:` или `docker` в `package.json` нет.

Фактическое состояние запуска на сегодня: backend `apps/api` реализует все 12 операций контракта на Express 5 поверх **in-memory хранилища** и запускается прямо из исходников (`npm start -w @minical/api` → `node src/server.ts`, сборки в `dist` нет); клиент поднимается на хосте через Expo; PostgreSQL не запускается нигде.

Ценность контура — разблокировать `back/002`: схема, миграции и exclusion constraint требуют работающей PostgreSQL, а установка базы прямо на хост противоречит согласованной архитектуре и не воспроизводится на другой машине. До появления персистентности вся занятость держится в памяти процесса, то есть последняя линия защиты от пересекающихся Booking (правило 3 корневого `AGENTS.md`) отсутствует — это известное ограничение, снимаемое только через реальную БД.

**Почему контур состоит из одного сервиса.** Прежняя редакция этой постановки исключала контейнер `api` на том основании, что он «оборачивает smoke-сервер». Это утверждение устарело: backend настоящий. Причина исключения другая и остаётся в силе — **до `back/002` backend к базе не подключается**, слоя persistence у него нет, поэтому в контуре ему не с чем взаимодействовать. Контейнер `web` дублирует `npm run web -w @minical/client` на хосте, а dev-режим с hot reload внутри контейнеров вынесен в non-goals — значит web-образ понадобился бы только ради production-like просмотра собранного бандла, которым в учебном проекте никто не пользуется, зато каждый `up --build` тянул бы медленный `expo export`. Оба контейнера добавляются отдельной задачей — вместе с персистентностью, когда подключение станет осмысленным.

**Docker на хосте отсутствует.** Проверено 2026-08-16: `docker` и `colima` в `PATH` не найдены. Это согласуется с `archive/000`, где отсутствие Docker зафиксировано в ADR, плане и таблице установленных инструментов `result.md`. По fallback-правилу из `archive/000/brief.md` (п. 1 функциональных требований) агент не устанавливает обязательный инструмент молча: он предлагает безопасный вариант с обоснованием и действует только после явного подтверждения владельца. Провайдер согласован владельцем 2026-08-16 — **colima + `docker` CLI + `docker compose` plugin через Homebrew**. В `archive/000` colima фигурировала лишь как кандидат («финальный выбор провайдера остаётся за пользователем»), поэтому решение принимается здесь, а не наследуется.

## Цель

Получить воспроизводимый локальный runtime-контур PostgreSQL на Docker Compose с единственным сервисом `postgres`, healthcheck и env-конфигурацией, в который `back/002` подключается для применения схемы и миграций без пересмотра инфраструктуры.

Контур даёт **две базы**: `minical` для разработки и `minical_test` для проверок. Вторая нужна потому, что DoD зоны `packages/database` требует подтверждать отсутствие двойной брони concurrency-тестом на реальной PostgreSQL, а не на моке; без отдельной базы такой тест разрушал бы данные разработки. Создание баз относится к инфраструктуре контура, поэтому решается здесь, а не в `back/002`: `compose.yml` принадлежит зоне `infra/`, и правка его из чужой зоны была бы нарушением границ.

Из чистого checkout контейнер должен подниматься одной документированной командой, `docker compose config` — проходить без ручного шага копирования `.env`, а корректность контура — проверяться в CI, а не только на машине автора.

## Зависимости

- `archive/000` — monorepo на npm workspaces и корневые npm scripts; там же зафиксировано отсутствие Docker и правило про молчаливую установку инструментов.
- `infra/006` — CI на GitHub Actions уже существует (`.github/workflows/ci.yml`, job `checks` на `ubuntu-latest`); проверка контура встраивается в него, а не заводится с нуля.
- Docker-провайдер на хосте — отсутствует. Установка выполняется только после явного подтверждения владельца (получено 2026-08-16); до неё зависимые пункты плана считаются заблокированными и фиксируются в `plan.md` и `result.md`.
- Контур строится вокруг пустой PostgreSQL и не зависит от доменной модели, контракта и backend.

**Потребители результата:** `back/002` (схема, миграции, exclusion constraint, concurrency-тест) — прямой и основной; `infra/002` — только в части рабочего Docker Engine, остальной scope этой задачи ей не нужен.

## Пользовательские сценарии

Продуктовых сценариев нет — задача инфраструктурная. Потребители:

- разработчик или агент из чистого checkout выполняет документированную последовательность и получает поднятый `postgres` без ручной донастройки хоста;
- задача `back/002` получает контейнер с постоянным volume и подключается к базе `minical` по переменным окружения для применения схемы и миграций;
- она же прогоняет concurrency-тест против `minical_test`, не затрагивая данные разработки;
- будущая задача, вводящая контейнеры `api` и `web`, расширяет тот же `compose.yml` по документированной точке расширения.

## Функциональные требования

1. **Docker-провайдер.** Проверить наличие Docker Engine и Compose plugin на хосте. При отсутствии — установить согласованный вариант (colima + `docker` CLI + `docker compose` plugin через Homebrew) и только после явного подтверждения владельца. Фактические версии фиксируются в `result.md`.
2. **`compose.yml`** с единственным сервисом `postgres`: официальный образ PostgreSQL с зафиксированным тегом версии (не `latest`), именованный volume для данных, публикация порта на хост.
3. **Healthcheck** сервиса `postgres` через `pg_isready`.
4. **Конфигурация через environment.** Все переменные в `compose.yml` имеют значения по умолчанию через синтаксис `${VAR:-default}`, поэтому `docker compose config` из чистого checkout проходит без предупреждений о неопределённых переменных и без обязательного копирования `.env`. В репозиторий добавляется `.env.example` как документация доступных переменных — сейчас в проекте нет ни одного файла `.env*`, при том что корневой `.gitignore` уже содержит блок `.env` / `.env.*` / `!.env.example`, то есть исключение подготовлено, а файла нет. Реальный `.env` остаётся игнорируемым и лишь переопределяет defaults.
5. **Две базы.** Скрипт инициализации создаёт `minical` и `minical_test` при первичной инициализации пустого volume. Имена баз конфигурируются через те же переменные окружения.
6. **Интеграция с корневыми npm scripts:** запуск, остановка, просмотр логов, полный сброс данных с удалением volume. Существующие команды продолжают работать без изменений; скриптов с префиксом `db:` или `docker` в проекте сейчас нет, конфликта имён не возникает.
7. **Проверка в CI.** В существующий `.github/workflows/ci.yml` добавляется job, который выполняет `docker compose config`, поднимает контур, дожидается состояния healthy, подтверждает, что обе базы принимают подключение, и останавливает контур. `.github/workflows/hexlet-check.yml` не редактируется — это внешний генерируемый чек учебной платформы.
8. **README.** Обновляются разделы, которые сейчас противоречат новому состоянию или его не описывают:
   - «Требования к окружению» — содержит утверждение «Docker для текущего этапа **не требуется**: Docker/Compose-контур вынесен в отдельную задачу», которое становится неверным; добавляются требование к Docker-провайдеру и способ его установки;
   - «Команды» — добавляются команды контура;
   - «Запуск» — добавляется поднятие базы, занятый порт, переменные окружения, процедура полного сброса состояния и явное предупреждение, что контур предназначен только для локальной учебной среды;
   - «Структура» — содержит строку `infra Docker/Compose (отдельная задача)`, которая перестаёт быть верной.
9. **`infra/AGENTS.md`.** Снять утверждение «Каталог пока пуст (`.gitkeep`) — зона активируется задачей `infra/001`» и развести Definition of Done зоны («поднимать web, API и PostgreSQL через Docker Compose», «`docker compose up --build` поднимает заявленные runtime services») со scope этой задачи: иначе зональный файл читается как невыполненное требование к уже закрытой работе.
10. **Точка расширения** — документируется без реализации: как в контур позже добавляются сервис `api`, сервис `web`, шаг применения миграций и сквозной e2e-прогон против контура (`infra/008`).

## Нефункциональные требования

- Воспроизводимость: контур поднимается из чистого checkout без ручных шагов помимо документированных команд.
- Версия базового образа PostgreSQL зафиксирована конкретным тегом, а не `latest`.
- Данные сохраняются между `down` и `up` за счёт именованного volume; способ полного сброса состояния документирован и проверен.
- Скрипт инициализации исполняется только при первичной инициализации пустого volume — это штатное поведение официального образа. Следствие документируется явно: правка скрипта не применяется к уже существующему volume, для повторного исполнения нужен полный сброс. Иначе это выглядит как поломка.
- Конфигурация задаётся только через environment; значения по умолчанию безопасны для локальной среды и не требуют ручного копирования `.env`.
- Образы и Git-история не содержат секретов и реального `.env`.
- Соблюдается security boundary из `docs/architecture.md`: в MVP нет auth, поэтому контур пригоден только для локальной учебной среды и наружу не публикуется.
- Установка Docker-провайдера обратима и не изменяет файлы проекта.
- CI-job не удлиняет критический путь проверок непропорционально: бюджет времени согласуется в `adr.md`, фактическое время фиксируется в `result.md`.

## API impact

`NONE` — TypeSpec-контракт и generated-артефакты не меняются. Контур не содержит прикладного API.

## Acceptance criteria

1. Установка Docker-провайдера согласована с владельцем и выполнена; фактические версии `docker` и Compose plugin зафиксированы в `result.md`.
2. `docker compose config` выполняется из чистого checkout без ошибок и без предупреждений о неопределённых переменных, без ручного создания `.env`.
3. Одна документированная команда из чистого checkout поднимает сервис `postgres`.
4. Сервис `postgres` достигает состояния healthy (healthcheck `pg_isready` проходит).
5. К базе `minical` успешно подключается клиент с параметрами по умолчанию из `.env.example`.
6. База `minical_test` существует и принимает подключение после первого запуска контура.
7. Данные сохраняются после `docker compose down` и повторного `up`.
8. Документированная процедура полного сброса выполнена и проверена: после неё контур поднимается заново, обе базы создаются с нуля и пусты.
9. В образах и в Git нет секретов и реального `.env`; `.env.example` содержит только безопасные значения по умолчанию.
10. README описывает требования к хосту, установку провайдера, команды, занятый порт, переменные окружения, процедуру сброса и предупреждение о локальном назначении контура; устаревшие утверждения о ненужности Docker и о «отдельной задаче» в разделе «Структура» сняты.
11. `infra/AGENTS.md` не утверждает, что каталог пуст, а его Definition of Done не читается как невыполненное требование к этой задаче.
12. CI-job контура зелёный на PR; `.github/workflows/hexlet-check.yml` не изменён.
13. Полный набор обязательных проверок из корневого `AGENTS.md` зелёный: `contracts:format:check`, `generate:check`, `typecheck`, `npm test`, `task:check`, `uispec:validate`, `npm test -w @minical/api`, `npm test -w @minical/client`.
14. Все выполненные команды и результаты проверок зафиксированы в `result.md`.

## Non-goals

- **контейнер `api`** — до `back/002` backend не имеет слоя persistence и к базе не подключается, поэтому в контуре ему не с чем взаимодействовать; запускается из исходников на хосте. Добавляется отдельной задачей вместе с персистентностью;
- **контейнер `web`** — дублирует `npm run web -w @minical/client` на хосте; dev-режим с hot reload вынесен в non-goals, а собранный бандл production-like в учебном проекте не просматривается. Добавляется той же отдельной задачей;
- Dockerfile для `apps/api`, Dockerfile для `apps/client`, `.dockerignore` — с единственным официальным образом PostgreSQL в контуре нет ни одной сборки образа;
- схема PostgreSQL, миграции, seed-данные и exclusion constraint — зона `back/002`; здесь только пустые базы;
- подключение backend к PostgreSQL и слой persistence — `back/002`;
- e2e-проверки: web-прогон на Playwright — `infra/008`, выбор native-инструмента — `infra/007`; здесь контур только готовится к тому, чтобы они были возможны;
- Docker-образ android-builder и сборка APK — `infra/002`; ей из этой задачи нужен только рабочий Docker Engine;
- документирование клиентской переменной `EXPO_PUBLIC_API_BASE_URL` в README — она сейчас описана только в коде и task-документах, но к контуру базы не относится;
- адрес API для Android Emulator — вопрос клиентской конфигурации и APK;
- production deployment, публикация образов в registry, reverse proxy и TLS, оркестрация;
- auth и любое ограничение доступа к admin;
- dev-режим с hot reload внутри контейнеров: Expo dev server и Metro продолжают работать на хосте.
