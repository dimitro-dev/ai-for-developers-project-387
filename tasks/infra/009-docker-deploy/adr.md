# Architecture decision — infra/009

## Контекст

Brief согласован 2026-08-18 и принял три решения (Р-brief-1..4): по ссылке открывается приложение
целиком — гость на `/`, владелец на `/admin`; клиент ходит в API по тому же origin через маркер
`same-origin`; деплой выполняется раньше персистентности. ADR отвечает на пять оставленных ему
вопросов: базовый образ и версия Node, способ раздачи двух бандлов и порядок middleware, дом и
состав демо-сида, платформа публикации, совместимость с `back/002`.

Факты кодовой базы, которые ограничивают решение:

- **Сборки у API нет.** `make -C apps/api start` выполняет `node src/server.ts` — Node исполняет
  TypeScript через нативный type stripping. `.nvmrc` — `26`, корневой `engines` — `>=24`. Внутри
  физического `node_modules` Node отказывается стриптить типы
  (`ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`), поэтому зависимости в образе обязаны ставиться
  из корня репозитория с сохранением симлинков npm workspaces — требование уже зафиксировано в
  `apps/api/architecture.md`, раздел «Запуск из исходников».
- **Middleware-цепочка одна и порядок значим:** `securityHeaders → cors → express.json → цикл по
  ROUTES → notFoundHandler → errorMiddleware` (`apps/api/src/app.ts`). Тест
  `routes.contract.test.ts` сверяет `ROUTES` с контрактом 1:1 и падает от любой лишней записи;
  тест `api.test.ts` фиксирует «вне контракта → 404 с JSON-телом ровно `{code, message}`».
- **Операции владельца уже живут под `/admin/...`** (`/admin/settings`, `/admin/event-types`) —
  префикс `/admin` делится между операциями контракта и статикой владельческого бандла.
- **`expo export --platform web` кладёт бандл с абсолютными путями ассетов от корня**
  (`/_expo/static/...`, `/favicon.ico`). Базовый префикс в `app.json` не настроен; без него
  владельческий бандл, поднятый на `/admin`, запрашивал бы ассеты из корня — из чужого бандла.
- **Ветки same-origin в `resolveApiBaseUrl()` нет**, а дев-адреса `http://localhost:4010` и
  `http://10.0.2.2:4010` — строковые литералы модуля `apps/client/src/api/config.ts`: без
  отдельной меры они попадут в production-бандл и нарушат AC4.
- **Рантайм-зависимости API минимальны:** `express@5`, `zod`, workspace-пакет
  `@minical/backend-contract` (сам зависит только от `zod`). Клиентские зависимости (Expo,
  React Native) нужны только на этапе сборки бандлов.

## Решение

### 1. Базовый образ — `node:26-slim`, multi-stage, запуск исходников без сборки

Оба этапа Dockerfile используют `node:26-slim`: major-версия следует `.nvmrc`, Debian-основа
выбрана вместо Alpine, чтобы не ловить musl-специфику нативных бинарей Expo-toolchain
(`lightningcss` и родня) на этапе сборки бандлов; экономия размера сверх отказа от dev-зависимостей —
non-goal брифа. Сам файл `.nvmrc` Dockerfile не читает: make-цель могла бы передать версию через
`--build-arg`, но платформа собирает образ без make, и дефолт в `FROM` обязателен — версия
дублируется, двойной дом факта помечается комментарием со ссылкой на `.nvmrc` и обновляется
вместе с ним.

- **Этап build:** `npm ci` по корневому `package-lock.json` (все workspaces, включая dev),
  затем два прогона `expo export --platform web` (см. §2).
- **Этап runtime:** копируются **только** манифесты цепочки API — корневые
  `package.json` + `package-lock.json`, `apps/api/package.json`,
  `packages/backend-contract/package.json`; полный набор манифестов workspaces непригоден —
  из-за особенности npm он протаскивает dev-зависимости вопреки `--omit=dev` (проверено на
  npm 11, штатном для Node 26). Затем `npm ci --omit=dev` с workspace-фильтром
  `apps/api` — ставятся только `express`, `zod` и симлинк `@minical/backend-contract`; исходники
  `apps/api/src` и `packages/backend-contract/src` (включая generated), готовые бандлы из этапа
  build. Транспиляции нет и в образе: `CMD ["node", "apps/api/src/server.ts"]` — тот же способ
  запуска, что и локально. Процесс работает под `USER node`, `NODE_ENV=production`.

`.dockerignore` заводится по FR5: `node_modules`, `.git`, `apps/client/dist`,
`apps/client/android`, `apps/client/ios`, `.expo`, локальные каталоги харнессов
(`.claude/`, `.opencode/`, `CLAUDE.md`, `.mcp.json`), логи и `.env*`.

### 2. Два web-бандла: два прогона `expo export`, владельческий — с базовым префиксом `/admin`

Режим и адрес API вшиваются при сборке, поэтому этап build выполняет экспорт дважды из одного
кода:

| Бандл | `EXPO_PUBLIC_APP_MODE` | Базовый префикс | Куда кладётся |
|---|---|---|---|
| Гостевой | `guest` | нет | `apps/client/dist/guest` |
| Владельческий | `owner` | `/admin` | `apps/client/dist/owner` |

Оба собираются с `EXPO_PUBLIC_API_BASE_URL=same-origin` (§4) и с флагом `--clear`: значения
`EXPO_PUBLIC_*` не входят в ключ transform-кеша Metro, и второй экспорт без сброса кеша может
молча переиспользовать модули первого — владельческий бандл оказался бы гостевым. Проект с этим
уже сталкивался: `EXPO_ARGS=--clear` в `apps/client/Makefile` заведён ровно по этой причине.
Каталоги под `dist/` уже накрыты `.gitignore`; существующая цель `make -C apps/client build`
не меняется.

Базовый префикс задаётся штатным механизмом Expo — `experiments.baseUrl`: заводится
`app.config.ts`, который расширяет `app.json` и выставляет префикс из переменной окружения
времени конфигурации (не `EXPO_PUBLIC_*` — она нужна конфигу, а не бандлу; имя —
`EXPO_WEB_BASE_URL`). Переменная задаётся только в Dockerfile при сборке владельческого бандла;
пустое значение — префикса нет, локальная разработка (`expo start`) не меняется. С префиксом
ассеты владельческого бандла адресуются как `/admin/_expo/...` и не пересекаются с гостевыми.

Привязывать префикс к `EXPO_PUBLIC_APP_MODE=owner` нельзя: локальный запуск владельческой
половины через dev-сервер получил бы префикс `/admin` и потерял ассеты.

### 3. Раздача статики: `express.static` после цикла `ROUTES`, до `notFoundHandler`

Раздачу выполняет тот же Express-процесс без новых зависимостей (`express.static` — часть
Express, NFR2). Точка вставки — **между циклом монтирования `ROUTES` и `notFoundHandler`**:

```text
securityHeaders → cors → express.json → цикл по ROUTES →
  static(dist/guest) на «/» → static(dist/owner) на «/admin» →
notFoundHandler → errorMiddleware
```

Следствия такого порядка:

- операции контракта затенить невозможно — они смонтированы раньше; `GET /admin/settings` уходит
  в API, `GET /admin/_expo/...` — в статику владельца. Сам `GET /admin` (без завершающего слэша)
  отвечает штатным `301`-редиректом `serve-static` на `/admin/`, где отдаётся `index.html`:
  браузер проходит это прозрачно, а проверка AC3 следует редиректу (`curl -L`);
- запрос без файла проваливается сквозь `express.static` дальше по цепочке — «вне контракта →
  404 в JSON» сохраняется как есть, SPA-fallback не вводится (FR9: навигация клиента не использует
  адресную строку);
- security-заголовки и CORS стоят раньше и накрывают статические ответы.

В реестр `ROUTES` записи не добавляются — статика монтируется отдельным шагом `createApp`, тесты
соответствия контракту не затрагиваются. `createApp` получает необязательный параметр с путями
двух каталогов; `server.ts` передаёт их, когда каталоги существуют (пути — конвенция
`apps/client/dist/{guest,owner}` относительно корня репозитория, вычисляются от файла, а не от
`cwd`). Без каталогов приложение стартует как сейчас — API-only, локальная разработка и тесты
зоны не меняются. Документированный инвариант «единственная точка вставки middleware — до цикла
маршрутов» уточняется в `apps/api/architecture.md`: у цепочки появляется вторая точка — статика
после маршрутов.

### 4. same-origin: маркер в `EXPO_PUBLIC_API_BASE_URL`, дев-дефолты — под `__DEV__`

`resolveApiBaseUrl()` получает первую ветку: значение `same-origin` → `baseUrl = ''` — запросы
уходят на origin страницы (Р-brief-2). Остальные непустые значения работают как раньше.

Чтобы выполнить AC4 (в бандлах нет `localhost:4010`, `localhost:3001`, `10.0.2.2`), дев-дефолты
уводятся под `__DEV__`: Metro в production-экспорте заменяет `__DEV__` на `false` и выкидывает
мёртвую ветку вместе с литералами. Ключевое условие: литералы **перестают быть экспортами
модуля** и существуют только внутри `__DEV__`-ветки `resolveApiBaseUrl` — Metro не делает
tree-shaking экспортов, и `export const DEFAULT_API_BASE_URL` пережил бы минификацию. Тесты,
которые сегодня импортируют эти константы, переписываются на проверку возвращаемых значений.
В production-сборке незаданная `EXPO_PUBLIC_API_BASE_URL` — явная ошибка конфигурации при старте
приложения, а не молчаливый уход на мок: это буква FR8 («пустое значение неотличимо от
"переменную забыли задать"»). Поведение маркера и ошибки фиксируется тестами зоны клиента
(`config.test.ts`).

### 5. Демо-сид: отдельный модуль `apps/api`, наполняется через use-cases

Сид — отдельный модуль зоны API (`apps/api/src/bootstrap/seed.ts`), вызывается из `server.ts`
после создания хранилища, когда флаг включён. Composition root остаётся один — `server.ts`.

Наполнение идёт **через существующие use-cases** (`completeAdminSetup`,
`createAdminEventType`), а не записью в store напрямую: доменные инварианты (валидная таймзона,
делимость интервала, корректность правил) проверяются бесплатно, и сид не разъезжается с доменом
при его изменении. Состав: настроенный календарь (имя владельца, таймзона, правила доступности
рабочих дней, интервал 30 минут) и два типа встреч разной длительности — минимум, при котором
сценарий брифа проходится целиком; конкретные значения — деталь плана.

`SEED_DEMO` парсится в `config.ts` по общей дисциплине «мусор → отказ старта»: `1`/`true` —
включён, `0`/`false`/пусто/нет переменной — выключен, любое другое значение — ошибка запуска.
По умолчанию выключен (AC10), на публичном деплое включается переменной окружения.

### 6. Слой команд: цели зоны `infra/`, делегаты в корне, расширение `lint-docs`

Строки `docker build` / `docker run` живут в `infra/Makefile` — целями `image-build` и
`image-run` (запуск с пробросом `PORT`, `SEED_DEMO`, `PUBLIC_WEB_URL`). Корневой `Makefile`
получает одноимённые делегаты по образцу `db-*` — так их показывает корневой `make help` (AC7).

FR12 обещает, что сырые вызовы `docker` в документации ловит гейт, но сейчас `scripts/lint-docs`
знает только `docker compose`. Список `RAW_CALLS` расширяется паттернами `docker build` и
`docker run` — иначе обещание гейта не выполняется. Существующее задокументированное исключение
в `infra/README.md` уже стоит под маркером `allow-raw` и не пострадает.

CI не меняется: сборка образа в `gates` не входит (Docker-этап в фазе «Проверка» выполняется
вручную, платформа собирает образ сама — non-goal «деплой из CI»), `hexlet-check.yml` не
трогается (NFR3).

### 7. Платформа публикации: Render, запасной — Railway

Основной вариант — **Render**: собирает образ по Dockerfile из корня репозитория, назначает
`PORT` сам, даёт публичный HTTPS-адрес `*.onrender.com` без настройки доменов. Переменные
`SEED_DEMO=true` и `PUBLIC_WEB_URL=<выданный адрес>` задаются в настройках сервиса;
`PUBLIC_WEB_URL` становится известен после создания сервиса — инициализация двухшаговая
(создать → вписать адрес в окружение, платформа перезапустит сервис).

Сид и AC8 совмещаются **порядком публикации**: с включённым сидом онбординг уже завершён, и
повторный `PUT /admin/setup` штатно отвечает `409 ONBOARDING_ALREADY_COMPLETED` — мастер
онбординга на таком инстансе не показать. Поэтому сценарий 2 (онбординг на `/admin`,
бронирование на `/`) проверяется и фиксируется в `result.md` **до включения `SEED_DEMO`**, на
пустом хранилище; после проверки флаг включается, и установившееся состояние ссылки — настроенный
демо-календарь, где посетитель по-прежнему может завести тип встречи, изменить настройки и
забронировать слот. Порядок закрепляется в инструкции публикации `infra/README.md`.

Критерий переключения на Railway: бесплатный план Render не собирает образ (лимиты билдера) или
не держит приложение (память инстанса, политика останова) — то есть сценарий 2 брифа не
проходится по выданной ссылке. Переключение — не новый ADR: решение и причина фиксируются в
`result.md`, инструкция публикации в `infra/README.md` правится на фактическую платформу.

### 8. Размещение: `Dockerfile` и `.dockerignore` в корне, исключение фиксируется в контракте

По Р-brief-4 внешняя проверка сильнее контракта размещения: `Dockerfile` и парный
`.dockerignore` лежат в корне. Отступление фиксируется **обоими** способами, названными в брифе:
строкой-исключением в `docs/sources-of-truth.md` (дом «Локальный runtime и build» получает
явную оговорку про корневой Dockerfile с причиной) и разделом эксплуатации в `infra/README.md`.
Молчаливого исключения нет; владелец файла — зона `infra/`, что уже допускает её `AGENTS.md`
(«разрешено менять: `Dockerfile*`»).

Отдельно про правило 12 («команда — рецепт цели в `Makefile`») внутри самого Dockerfile: его
этапы содержат `npm ci` и два `expo export` — строки, похожие на рецепты make-целей. Решение:
Dockerfile признаётся **исполняемым рецептом**, а не документацией — как и рецепт цели make, он
и есть дом своих строк; правило 12 запрещает пересказ команд в документации, и `lint-docs`
проверяет именно её. Вызывать make из build-этапа не вариант: в `node:26-slim` make нет, ставить
его — лишняя сборочная зависимость; а рецепты не дублируются по смыслу — `make -C apps/client
build` собирает один бандл в `dist/` с локальным окружением, этапы образа — два бандла с другими
переменными и каталогами. Эта трактовка вписывается в ту же оговорку `docs/sources-of-truth.md`.

## Последствия и компромиссы

- **Данные не переживают перезапуск** (цена Р-brief-3): публичная ссылка после каждого рестарта
  показывает демо-состояние сида, а не настройки предыдущего посетителя. Снимается задачей
  `back/002`.
- **Мастер онбординга на устоявшейся публичной ссылке не воспроизвести**: с включённым сидом
  setup завершён, повторный — `409`. Проверка AC8 встроена в порядок публикации (§7: сценарий 2 —
  до включения `SEED_DEMO`); посетителю остаются настройки, типы встреч и бронирование.
- **Сборка образа удвоена вторым экспортом** (NFR7): два прогона `expo export` — осознанная цена
  за целое приложение по одной ссылке; если ручной прогон окажется непрактично долгим, компромисс
  уже зафиксирован здесь и пересматриваться будет явно.
- **Production-сборка клиента без `EXPO_PUBLIC_API_BASE_URL` перестаёт собирать рабочий бандл
  молча**: незаданная переменная — явная ошибка вместо тихого ухода на мок. Это касается и
  будущих production-сборок Android APK — им переменная нужна была и раньше, теперь забывчивость
  видна сразу.
- **Версия Node живёт в двух местах** (`.nvmrc` и `FROM` Dockerfile) — неустранимо, помечено
  комментарием.
- **`/admin` публикуется без auth** — правило 9 и Security boundary (`docs/architecture.md`):
  публикация не притворяется защищённой, `infra/README.md` называет это ограничение явно;
  введение защиты — отдельная задача (non-goal).
- **Бесплатный инстанс Render засыпает** — первый запрос после простоя ждёт холодного старта;
  для учебной публикации приемлемо, в `infra/README.md` упоминается, чтобы «висит и не отвечает»
  не читалось как поломка.
- **Инвариант зоны API ослабляется осознанно**: middleware-цепочка получает вторую точку вставки
  (статика после маршрутов); формулировка в `apps/api/architecture.md` обновляется, чтобы код и
  документ не разъехались.

## Рассмотренные альтернативы

| Вариант | Почему отвергнут |
|---|---|
| Базовый образ `node:26-alpine` | musl-специфика нативных бинарей Expo-toolchain на этапе сборки; выигрыш — только размер, а его оптимизация — non-goal |
| Раздача обоих бандлов из корня без префикса (опора на хэш-уникальность имён `/_expo/...`) | работает по совпадению: неявная зависимость от схемы именования Metro, конфликт нехэшированных файлов (`favicon.ico`, `metadata.json`), порядок монтирования решает «кто выиграл корень» |
| Отдельный веб-сервер для статики (nginx, `serve`) | второй процесс и новая рантайм-зависимость против NFR2 и FR6; supervisor внутри контейнера — лишняя сущность |
| SPA-fallback «неизвестный путь → index.html» | навигация клиента не использует адресную строку (linking отключён сознательно, ADR front-задач); fallback сломал бы «вне контракта → 404 в JSON» и тест G3 |
| Префикс `/admin` через привязку к `EXPO_PUBLIC_APP_MODE` | локальный dev владельческой половины получил бы префикс и потерял ассеты; префикс — свойство публикации, а не режима |
| Рантайм-этап: полный `npm ci --omit=dev` без workspace-фильтра | в образ приезжают production-зависимости клиента (Expo, React Native) — сотни мегабайт, не нужных серверу |
| Сид записью в store напрямую | обходит доменную валидацию; разъедется с доменом при первом изменении инвариантов |
| Сид как HTTP-вызовы самого API после старта | требует оркестрации «дождаться listen», усложняет composition root; use-cases дают то же без транспорта |
| Платформа Fly.io | требует CLI-инициализации и конфиг-файла в репозитории; Render/Railway собирают образ из репозитория без дополнительных артефактов |
| Оставить `lint-docs` без паттернов `docker build`/`docker run` | FR12 обещает гейт против сырых вызовов docker; без расширения обещание пустое |

Решения, принятые в брифе (один образ с обоими бандлами, маркер `same-origin` вместо пустой
строки или вшитого адреса, деплой раньше персистентности, Dockerfile в корне), здесь не
пересматривались — см. Р-brief-1..4.

## Совместимость и миграция

- **`back/002` (персистентность).** Образ не переписывается: `pg`-зависимость попадёт в корневой
  lockfile и приедет в рантайм-этап тем же `npm ci` с workspace-фильтром; на деплое добавятся
  managed-PostgreSQL платформы и переменная подключения. Форму строки подключения и момент
  прогона миграций выбирает `back/002` (граница зафиксирована в `infra/AGENTS.md`); судьба
  `SEED_DEMO` при постоянном хранилище (идемпотентность или отключение) — тоже её решение.
- **`infra/002` (Android builder)** — не затрагивается: другой образ с другим назначением.
- **Локальная разработка не меняется:** без каталогов бандлов API стартует как раньше;
  `make -C apps/client web`, мок Prism и compose-контур PostgreSQL работают как до задачи.
- **Контракт и generated** — без изменений (API impact `NONE` подтверждён: статика монтируется
  вне `ROUTES`, тесты соответствия контракту остаются страховкой от дрейфа).
- **Обратный путь:** удаление `Dockerfile`, `.dockerignore`, целей `image-*` и статик-параметра
  `createApp` возвращает репозиторий в текущее состояние; изменения клиента (`same-origin`,
  `__DEV__`-дефолты) самостоятельны и полезны независимо от деплоя.
