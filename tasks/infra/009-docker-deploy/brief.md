# infra/009 — Публикация приложения: Docker-образ и деплой

## Контекст и проблема

Учебная платформа добавила шаг «Docker и деплой» с четырьмя требованиями: в репозитории лежит
`Dockerfile`; по нему собирается образ; запущенный контейнер стартует приложение сам; приложение
слушает порт из переменной `PORT`; после деплоя у приложения есть публичная ссылка, и она указана
в репозитории. Переменная `PORT` существует потому, что порт назначает облако, а не приложение:
сервис, жёстко занявший `3001`, снаружи недоступен.

**Что уже есть.** `apps/api` читает `PORT` в `src/config.ts`, проверяет диапазон `1..65535`
и отказывается стартовать на мусорном значении вместо тихого отката к умолчанию; `app.listen(port)`
без явного хоста слушает все интерфейсы, что для контейнера и требуется. То есть третье требование
закрыто до начала задачи.

**Чего нет.** `Dockerfile` в репозитории отсутствует — ни одного файла. Нет `.dockerignore`, образа,
деплоя и ссылки. Docker в проекте используется, но для другого: `infra/compose.yml` поднимает
PostgreSQL для локальной разработки (`infra/001`), а задача `infra/002` описывает Docker-образ как
сборочную машину для APK. Ни то, ни другое не упаковывает приложение.

**Почему это не сводится к «написать Dockerfile».** Репозиторий содержит две половины, а требование
говорит про один порт и одну ссылку:

- `apps/api` — сервер, отвечающий JSON; страниц у него нет. По ссылке человек увидел бы
  `{"status":"ok"}` и решил бы, что приложение не работает.
- `apps/client` — интерфейс; для web он собирается в статические файлы (`make -C apps/client build`),
  которые кто-то должен отдавать по HTTP.

К этому добавляются три свойства клиента, которые проявляются только при публикации:

1. **Режим клиента вшивается при сборке.** `EXPO_PUBLIC_APP_MODE` подставляется в бандл в момент
   сборки, поэтому одна сборка показывает либо гостевую половину, либо владельческую, но не обе.
2. **Адрес API вшивается при сборке.** `EXPO_PUBLIC_API_BASE_URL` тоже подставляется в бандл, а
   публичный адрес известен только после деплоя — замкнутый круг.
3. **Хранилище живёт в памяти процесса.** `back/002` не сделана, поэтому после каждого перезапуска
   контейнера онбординг не пройден, и гостевой сценарий начинается с `CALENDAR_NOT_CONFIGURED`
   (проверено в `usecases/owner.ts`). По ссылке это выглядит как неработающее приложение.

## Цель

По одной публичной ссылке открывается работающее приложение MiniCal: интерфейс и API отвечают
с одного порта, образ собирается из репозитория одной командой, контейнер стартует без ручных
действий и слушает порт из `PORT`.

## Зависимости

- [`back/001`](../../back/001-api-skeleton/) — API и чтение `PORT` (завершена).
- [`front/guest/002`](../../front/guest/002-guest-screens/), [`front/owner/001`](../../front/owner/001-owner-screens/) — экраны обеих половин (завершены).
- [`process/003`](../../process/003-docs-commands-rework/) — слой команд: сборка и запуск образа описываются целями `Makefile` (завершена).
- [`back/002`](../../back/002-database-persistence/) — **не является зависимостью**. Решение владельца
  2026-08-18: деплой выполняется раньше персистентности, обоснование — в разделе «Принятые решения».

## Пользовательские сценарии

1. **Автопроверка платформы.** Собирает образ по `Dockerfile` из корня репозитория, запускает
   контейнер, передав свой `PORT`, и обращается к этому порту. Получает ответ, а не отказ.
2. **Проверяющий человек.** Открывает публичную ссылку, видит гостевой экран приложения. Переходит
   на `/admin`, проходит онбординг и заводит тип встречи. Возвращается на корень и бронирует слот —
   видит сквозной сценарий целиком, без установки чего-либо.
3. **Разработчик.** Собирает и запускает образ локально одной целью `make`, без запоминания флагов
   `docker`, и получает то же приложение, что и в облаке.
4. **Новый участник репозитория.** Открывает `README.md` и находит ссылку на опубликованное
   приложение рядом с описанием проекта.

## Функциональные требования

### Образ

- **FR1.** В корне репозитория появляется `Dockerfile`. Расположение продиктовано внешней проверкой:
  она собирает образ из корня контекста. Контекст сборки — корень, потому что репозиторий использует
  npm workspaces и `@minical/api` зависит от `@minical/backend-contract` по `*`: установка возможна
  только из корневого манифеста.
- **FR2.** Запуск контейнера стартует приложение сам, без дополнительных команд. Команда запуска
  вызывает `node` напрямую: `make` — инструмент разработки, в рантайм-образ он не попадает.
- **FR3.** Приложение слушает порт из переменной `PORT` и все сетевые интерфейсы. Значение по
  умолчанию сохраняется для локального запуска.
- **FR4.** Сборка многоэтапная: этап сборки ставит все зависимости и собирает web-бандлы, рантайм-этап
  содержит только то, что нужно для работы — Node, продакшен-зависимости, исходники `apps/api`,
  generated-пакеты и собранные бандлы. Dev-зависимости в рантайм-образ не попадают.
- **FR5.** Появляется `.dockerignore`, исключающий из контекста сборки `node_modules`, `.git`,
  `apps/client/dist`, `apps/client/android`, `apps/client/ios`, `.expo` и локальные каталоги
  харнессов. Без него контекст раздувается и в образ уезжает мусор с машины сборщика.

### Приложение по одному порту

- **FR6.** Тот же процесс, что обслуживает операции контракта, отдаёт статические файлы web-клиента.
  Отдельного веб-сервера в образе нет.
- **FR7.** В образе лежат **два** бандла клиента: гостевой и владельческий. Гостевой доступен по
  корню (`/`), владельческий — по префиксу (`/admin`). Причина — в контексте: режим вшивается при
  сборке, и без двух бандлов по ссылке видна половина приложения. Оба бандла собираются из одного
  кода, разными значениями `EXPO_PUBLIC_APP_MODE`.
- **FR8.** Клиент обращается к API по тому же origin, откуда загружена страница. Для этого вводится
  явное значение-маркер переменной `EXPO_PUBLIC_API_BASE_URL` (например `same-origin`), которое
  `resolveApiBaseUrl()` превращает в пустой `baseUrl`. Именно маркер, а не пустая строка: пустое
  значение неотличимо от «переменную забыли задать», и вместо явной ошибки получился бы молчаливый
  уход на мок разработки. Поведение фиксируется тестом зоны клиента.
- **FR9.** Раздача статики не добавляет записей в реестр `ROUTES` и не меняет контракт: это
  инфраструктурный маршрут, а не операция API. Существующее поведение «запрос вне контракта →
  `404 NOT_FOUND` в JSON» сохраняется — правило «любой неизвестный адрес отдаёт главную страницу»
  не вводится (навигация клиента не использует адресную строку, необходимости нет).

### Первое впечатление и эксплуатация

- **FR10.** Появляется флаг окружения (например `SEED_DEMO`), при котором API создаёт на старте
  демонстрационные данные: настроенный календарь и типы встреч. По умолчанию флаг выключен —
  на пустом старте поведение не меняется. Назначение флага — чтобы публичная ссылка не встречала
  посетителя состоянием «календарь не настроен» до того, как кто-то пройдёт онбординг.
- **FR11.** Публичный адрес приложения задаётся на деплое переменной `PUBLIC_WEB_URL`: backend
  сообщает её гостю в поле `publicUrl` ответов настроек. Без неё гость получит `localhost:8081`.
- **FR12.** Команды сборки и запуска образа определяются целями `Makefile` — по контракту размещения
  ([`docs/sources-of-truth.md`](../../../docs/sources-of-truth.md)) строка команды живёт только там.
  В документации сырых вызовов `docker` не появляется: это проверяет гейт `make lint-docs`.
- **FR13.** Приложение публикуется на внешней платформе, публичная ссылка добавляется в
  корневой `README.md`. Ссылка проверена вручную по сценарию 2.
- **FR14.** Эксплуатация образа и деплоя описывается в [`infra/README.md`](../../../infra/README.md):
  переменные окружения, локальный запуск, порядок публикации. Корневой `README.md` получает только
  ссылку на приложение и отсылку к зоне.

## Нефункциональные требования

- **NFR1.** Существующие гейты остаются зелёными: `make gates` целиком, включая контрактный гейт,
  тест «вне контракта → 404» и `lint-docs`.
- **NFR2.** Новых рантайм-зависимостей не добавляется: раздача статики выполняется средствами уже
  установленного Express.
- **NFR3.** `.github/workflows/hexlet-check.yml` и `.github/workflows/README.md` не изменяются.
- **NFR4.** Секретов в образе и в репозитории нет. Всё, что зависит от среды, приходит переменными
  окружения на запуске.
- **NFR5.** Сборка образа воспроизводима из чистого клона: зависимости ставятся по `package-lock.json`,
  результат не зависит от состояния машины сборщика.
- **NFR6.** Схема БД, контракт (`*.tsp`) и generated-каталоги не затрагиваются.
- **NFR7.** Время сборки образа остаётся практичным для ручного прогона. Два бандла клиента удваивают
  этап сборки — если это окажется неприемлемо долго, компромисс фиксируется в ADR, а не подразумевается.

## API impact

`NONE`

Контракт не меняется: операций не добавляется и не удаляется, `packages/contracts/src/**/*.tsp`
не трогается. Раздача статических файлов появляется как инфраструктурный маршрут вне реестра
операций; контрактный гейт и тест покрытия сверяют реестр `ROUTES` с контрактом и её не видят.

## Принятые решения и рассмотренные варианты

Решения приняты владельцем 2026-08-18 в обсуждении до постановки. Записаны здесь, чтобы ADR
не пересматривал их заново, а занимался тем, как их выполнить.

### Р-brief-1. По ссылке открывается приложение, а не JSON

| Вариант | Почему отвергнут или принят |
|---|---|
| Только API в образе | Формально удовлетворяет проверке: робот стучится в порт и получает ответ. Отвергнут: человек по ссылке видит `{"status":"ok"}` и делает вывод, что приложения нет. Смысл публикации теряется |
| API плюс гостевой бандл | Показывает приложение, но половину: настроить календарь невозможно, а на пустом хранилище гостевой сценарий упирается в `CALENDAR_NOT_CONFIGURED` |
| **API плюс оба бандла: гость на `/`, владелец на `/admin`** | **Принят.** Показывает сценарий целиком: посетитель настраивает календарь как владелец и бронирует как гость. Auth в MVP нет, и для учебной среды это штатно (правило 9 корневого `AGENTS.md`) |

### Р-brief-2. Клиент ходит в API по тому же origin

Проверено по коду собранного SDK: `getUrl` собирает адрес как `(baseUrl ?? '') + path`, где `path`
всегда начинается со слэша.

| Вариант | Почему отвергнут или принят |
|---|---|
| Вшить публичный адрес при сборке образа | Замкнутый круг: адрес известен только после деплоя. Образ становится привязан к платформе и домену — смена адреса требует пересборки |
| `baseUrl = '/'` | Ломается: получается `//health`, а это протокол-относительный адрес — браузер прочитает `health` как имя хоста |
| **`baseUrl = ''` через маркер `same-origin`** | **Принят.** Запрос уходит туда же, откуда загружена страница. Адрес при сборке не нужен вообще: один образ работает на любой платформе и при смене домена. Межсайтовых запросов не возникает, CORS не участвует |

### Р-brief-3. Деплой раньше персистентности

`back/002` (схема БД, миграции, exclusion constraint) не блокирует эту задачу и делается после неё.
Обоснование: с внешней базой задача про образ **растёт** — появляются managed-БД у провайдера,
строка подключения, прогон миграций и обработка неготовности базы. Требование платформы закрывается
раньше, а переезд на базу потом не переписывает образ: меняются переменные окружения и добавляется
шаг миграций. Цена решения названа явно: до `back/002` данные не переживают перезапуск контейнера,
и публичная ссылка после каждого рестарта показывает демонстрационное состояние (FR10), а не то,
что настроил предыдущий посетитель.

### Р-brief-4. `Dockerfile` лежит в корне вопреки контракту размещения

Контракт размещения относит инфраструктуру в `infra/`, но внешняя проверка собирает образ из корня
репозитория. Внешнее требование сильнее внутреннего соглашения; расхождение фиксируется явно —
в `infra/README.md` и, если ADR сочтёт нужным, строкой в самом контракте размещения. Молчаливого
исключения быть не должно.

### Открыто для ADR

1. Базовый образ и версия Node: сборки у нас нет, контейнер исполняет TypeScript-исходники напрямую
   (strip-types), значит нужен Node не ниже заявленного в `.nvmrc`.
2. Способ раздачи двух бандлов и порядок middleware: статика не должна перехватывать пути операций
   контракта и не должна ломать `404` вне контракта.
3. Где живёт демо-сид (FR10) — отдельный модуль зоны `apps/api` или часть bootstrap — и что именно
   он создаёт.
4. Платформа публикации: Render как основной вариант, Railway как запасной; критерий переключения.
5. Что произойдёт с образом при переходе на `back/002` — какие переменные и шаги добавятся, чтобы
   переезд не оказался переписыванием.

## Acceptance criteria

- **AC1.** `docker build` из корня репозитория завершается успешно на чистом клоне.
- **AC2.** `docker run -e PORT=<произвольный> -p <порт>` поднимает приложение; запрос `/health`
  на этом порту отвечает `{"status":"ok"}`. Приложение стартует без ручных действий внутри контейнера.
- **AC3.** Запрос корня (`/`) отдаёт HTML гостевого клиента, запрос `/admin` — HTML владельческого.
- **AC4.** В собранных бандлах нет адреса разработки: `localhost:4010`, `localhost:3001` и `10.0.2.2`
  в них не встречаются. Запросы клиента в браузере уходят на тот же origin.
- **AC5.** Запрос по несуществующему адресу отдаёт `404` с JSON-телом ошибки — существующее
  поведение и покрывающий его тест не сломаны.
- **AC6.** `make gates` зелёный целиком; CI на PR зелёный.
- **AC7.** В `Makefile` есть цели сборки и запуска образа; `make help` их показывает; в документации
  нет сырых вызовов `docker` (`make lint-docs` зелёный).
- **AC8.** Приложение опубликовано, ссылка открывается, сценарий 2 пройден вручную и зафиксирован
  в `result.md`: онбординг на `/admin`, бронирование на `/`.
- **AC9.** Ссылка на опубликованное приложение присутствует в корневом `README.md`.
- **AC10.** С выключенным `SEED_DEMO` поведение старта не меняется: приложение поднимается с пустым
  хранилищем, как сейчас.
- **AC11.** Рантайм-слой образа не содержит dev-зависимостей и каталогов, исключённых `.dockerignore`.
- **AC12.** Эксплуатация описана в `infra/README.md`: переменные `PORT`, `PUBLIC_WEB_URL`,
  `SEED_DEMO`, локальный запуск образа, порядок публикации.

## Non-goals

- Персистентность (`back/002`): схема, миграции и exclusion constraint делаются отдельной задачей
  после этой.
- Сборка Android APK в контейнере (`infra/002`) — другое применение Docker, к публикации сервера
  отношения не имеет.
- Мобильная публикация: раздача APK и переключение его адреса на публичный сервер. После деплоя
  в `apps/client/README.md` добавляется только команда сборки с публичным адресом.
- Введение auth или ограничение доступа к `/admin`. Admin без auth допустим только для локальной
  учебной среды (правило 9), и публикация этого не меняет — задача не вводит защиту, но и не делает
  вид, что она есть.
- Публикация образа в реестр (GHCR, Docker Hub) и деплой из CI. Платформа собирает образ сама.
- Оптимизация размера образа сверх отказа от dev-зависимостей.
- HTTPS, домены и сертификаты — их предоставляет платформа публикации.
