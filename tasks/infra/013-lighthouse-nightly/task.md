# infra/013 — Ночной аудит Lighthouse: запуск по расписанию и вручную, отчёт в прогоне

## Контекст и цель

Внешнее требование учебной платформы (issue #14): показать в проекте регулярную задачу, которая
идёт по расписанию и запускается вручную. Наполнение задано там же — ночной прогон Lighthouse,
отчёт которого команда смотрит утром и решает по нему, какие правки нужны.

Сейчас в `.github/workflows/` четыре файла и ни одного триггера `schedule` или
`workflow_dispatch`: `ci.yml` (обязательные проверки на PR и push), `opencode.yml` (агент по
комментарию и авто-ревью PR), `release-please.yml` (release-PR) и `hexlet-check.yml` — внешний
генерируемый чек платформы, который зона не редактирует. Lighthouse не настроен вовсе: ни
конфига, ни зависимости, ни цели в Makefile.

Три обстоятельства репозитория определяют решение:

- **клиент — SPA на Expo Web.** `expo export --platform web` собирает два бандла, Express из
  `apps/api` раздаёт их статикой: гостевой с `/`, владельческий с `/admin`. Переходы между
  экранами живут в React Navigation внутри загруженного бандла, собственных URL у внутренних
  экранов в вебе нет — точек аудита ровно две, и расширять список некуда.
- **задеплоенный контур недоступен.** `infra/009` опубликовал приложение на DockHost, но на
  счету провайдера кончились средства. Целиться в публичную ссылку нельзя: прогон будет либо
  падать, либо мерить холодный старт усыплённого контейнера.
- **полный контур поднимается одной целью.** `up-app` в `infra/Makefile` собирает образ
  (внутри — оба `expo export`) и поднимает postgres с api, дожидаясь healthcheck через `--wait`;
  у `api` healthcheck реальный, запросом к `/health`. Джоба `compose` в `ci.yml` уже ходит по
  цепочке `config` → подъём → работа → `reset`, и эта цепочка проверена в CI.

Трек lite: HTTP-контракт и схема БД не затронуты, работа целиком в зоне `infra/` (CI
configuration принадлежит ей), новой зависимости в `package.json` не появляется — `@lhci/cli`
вызывается через `npx` с прибитой версией, — работы меньше дня. Все пять критериев
`flows/lite.md` отвечены «нет».

Цель: ночью и по кнопке прогоняется Lighthouse по обеим точкам входа, а утром результат виден
на странице прогона без скачивания файлов.

## Решение

### Цель аудита — контур, поднятый в самом прогоне

Локальная сборка вместо публичной ссылки — вынужденный, но не худший выбор. Плумбинга она не
требует ни строчки нового: `make -C infra up-app` уже делает всё, что нужно, а `--wait` снимает
вопрос ожидания готовности.

Адрес остаётся параметром, а не константой в конфиге:

```js
// lighthouserc.js
const base = (process.env.LHCI_BASE_URL ?? 'http://localhost:3001').replace(/\/+$/, '');

module.exports = {
  ci: {
    collect: {
      url: [base, `${base}/admin/`],
      numberOfRuns: 3,
    },
    upload: {
      target: 'filesystem',
      outputDir: '.lighthouseci',
    },
  },
};
```

Завершающий слэш у `/admin/` обязателен и проверен: `express.static` смонтирован на префикс
`/admin`, поэтому запрос без слэша даёт штатный 301 от `serve-static` — это зафиксировано
отдельным тестом в `apps/api/src/static.test.ts`. Без слэша Lighthouse мерил бы редирект и
отдельно жаловался бы на него в разделе производительности. Поведение одинаково локально и на
деплое: это свойство раздачи, а не платформы.

`numberOfRuns: 3` — дефолт LHCI, оставлен в конфиге явно: на shared-раннере Lighthouse шумит,
и медиана представительного прогона — единственное, чему можно верить. Величина не из тех,
которые стоит уменьшать не глядя, поэтому она видна в конфиге, а не подразумевается.

Пресет не задаётся: дефолт Lighthouse — mobile с эмуляцией медленной сети и слабого CPU. Для
MiniCal, который задуман мобильным, это ближе к правде, чем desktop-пресет.

### `SEED_DEMO=true` обязателен

Без демо-данных `/calendar` отвечает `400 CALENDAR_NOT_CONFIGURED` (зафиксировано в результате
`infra/009`), и Lighthouse померил бы гостевой экран с ошибкой вместо календаря. Переменная уже
проброшена в `infra/compose.yml`, задаётся окружением шага.

### Ассертов в первой версии нет

SPA отдаёт браузеру почти пустой HTML и мегабайты JavaScript; до первого осмысленного пикселя
проходят три шага подряд — скачать бандл, выполнить его, сходить в API. Поэтому Performance у
Expo Web заведомо далёк от 90, и это свойство схемы, а не дефект кода. Включённый сразу
`lighthouse:recommended` красил бы каждый ночной прогон в красный, и через неделю на него
перестали бы смотреть.

Порядок обратный: сначала неделя информационных прогонов и базовая линия с её разбросом, затем
отдельной задачей — пороги чуть ниже фактических, ловящие деградацию, а не абсолютный уровень.

Часть находок первого прогона предсказуема уже из конфигурации клиента: в `apps/client/app.json`
секция `web` содержит только `favicon`, атрибут `lang` у документа не задаётся нигде, а
`robots.txt` и meta-description в экспорте отсутствуют. Это замечания accessibility и SEO, а не
производительности, и чинятся они дешевле всего — но чинятся отдельной задачей, эта только
показывает.

### Отчёт — два слоя, оба внутри GitHub

`$GITHUB_STEP_SUMMARY` получает markdown-таблицу «URL × пять категорий»: утром достаточно
открыть страницу прогона, скачивать нечего. Артефакт с `.lighthouseci/` целиком, включая
HTML-отчёты, живёт 30 дней — для разбора, когда цифра просела.

`upload.target: temporary-public-storage` из документации LHCI отвергнут сознательно: он
публикует отчёт о нашем приложении в публичное хранилище Google. Код и так открыт, но публикация
наружу выбирается явно, а не достаётся по умолчанию — то же соображение, что привело к
`share: false` в `infra/010`.

Таблица собирается `jq` из `manifest.json`, который LHCI пишет сам: там уже лежат url, оценки по
категориям и путь к HTML. Отдельного скрипта задача не заводит.

### Ни одного нового стороннего action

Workflow использует только `actions/checkout`, `actions/setup-node` и `actions/upload-artifact` —
first-party, первые два уже стоят в `ci.yml`. `treosh/lighthouse-ci-action` не берём: `infra/011`
заявлена ровно про то, что неприпиненный сторонний action в CI — проблема, и добавлять сюда
второй значило бы идти против неё. `npx --yes @lhci/cli@0.15.1` даёт ту же работу с явной
версией в строке команды.

Цена решения честная: инструмента нет в lockfile, Dependabot его не обновляет, и пакет качается
каждую ночь заново. Для информационного ночного прогона это приемлемо; альтернатива — devDependency
в корневом `package.json` — делает задачу full по критерию «новая зависимость».

### Команда живёт в `infra/Makefile`

```makefile
LHCI_VERSION ?= 0.15.1

lighthouse: ## Прогнать Lighthouse по поднятому контуру, отчёт в .lighthouseci/
	cd $(REPO_ROOT) && npx --yes @lhci/cli@$(LHCI_VERSION) autorun

lighthouse-report: ## Markdown-сводка последнего прогона в stdout
	@if [ ! -f $(REPO_ROOT)/.lighthouseci/manifest.json ]; then \
	  echo "Отчёт не сформирован: прогон не дошёл до записи manifest.json"; \
	else \
	  echo "| URL | Perf | A11y | BP | SEO |"; \
	  echo "|---|---|---|---|---|"; \
	  jq -r '.[] | select(.isRepresentativeRun) | "| \(.url) | \(.summary.performance*100|round) | \(.summary.accessibility*100|round) | \(.summary["best-practices"]*100|round) | \(.summary.seo*100|round) |"' $(REPO_ROOT)/.lighthouseci/manifest.json; \
	fi
```

Переход в корень обязателен, и это выяснилось на реализации: `make -C infra` уходит в каталог
зоны, а `lhci` ищет конфигурацию только в текущем каталоге и вверх по дереву не поднимается —
из зоны `healthcheck` отвечает «Configuration file not found». Без перехода прогон остался бы
без конфигурации, свалился на дефолтные ассерты `lighthouse:recommended` и положил бы отчёт
в `infra/.lighthouseci/`, мимо корневой строки `.gitignore` и мимо пути артефакта в workflow.
`$(REPO_ROOT)` — уже принятая в этом файле идиома, тем же способом устроены `db-migrate`,
`db-test` и `image-build`.

Корневой Makefile получает делегаты обеих целей — строка команды остаётся одна, в зоне.

В `make gates` цель **не входит**: это сетевой прогон на несколько минут, требующий поднятого
контура, и на каждом PR ему делать нечего. Зона своих гейтов по-прежнему не имеет.

### Workflow

```yaml
name: lighthouse

on:
  schedule:
    - cron: '0 2 * * *'   # 05:00 MSK — отчёт готов к началу дня
  workflow_dispatch:
    inputs:
      base_url:
        description: 'Адрес вместо настроенного (пусто — как настроено)'
        required: false
        default: ''

concurrency:
  group: lighthouse
  cancel-in-progress: false

permissions:
  contents: read

jobs:
  audit:
    runs-on: ubuntu-latest
    timeout-minutes: 20
    env:
      LHCI_BASE_URL: ${{ github.event.inputs.base_url || vars.LHCI_BASE_URL || 'http://localhost:3001' }}
      LOCAL_TARGET: ${{ startsWith(github.event.inputs.base_url || vars.LHCI_BASE_URL || 'http://localhost:3001', 'http://localhost') }}
    steps:
      - uses: actions/checkout@v7
        with:
          persist-credentials: false
      - uses: actions/setup-node@v7
        with:
          node-version-file: .nvmrc

      - if: env.LOCAL_TARGET == 'true'
        run: make -C infra config
      - if: env.LOCAL_TARGET == 'true'
        run: make -C infra up-app
        env:
          SEED_DEMO: 'true'

      - name: Убедиться, что контур раздаёт web
        if: env.LOCAL_TARGET == 'true'
        run: curl -sSf -o /dev/null "$LHCI_BASE_URL"

      - name: Разбудить внешний адрес
        if: env.LOCAL_TARGET != 'true'
        run: curl -sSf -o /dev/null --retry 5 --retry-all-errors --retry-delay 10 --max-time 180 "$LHCI_BASE_URL"

      - run: make lighthouse
      - if: always()
        run: |
          echo "Аудит: $LHCI_BASE_URL" >> "$GITHUB_STEP_SUMMARY"
          make lighthouse-report >> "$GITHUB_STEP_SUMMARY"
      - if: always()
        uses: actions/upload-artifact@v7
        with:
          name: lighthouse-${{ github.run_id }}
          path: .lighthouseci/
          retention-days: 30
          # .lighthouseci — скрытый каталог, а upload-artifact такие по умолчанию пропускает:
          # без этого шаг зеленеет с предупреждением, а артефакт не создаётся вовсе.
          include-hidden-files: true
          # Тот же молчаливо-зелёный дефолт (warn) и скрыл дефект: пустой артефакт обязан быть
          # отказом, иначе следующая смена пути вывода снова пройдёт незамеченной.
          if-no-files-found: error
      - if: always() && env.LOCAL_TARGET == 'true'
        run: make -C infra reset
```

Отличия от типового примера и их причины:

1. **`timeout-minutes: 20`** — против 10 у джобы `compose` в `ci.yml`: та образ приложения не
   собирает, а здесь внутрь подъёма попадают два `expo export`. Значение уточняется по факту
   первого прогона.
2. **`concurrency` без отмены** — ручной запуск поверх ночного не должен убивать уже идущий
   аудит; параллельные прогоны на одном раннере испортили бы метрики обоим.
3. **`permissions: contents: read`** — job'у нужен только чекаут. Артефакт и сводка прогона прав
   на запись не требуют.
4. **`if: always()` на сводке, артефакте и `reset`** — упавший аудит обязан оставить отчёт и
   погасить контур; без этого раннер оставался бы с поднятыми контейнерами, а причина падения
   осталась бы только в логе.
5. **`workflow_dispatch` со входом `base_url`** — ручной запуск кнопкой Run workflow, второй
   пункт issue, плюс разовый прогон против произвольного адреса без правки файла.
6. **Шаги контура условны** — при внешнем адресе подъём и уборка пропускаются, иначе прогон
   тратил бы минуты на сборку образа, который не понадобится. Зеркально: прогрев `curl` идёт
   только для внешнего адреса.
7. **Проверка, что контур раздаёт web** — добавлена по итогам первой попытки прогона.
   `server.ts` при отсутствующих бандлах штатно поднимается в режиме API-only, а healthcheck
   контейнера смотрит на `/health` и остаётся зелёным. То есть `up-app --wait` может завершиться
   успехом, а по `/` при этом будет 404, и Lighthouse свалится невнятным `Status code: 404`
   вместо понятного «бандлов нет». Один `curl -sSf` превращает это в явный отказ на своём шаге.
8. **Выражение адреса продублировано в `LOCAL_TARGET`** — `env` не может ссылаться на соседний
   ключ того же `env`. Дублирование неприятное, но альтернатива — вычислять признак отдельным
   шагом через `$GITHUB_OUTPUT`, что длиннее и не нагляднее.

### Переключение на реальный деплой

Первая редакция решения обещала «одну переменную окружения». Проверка это опровергла: цель
аудита определяется не только адресом, но и тем, поднимать ли контур, а ночной прогон идёт по
cron, где входы `workflow_dispatch` недоступны в принципе. Поэтому переключатель вынесен из файла
в переменную репозитория, а шаги контура стали условными.

Адрес берётся тремя уровнями, каждый следующий — запасной:

1. вход `base_url` ручного запуска — разовый прогон против произвольного адреса;
2. переменная репозитория `vars.LHCI_BASE_URL` — то, что действует для ночных прогонов;
3. `http://localhost:3001` — контур, поднятый в самом прогоне.

Признак «цель локальная» вычисляется из итогового адреса через `startsWith`, а не из пустоты
входа: иначе при заданной переменной ручным запуском нельзя было бы вернуться к контуру.

Механизм для проекта новый: переменных у репозитория нет ни одной (`gh variable list` пуст),
контекст `vars` не используется ни в одном workflow. Доступность `vars` в job-level `env:` и
`env` в `if:` шага сверена по документации contexts.

Включение на деплое тогда не требует ни правки файлов, ни повторного согласования гейта:

```bash
gh variable set LHCI_BASE_URL --body 'https://6b1y-3d3v-dk6o.gw-1a.dockhost.net'
gh workflow run lighthouse.yml   # проверить сразу, не дожидаясь ночи
```

Откат — `gh variable delete LHCI_BASE_URL`: следующий прогон снова поднимет контур.

Две проверки состояния деплоя обязательны до переключения, и к workflow они отношения не имеют:

- **Ветка сборки в DockHost.** Платформа пересобирает образ на каждый push в ветку, указанную
  при подключении репозитория. Результат `infra/009` оставил действие незакрытым: после merge
  ветку деплоя нужно переключить, «сейчас собирается из ветки задачи». Пока это не сделано, на
  публичном адресе живёт код старой ветки, и аудит мерил бы не то, что в `master`.
- **Инстанс отвечает.** На 2026-08-30 `/`, `/admin` и `/admin/` отдают `503` за 0.2–0.35 с —
  отвечает шлюз, контейнер не поднят.

Отдельно про сами цифры: **метрики контура и деплоя несравнимы**. Localhost — это отсутствие
сети, TLS и расстояния до сервера; DockHost — реальная доставка. Переключение обнуляет базовую
линию, а вся стратегия с порогами построена на её накоплении. Если оплата вернётся в ближайшие
дни, копить локальную линию незачем — дешевле переключиться сразу и вести отсчёт с неё.

Попутная находка, прямого отношения к задаче не имеющая: инструкция про ветку деплоя в
`infra/README.md` и описание триггеров `ci.yml` в `docs/architecture.md` называют ветку `main`,
тогда как дефолтная ветка репозитория — `master`, и `ci.yml` триггерится по `master`. Тот, кто
пойдёт переключать DockHost по README, будет искать несуществующую ветку. Правка на строку в
двух файлах, но она за границами этой задачи — выносится решением владельца.

### Что про само расписание нужно знать

Cron в GitHub Actions не точен: запуск сдвигается на 15–30 минут в пиковые часы, а после 60 дней
без активности в репозитории расписание отключается автоматически. Обещать «ровно в 02:00 каждую
ночь» нельзя.

Отдельная оговорка про смысл: раз аудит собирает `master`, ночной прогон при отсутствии коммитов
меряет один и тот же код повторно. Это не пустая работа — так набирается разброс метрики, без
которого пороги не выставить, — но основную пользу даст либо активная разработка, либо второй
триггер на push в `master`. Расписание оставлено, потому что оно и есть предмет issue.

Отдельная оговорка про цифры: localhost — это отсутствие реальной сети, TLS и расстояния до
сервера, поэтому абсолютные значения будут оптимистичнее того, что видит живой пользователь.
Для отслеживания регрессий важна стабильность условий от ночи к ночи, а не близость к реальности.

### Отвергнутые альтернативы

**Аудит публичной ссылки DockHost** — исходный замысел, снят обстоятельствами: денег на счету
провайдера нет, инстанс отдаёт `503`. Порядок возврата — в разделе «Переключение на реальный
деплой», это переменная репозитория плюс две проверки состояния деплоя.

**Сборка web-бандла в раннере без Docker** (`npm ci` + `expo export` + запуск api) — дублирует
то, что уже умеет `up-app`, и разъезжается с ним при первой же правке Dockerfile.

**Прогон Lighthouse силами агента OpenCode по расписанию** — issue формулирует задачу как
«ночью агент выполняет проверку», но гонять детерминированный аудит через LLM значит платить
токенами за `npx lhci autorun` и получать нестабильный результат.

### Что осталось за рамками

- **Пороги и ассерты** — отдельной задачей после накопления базовой линии.
- **Агент, заводящий issue по итогам отчёта** — последний пункт issue #14. Второй job после
  `audit`, который отдаёт opencode JSON-отчёт и просит завести или обновить issue со списком
  регрессий; требует `issues: write`, обязательного `prompt` и упирается в те же вопросы
  триггера и версии action, что закрывают `infra/011` и `infra/012`. Осмысленно делать, когда
  станет понятно, о чём вообще заводить issue.

## Результат и проверки

Реализованы P01–P04. P05 и P06 закрываются после merge: по документации events и `schedule`,
и `workflow_dispatch` срабатывают, только если файл workflow лежит в дефолтной ветке, — до
вливания прогона не существует в принципе. Тот же порядок был у комментарийного триггера
в `infra/010`.

### Что появилось

- `lighthouserc.js` в корне — две точки входа из `LHCI_BASE_URL`, вывод в `.lighthouseci/`.
- `.github/workflows/lighthouse.yml` — cron `0 2 * * *`, ручной запуск со входом `base_url`,
  условные шаги контура, проверка раздачи web, прогрев внешнего адреса, сводка в прогоне,
  артефакт на 30 дней.
- `infra/Makefile` — `LHCI_VERSION`, цели `lighthouse` и `lighthouse-report`; корневой Makefile —
  делегаты. В `gates` цели не входят.
- `.gitignore` — `.lighthouseci/`; `docs/architecture.md` — строка про workflow; `infra/README.md`
  — раздел «Ночной аудит Lighthouse» с порядком переключения на опубликованный инстанс.

Версии actions: `checkout@v7` и `setup-node@v7` — как в `ci.yml`, `upload-artifact@v7` — текущий
мажорный релиз на 2026-08-30.

### Два дефекта, найденные на реализации

**Конфигурация не находилась из зоны.** `make -C infra` уходит в каталог зоны, а `lhci` ищет
конфигурацию только в текущем каталоге: `healthcheck` из `infra/` отвечает «Configuration file
not found», из корня — «Configuration file found». По букве согласованного решения прогон остался
бы без конфигурации, свалился на дефолтные ассерты `lighthouse:recommended` и положил отчёт
в `infra/.lighthouseci/` — мимо корневой строки `.gitignore` и мимо пути артефакта в workflow.
Исправлено переходом в `$(REPO_ROOT)`; гейт `setup` возвращался в черновик, блок «Решения»
приведён к фактическому.

**Зелёный контур без единого байта web.** Первая попытка прогона выглядела успешной и не
проверяла ничего: `/health` отвечал 200, а `/`, `/admin` и `/admin/` — 404. Причина в том, что
`server.ts` при отсутствующих бандлах штатно поднимается в режиме API-only, а healthcheck
контейнера смотрит только на `/health`. Значит `up-app --wait` способен завершиться успехом,
а Lighthouse после него падает невнятным `Runtime error ... (Status code: 404)`. Добавлен
отдельный шаг `curl -sSf` по базовому адресу — отказ становится явным и на своём месте.

### Сквозная проверка плумбинга

Контур на машине разработчика поднять не удалось по причинам, к задаче отношения не имеющим:
`docker buildx` не установлен и сборка образа падает (`fork/exec /usr/bin/unpigz: input/output
error`), а порт 3001 занят вручную запущенным `node apps/api/src/server.ts`. Поэтому цепочка
проверена на реальном экспортированном бандле `apps/client/dist`, разложенном статическим
сервером по `/` и `/admin/`:

| URL | Perf | A11y | BP | SEO |
|---|---|---|---|---|
| `http://localhost:8099/` | 80 | 100 | 96 | 90 |
| `http://localhost:8099/admin/` | 80 | 100 | 96 | 90 |

Подтверждено: конфигурация находится из корня, обе точки входа со слэшем отдают 200 без
редиректа, `manifest.json` пишется в корневой `.lighthouseci/`, `jq`-сводка печатает ровно две
строки — немедианные прогоны отфильтрованы, округление верное.

Чем эти цифры не являются: базовой линией. Раздавал их `python3 -m http.server`, а не Express
с его заголовками кеширования; бандл — общий экспорт, а не пара guest/owner; backend
отсутствовал, поэтому приложение мерилось без данных. Обе строки одинаковы просто потому, что
бандл один и тот же, разложенный дважды.

Отдельно — поправка к собственному прогнозу из постановки. Предполагалось, что первый прогон
даст заметные замечания по accessibility. На этом бандле категория дала 100, то есть прогноз
не подтвердился; где приложение реально слабо, покажет прогон в CI по настоящему контуру.

### Замечания авто-ревью на PR #15

Ревью независимо перепрогнало `make gates`, `scripts/task check` и `lint-docs` и подтвердило
результаты, а также проверило заявление «ассертов нет»: в `autorun` дефолтный пресет
`lighthouse:recommended` не применяется, когда настроен upload-таргет, а он настроен. Три
найденных расхождения приняты и закрыты:

1. **Листинг в «Решении» разошёлся с кодом.** Согласуемая часть называла `upload-artifact@v4`,
   тогда как в файле стоит `@v7`; кроме того, в листинге не хватало шага проверки раздачи web,
   добавленного по ходу реализации. Оба блока приведены к фактическому коду и сверены построчно —
   расхождений ноль.
2. **Сводка падала на отсутствующем манифесте.** Шаг стоит в `always()`, но `jq` на
   несуществующем файле давал вторую ошибку поверх первой — ровно это наблюдалось при неудачной
   попытке локального прогона. Цель `lighthouse-report` теперь проверяет наличие
   `manifest.json` и печатает «Отчёт не сформирован», завершаясь нулём.
3. **Двойной слэш.** `LHCI_BASE_URL` с завершающим слэшем давал `//admin/`. Базовый адрес
   в `lighthouserc.js` срезает хвостовые слэши; проверено на четырёх вариантах входа.

Замечание о хрупкости `startsWith('http://localhost')` принято как верное, но без изменений:
альтернатива с отдельной переменной-признаком громоздче, а цена ошибки — лишний подъём контура.

Риск «LHCI 0.15.1 против Node 26», отмеченный ревью как непроверенный, снят фактом: локальный
сквозной прогон шёл на Node 26.0.0 — той версии, которую задаёт `.nvmrc` и ставит `setup-node`
в раннере.

Процессное возражение — нельзя вливать код с гейтом `setup` в черновике — верно и учтено:
владелец согласовал гейт после закрытия перечисленных расхождений, merge выполнен после
согласования.
