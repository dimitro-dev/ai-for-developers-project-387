# Architecture decision — TASK-INFRA-004

## Контекст

`packages/contracts/generated/openapi.yaml` описывает 8 маршрутов и 11 операций контракта MiniCal, но `apps/api` — пока smoke-сервер на `node:http` с единственным маршрутом `/health`. Клиентская разработка заблокирована готовностью backend, что противоречит цели contract-first из `docs/contract-pipeline.md`: «Frontend Agent может работать по generated SDK и mock API до готовности backend». Пробел зафиксирован в `task-003` как пропущенная проверка P09 и known limitation. Нужно решение о том, чем и как поднять mock-сервер поверх уже сгенерированного OpenAPI.

## Решение

Использовать **Stoplight Prism CLI v5** (`@stoplight/prism-cli`) как корневой `devDependency` и поднимать mock-сервер одной npm-командой из `packages/contracts/generated/openapi.yaml`:

```bash
npm run mock:prism   # prism mock packages/contracts/generated/openapi.yaml -p 4010
```

Детали:

1. **Валидация запросов — поведение Prism по умолчанию.** Prism в mock-режиме валидирует все входящие запросы (body, query, path) против OpenAPI-документа. Невалидный запрос отклоняется 4xx-ответом операции — фактически Prism 5.16.0 возвращает документированный error-ответ (`POST /bookings` → `400 Bad Request`), а не дефолтный mock-ответ `201`. Детализация несоответствия передаётся заголовком `sl-violations` (RFC 7807 problem details body Prism 5.16.0 в mock-режиме не формирует). Этим закрывается требование FR#3 brief («отклонять запрос, не соответствующий контракту»).
   *Наблюдаемый артефакт:* error-схемы контракта требуют `code` из конкретного enum, но Prism генерирует пример `{"code":"string","message":"string"}`, не соответствующий ни одной из них; поэтому в `sl-violations` на 4xx-ответах появляется response-шум (`code must be equal to one of the allowed values: ...`), а тело `Prefer: code=404/409` отдаёт `code: "string"` вместо `EVENT_TYPE_NOT_FOUND`/`ONBOARDING_ALREADY_COMPLETED`. Статус выбирается правильно, форма error-тела — нет. Это ограничение мока, а не провал acceptance criteria (AC#5 требует только статус); возможное решение — явные `examples` в TypeSpec error-моделях, но это изменение контракта и отдельная задача, вне scope этой.
2. **Запрос конкретного не-2xx статуса — штатный механизм Prism `Prefer: code=<status>`.** Для операций с документированными error-ответами (`createPublicBooking` → 400/404/409, `getPublicSlots` → 400/404 и т. д.) клиент выбирает ответ заголовком `Prefer: code=404`, тело берётся из контракта.
3. **Примеры ответов — статические, по умолчанию.** `--dynamic` не включается: статические примеры детерминированы, что удобнее для проверок формы ответов (AC#2/#3) и ручных smoke-запросов.
4. **Порт `4010`** — дефолт Prism; свободен, не конфликтует с `3001` (smoke API) и `8081` (Metro). Фиксируется явным `-p 4010` в npm-скрипте.
5. **Авто-reload.** Prism следит за изменениями документа: при перегенерации `openapi.yaml` сервер перезапускается сам, без ручного рестарта.
6. **Никаких runtime-сервисов.** Мок работает локально поверх `openapi.yaml`, не требует backend, PostgreSQL или Docker, не используется в CI и не подменяет контрактный gate (`tests/contract-validation.test.ts`, `npm run generate:check`).
7. **baseUrl клиента остаётся конфигурацией.** Переключение клиента между моком (`http://localhost:4010`) и реальным API (`http://localhost:3001`) документируется в README через `client.setConfig({ baseUrl })` generated SDK (`@minical/api-client`); клиентских экранов и фактического подключения в scope нет.

## Затронутые компоненты

```text
package.json                     (devDependencies + npm-скрипт mock:prism)
package-lock.json                (зафиксированная версия @stoplight/prism-cli)
README.md                        (секция mock, порт 4010, режим валидации, переключение base URL)
```

Контракт и generated-артефакты не затрагиваются — API impact `NONE`.

## Последствия и компромиссы

Положительные:

- клиентская разработка и QA получают работающий API для 11 операций до готовности backend — без изменений в контракте;
- валидация запросов «из коробки» ловит несоответствия контракту на той же границе, что и будущий backend (generated Zod-схемы), что облегчает согласование транспортной формы;
- мок поднимается из чистого checkout одной командой, без ручных шагов (требование воспроизводимости из brief);
- `Prefer: code=` позволяет проверять и error-пути, которых в реальном in-memory backend ещё нет.

Компромиссы:

- mock-ответы — сгенерированные Prism примеры по схемам, а не реализация бизнес-правил (слоты, конфликты, 14-дневное окно): сценарии, требующие доменной логики, остаются предметом будущего backend и E2E-проверок;
- версия `@stoplight/prism-cli` требует Node `>=24.18.0` (проект использует Node 26 — совместимо; потолок `engines` не поднимается);
- мок не хранит состояние между запросами — для сценариев, зависящих от последовательности (onboarding → слоты), он даёт лишь транспортную форму, а не последовательные переходы.

## Рассмотренные альтернативы

### Docker-контейнер Prism (образ в `infra/`, `docker compose`)

Отклонено: противоречит текущему этапу проекта (Docker-контур вынесен в отдельную задачу `task-infra-001`; на этапе `task-000` принято «Docker для текущего этапа не требуется»). CLI-зависимость легче: не требует Docker Engine для локальной разработки клиента. Docker-обёртка остаётся возможным надстроечным шагом в будущем.

### Ручной mock на `node:http` (по примеру `apps/api/src/server.ts`)

Отклонено: дублирует контракт вручную (маршруты, схемы, примеры) — создаёт второй источник истины и риск расхождения с `openapi.yaml`, как это уже случалось с `server.ts` (task-006). Prism сам читает `openapi.yaml`, исключая drift. Дополнительно Prism бесплатно даёт request-валидацию и выбор статус-кода.

### Mockoon или другой GUI-инструмент

Отклонено: интерактивный GUI плохо ложится на воспроизводимую одну команду из чистого checkout и на headless-прогоны; Prism — npm-зависимость, управляется скриптом.

### Prism как runtime-зависимость (`dependencies`) вместо `devDependencies`

Отклонено: мок используется только локально в разработке, в CI не применяется и в production не попадает — `devDependencies` корректнее.

## Совместимость и миграция

Версия фиксируется в `package-lock.json` через явное `devDependency` (`^5.16.0` на момент реализации). Runtime-поведение существующих команд не меняется; для работы мока нужен только чистый `npm ci`. Миграций данных нет, контракт и generated-артефакты не меняются. При появлении реального backend мок остаётся как временный инструмент разработки и не конфликтует с ним (разные порты).
