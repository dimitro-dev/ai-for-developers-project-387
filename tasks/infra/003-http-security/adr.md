# Architecture decision — TASK-INFRA-003

## Контекст

Backend HTTP-сервер должен быть доступен из браузера (React Web) и защищён минимальными
security-заголовками: `brief.md` (`status: согласовано`) фиксирует CORS с `Access-Control-Allow-Origin: *`,
два заголовка (`X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`) и лимит тела 64KB с ответом
`413`.

**Первая редакция этого ADR писалась до появления сервера** и поэтому формулировала решения в
условном наклонении («для Express — пакет `cors`, для Fastify — `@fastify/cors`»), а выбор пакетов
прямо откладывала. Основание исчезло: `task-back-001` реализована (`497dfc2`), фреймворк —
Express 5.2.1, точка вставки middleware существует физически.

Фактическое состояние цепочки (`apps/api/src/app.ts`), проверено по коду:

```text
express.json()            // дефолты, в т. ч. лимит 100kb — «отсутствие решения о лимите» (back-001, Р8)
цикл монтирования по ROUTES
notFoundHandler           // 404 NOT_FOUND на неизвестный URL и метод
errorMiddleware           // DomainError → таблица ERROR_STATUS; entity.parse.failed → 400; остальное → 500
```

`task-back-001` (Р8, «Совместимость и миграция») зарезервировала за этой задачей ровно одну точку:
начало `createApp(deps)`, до цикла монтирования.

Факты, проверенные в этой рабочей копии прогоном на установленных `express@5.2.1` /
`body-parser@2.3.0` / `raw-body@3.0.2`, а не по документации:

| Факт | Проверка | Результат |
|---|---|---|
| Ошибка превышения лимита | `express.json({ limit: '64kb' })`, тело 70KB | `PayloadTooLargeError` (не `SyntaxError`), `type: 'entity.too.large'`, `status`/`statusCode` `413`, `limit: 65536`, `length: 70010`, `message: 'request entity too large'` |
| Ответ доходит до клиента | тот же прогон | error-middleware вызван, ответ отдан; соединение не рвётся |
| Область действия лимита | тело 70KB с `Content-Type: text/plain` | `express.json()` тело **не читает**, ошибки нет, обработчик получает `{}` — лимит действует только на `application/json` |
| Тело без `Content-Length` | 70KB чанкованным стримом, `Content-Type: application/json` | `413` — `raw-body` считает фактически принятые байты, а не заголовок |
| Встроенный OPTIONS Express 5 | `OPTIONS` на смонтированный маршрут без CORS-middleware | `200` + `Allow: POST`, то есть **не** `204`, которого требует AC2 |
| `cors` / `@types/cors` | `ls node_modules` | не установлены; добавление — новая зависимость, а не подключение имеющейся |

## Решение

Новых npm-зависимостей у задачи нет: `apps/api/package.json` не меняется. Весь код — один новый
модуль `apps/api/src/http/security.ts` (≈25 строк), две строки монтирования в `app.ts` и одна ветка в
`errorMiddleware`.

### Р1. CORS — собственный middleware, без пакета `cors`

`cors@2.8.5` (последняя публикация — 2018) плюс `@types/cors` — две новые зависимости ради трёх
статических заголовков и одной ветки на `OPTIONS`. Из его функциональности при
`Access-Control-Allow-Origin: *` не используется ничего: ни функция-предикат origin, ни `Vary: Origin`
(при статическом `*` он не нужен), ни `credentials`, ни `exposedHeaders`, ни `maxAge`.

Решение симметрично тому, что brief уже принял для заголовков: «Helmet full preset» в Non-goals
отклонён по той же причине — нужны два заголовка, а не преset. Прецедент проекта — Р13 `back-001`
(отклонены `supertest`, `luxon`, внешний тест-раннер при том же соотношении «используемая поверхность
/ зависимость»).

Цена решения: корректность preflight-ответа принадлежит нам, а не пакету. Оплачивается тем, что
ответ — три константных заголовка и статус, и тем, что AC1–AC4 покрываются автотестами (Р9), а не
только curl'ом.

### Р2. Один новый модуль `http/security.ts`, два middleware, фиксированный порядок

`http/**` — единственное место, где по Р1 `back-001` живёт transport; CORS и security-заголовки —
transport и есть. Инлайн в `app.ts` отклонён: `createApp` держит роль «единственная точка
монтирования», а не место с логикой.

Экспорты: `securityHeaders` (два заголовка + `next()`), `cors` (ACAO всегда + короткое замыкание
preflight), `BODY_LIMIT_BYTES`.

Порядок в начале `createApp`, до цикла монтирования:

```text
1. securityHeaders                  → nosniff и DENY попадают во все ответы, включая 204, 404, 413, 500
2. cors                             → ACAO во все ответы; OPTIONS отвечает сам
3. express.json({ limit: … })       → тело парсится уже после того, как заголовки выставлены
4. …ROUTES → notFoundHandler → errorMiddleware   (без изменений)
```

Порядок значим в обе стороны: заголовки обязаны стоять до `express.json()`, иначе ответ `413` уйдёт
без CORS-заголовков и браузер не даст клиенту прочитать даже код ошибки; `securityHeaders` стоит до
`cors`, потому что `cors` завершает preflight и `next()` не вызывает.

### Р3. Список методов для CORS выводится из `ROUTES`, а не задаётся константой

`Access-Control-Allow-Methods` собирается как множество `method` из `ROUTES` в верхнем регистре плюс
`OPTIONS`. Сегодня это `GET, POST, PUT, OPTIONS` — ровно то, что перечисляет brief.

Основание: brief требует, чтобы список **соответствовал фактическому набору методов generated
OpenAPI**, и предупреждает, что при добавлении метода конфигурацию придётся пересматривать вручную,
иначе preflight нового метода будет молча отклоняться. Вывод из `ROUTES` снимает ручной шаг:
`routes.contract.test.ts` уже доказывает двустороннее равенство `ROUTES` и `generated/openapi.yaml`
(FR7 `back-001`), поэтому производный список равен методам контракта по построению. Стоимость — две
строки; предупреждение brief про ручной пересмотр становится неактуальным, а не нарушенным.

`HEAD` в список не добавляется: Express обслуживает его автоматически для `GET`-маршрутов, а CORS
относит `GET`/`HEAD`/`POST` к safelisted-методам, которые в `Access-Control-Allow-Methods` перечислять
не требуется.

### Р4. Preflight: любой `OPTIONS` → `204`

Middleware отвечает `204` на **каждый** `OPTIONS`, не проверяя наличие `Access-Control-Request-Method`
— та же семантика, что у пакета `cors` при глобальном монтировании. Это осознанно замещает встроенный
ответ Express 5 (`200` + `Allow`, проверено): AC2 требует `204`.

Заголовки preflight-ответа: `Access-Control-Allow-Origin: *`, `Access-Control-Allow-Methods` (Р3),
`Access-Control-Allow-Headers: Content-Type`, плюс два security-заголовка из `securityHeaders`.
`Access-Control-Max-Age` не ставится — brief его не требует, кеширование preflight в учебном контуре
выигрыша не даёт.

Два следствия принимаются явно:

- `Allow` на `OPTIONS` больше не отдаётся. Согласуется с уже принятым в Р8 `back-001` отказом от
  `405` с `Allow` по той же причине: у ответа нет потребителя.
- `OPTIONS` на неизвестный URL отвечает `204`, а не `404` (`notFoundHandler` до него не доходит).
  Безвредно: настоящий запрос по тому же URL по-прежнему получит `404 NOT_FOUND`.

`Access-Control-Allow-Methods` — общий для приложения, а не для конкретного пути. Так же ведёт себя
`cors`; браузеру этого достаточно, потому что preflight проверяет только вхождение метода в список.

### Р5. Лимит тела — `express.json({ limit: BODY_LIMIT_BYTES })`, 65536

Единственное объявление величины — `export const BODY_LIMIT_BYTES = 64 * 1024;` в `http/security.ts`.
Отдельного guard-middleware нет.

Область действия зафиксирована честно: лимит действует на тела с `Content-Type: application/json` —
единственный тип, который контракт использует в запросах. Тело другого типа `express.json()` не
читает вовсе (проверено), поэтому в память приложения оно не попадает; такой запрос дойдёт до
обработчика с `{}` и получит `400 VALIDATION_ERROR` от Zod, а не `413`. Практическое следствие для
проверки AC3: curl обязан передать `-H 'Content-Type: application/json'`, иначе критерий проверяет не
то, что описан (пункт P06 плана это учитывает).

### Р6. `413` собирается в `errorMiddleware` — новой веткой в `http/errors.ts`

`errorMiddleware` учится распознавать `entity.too.large` и отвечает
`413 {code: 'PAYLOAD_TOO_LARGE', message: …}`. Ветка ставится рядом с существующей
`entity.parse.failed` → `400 VALIDATION_ERROR`: это ошибки одного класса и одного источника
(body-parser), и `http/errors.ts` уже объявлен единственным местом, где ошибка превращается в статус.

Отклонён вариант «не трогать чужой файл, а поставить свой error-middleware сразу после
`express.json()`»: механически он работает (Express ищет 4-арный обработчик ниже сбойного слоя), но
даёт две точки превращения ошибки в статус и второй, неочевидный error-middleware в середине цепочки.
Цена выбранного варианта — правка файла, который создала `back-001`; она допустима именно здесь,
см. Р8.

Механика распознавания:

- проверка структурная — `error instanceof Error && 'type' in error && type === 'entity.too.large'`,
  как у существующей `isBodyParseError`. `instanceof PayloadTooLargeError` не используется:
  `http-errors` не является объявленной зависимостью `apps/api`, а импорт класса ради `instanceof`
  привязал бы код к транзитивному пакету;
- `SyntaxError` в проверку не входит: `PayloadTooLargeError` им не является (проверено), поэтому
  существующая ветка парсинга нового поведения не получает и остаётся в силе;
- `message` формируется из поля `limit` самой ошибки, поэтому `errors.ts` не импортирует
  `BODY_LIMIT_BYTES` и рассинхронизация текста с фактическим лимитом невозможна;
- `PAYLOAD_TOO_LARGE` — литерал в `http/errors.ts` рядом с `NOT_FOUND`, а не член
  `DomainErrorCode`: домен об ограничениях транспорта не знает, и `ERROR_STATUS` (таблица
  `satisfies Record<DomainErrorCode, number>`) не расширяется.

### Р7. `413` вне контракта: gap G5, контракт не правится

API impact задачи — `NONE` (brief), поэтому `.tsp` не открывается. `413 PAYLOAD_TOO_LARGE` контрактом
не описан и попадает в тот же класс, что уже принятые `404 NOT_FOUND` и `500 INTERNAL_ERROR` (gap G3
`back-001`): ситуация вне описанных операций, форма ответа — `ErrorResponse`. Соответствие форме
проверено по контракту: базовая модель `ErrorResponse` (`packages/contracts/src/models/errors.tsp`)
объявляет `code` как `string` с `@maxLength(100)`, литеральные коды сужают только производные модели,
поэтому `PAYLOAD_TOO_LARGE` — валидный `ErrorResponse`, просто не документированный.

Фиксация: **G5** в этом ADR и в `result.md` задачи. Машиночитаемого backend-реестра гапов в проекте
нет (`back-001/result.md`, O3: `contract-gaps.xml` — реестр UISpec и привязан к экранам). Таблицы
`back-001` эта задача не правит: чужая задача, `status: согласовано`.

| # | Gap | Состояние |
|---|---|---|
| G5 | `413 PAYLOAD_TOO_LARGE` при превышении лимита тела контрактом не описан | open, осознанно. Класс G3. Форма `ErrorResponse` соблюдена; generated SDK кода не знает и разберёт ответ как неизвестную ошибку |

Описать `413` в контракте отклонено: ограничение размера тела — свойство транспорта, одинаковое для
всех 12 операций, а описать его пришлось бы в каждой; клиентской ветки на этот ответ нет. Ровно то же
обоснование уже принято для `404`/`500`.

### Р8. Границы роли: почему задача правит `apps/api/src/**`

`infrastructure-agent.md` в «Разрешено менять» перечисляет `infra/**`, Dockerfile, compose, CI и
environment examples — `apps/api/src/**` там нет. Работа тем не менее ведётся в границах, потому что:

- `brief.md` задачи (`status: согласовано`) прямо описывает предмет как middleware backend-сервера и
  требует ответ `413` от него, а не от прокси; вариант «reverse proxy» отклонён ещё в первой редакции
  этого ADR;
- `back-001` (Р8, «Совместимость и миграция», ограничение 10 `result.md`) зарезервировала за
  `task-infra-003` конкретную точку вставки и прямо оставила лимит тела нерешённым — то есть передала
  решение этой задаче;
- перечень открываемых файлов ограничен четырьмя (см. «Затронутые компоненты»); ни один другой файл
  `apps/api` не открывается, доменный и прикладной слои не трогаются.

Правило 8 `AGENTS.md` соблюдается: скрытых изменений согласованных требований нет — расширение
поведения `errorMiddleware` записано здесь, до реализации.

### Р9. Как проверяется

Три уровня, потому что brief требует и curl-проверок, и браузерной smoke-проверки, а в `apps/api` уже
есть `node --test`:

1. **Автотесты** — новый файл `apps/api/src/http/security.test.ts` по существующей схеме
   (`createApp(deps)` на `listen(0)` + глобальный `fetch`, без `supertest`): AC1–AC4 воспроизводятся в
   `npm test -w @minical/api`, а не только руками. Плюс регрессия: `entity.parse.failed` по-прежнему
   даёт `400 VALIDATION_ERROR`, а тело чуть меньше лимита не даёт `413`.
2. **curl** — AC1–AC4 на реально поднятом сервере (`npm start -w @minical/api`), как требует brief.
3. **Браузер** — AC5 вручную: из origin web-сборки клиента выполняется `fetch` к API, в консоли не
   должно быть CORS-ошибки. Код клиента не правится — это территория Frontend Agent и вне scope
   задачи.

## Последствия и компромиссы

Положительные:

- web-клиент работает без CORS error; ошибки API читаемы из браузера, потому что CORS-заголовки стоят
  и на ответах об ошибках;
- минимальная защита от MIME-sniffing и clickjacking на всех ответах, включая `404`, `413` и `500`;
- превышение лимита даёт документированную форму `ErrorResponse` со статусом `413`, а не `500`;
- список методов CORS не может разойтись с контрактом (Р3);
- задача не добавляет ни одной npm-зависимости; рантайм `apps/api` остаётся `express` + `zod`.

Ограничения и принятые компромиссы:

1. `Access-Control-Allow-Origin: *` открывает API для любого origin — осознанно принято для локальной
   учебной среды, риск зафиксирован в security review `task-002` (см. `brief.md` → «CORS»). Изменение
   origin-политики в будущем — потенциальный breaking change для web-клиентов.
2. Корректность preflight-ответа принадлежит проекту, а не пакету `cors` (Р1); держится тестами.
3. Лимит 64KB действует только на `application/json` (Р5). Тело другого типа не читается и потому
   памяти не занимает, но и `413` не получает — вернётся `400 VALIDATION_ERROR`.
4. `OPTIONS` на неизвестный URL отвечает `204`, `Allow` на `OPTIONS` не отдаётся (Р4).
5. `Access-Control-Allow-Methods` общий для приложения, а не пооперационный (Р4).
6. `413 PAYLOAD_TOO_LARGE` — ответ вне контракта (G5, Р7); generated SDK этого кода не знает.
7. `X-Frame-Options: DENY` для чистого JSON API даёт минимальный практический эффект — оставлен как
   defense-in-depth по прямому решению brief.
8. Rate limiting, TLS и полный preset helmet остаются вне scope (Non-goals brief).

## Рассмотренные альтернативы

**Пакет `cors` (+ `@types/cors`) вместо своего middleware (Р1).** Отклонён: две новые зависимости, из
функциональности которых при статическом `*` не используется ничего; версия 2.8.5 не публиковалась с
2018 года. Для полноты: `cors()` с дефолтами не подошёл бы и по существу — по документации пакета он
отдаёт `Access-Control-Allow-Methods: GET,HEAD,PUT,PATCH,POST,DELETE` и отражает запрошенные
заголовки, то есть требует явной конфигурации ровно тех же трёх значений (в отличие от остальных
фактов этого ADR, проверено по документации, а не прогоном — пакет не установлен).

**`helmet` (Р1).** Отклонён brief в Non-goals; здесь только подтверждается: из preset'а нужны два
заголовка, остальные (CSP, HSTS) в локальном HTTP-контуре либо бесполезны, либо ломают web-клиент.

**Guard-middleware по `Content-Length` в дополнение к лимиту парсера (Р5).** Отклонён: строго слабее.
`raw-body` считает фактически принятые байты и потому ловит и чанкованное тело без `Content-Length`
(проверено), а guard по заголовку такой запрос пропустит; при этом guard дублирует ответственность
парсера и добавляет второй источник правды о величине лимита.

**Отдельный error-middleware для `413` сразу после `express.json()` (Р6).** Отклонён: сохраняет
`http/errors.ts` нетронутым, но заводит вторую точку превращения ошибки в статус и error-middleware в
середине цепочки, который читатель там не ожидает.

**Жёсткая константа `'GET, POST, PUT, OPTIONS'` (Р3).** Отклонена: требует ручного пересмотра при
любом новом методе в контракте, о чём brief прямо предупреждает; вывод из `ROUTES` стоит две строки.

**Описать `413` в контракте (Р7).** Отклонено: API impact brief — `NONE`; ограничение транспорта
одинаково для всех 12 операций, а описывать его пришлось бы в каждой, без потребителя на клиенте.

**Reverse proxy (nginx, Docker).** Отклонено: избыточно для MVP, добавляет точку конфигурации без
необходимости; brief требует ответ `413` и CORS-заголовки от самого API.

**Не добавлять CORS.** Отклонено: React Web клиент не сможет работать.

## Совместимость и миграция

Начальная настройка для локального dev. При переходе к production:

- `*` → конкретный домен: правится один литерал в `http/security.ts`; появится необходимость в
  `Vary: Origin`, и вот тогда пакет `cors` может стать оправданным — решение Р1 пересматривается
  вместе с origin-политикой, а не раньше;
- security-заголовки могут быть расширены (HSTS, CSP) — добавлением строк в тот же модуль;
- лимит 64KB меняется в одном месте (`BODY_LIMIT_BYTES`), текст ответа `413` следует за ним
  автоматически (Р6).

**Новый HTTP-метод в контракте** — действий не требует: список методов производный (Р3). **Новый тип
тела запроса** (не `application/json`) потребует второго парсера со своим лимитом — Р5 описывает
область действия текущего.

**Docker (`task-infra-001`).** Ограничение Р11 `back-001` в силе и этой задачей не меняется:
зависимости ставятся в корне репозитория с сохранением симлинков npm workspaces. Новых зависимостей
задача не вводит, поэтому на образ не влияет.

**Отношение к последующим задачам.** `task-front-guest-*` получает работающий cross-origin доступ к
API из браузера; никакого клиентского кода эта задача не добавляет.
