# TASK-INFRA-002 — Android builder: Docker-образ для сборки APK

## Контекст и проблема

В `task-000` Android debug APK успешно собран, но только локально: через `expo prebuild` и Gradle на host Android SDK (`~/Library/Android/sdk`, JDK 17). Такая сборка зависит от состояния конкретной машины — версий Android SDK cmdline-tools, JDK, принятых лицензий и переменных окружения — и не воспроизводится на другой машине или в CI без повторной ручной настройки toolchain. Нужен изолированный build-time контур, который собирает Android APK из исходников `apps/client` в предсказуемом Docker-окружении, независимом от host.

**Риск архитектуры хоста (arm64/QEMU).** Хост проекта — Apple Silicon, `uname -m` возвращает `arm64`. Google не публикует Android SDK build-tools под linux-aarch64: инструменты `aapt2`, `zipalign`, `d8` распространяются только как x86_64-бинарники для Linux. Следовательно образ `android-builder` придётся запускать с `--platform linux/amd64` через QEMU-эмуляцию (в используемом на хосте Docker-провайдере, например colima), что кратно замедляет Gradle-сборку по сравнению с нативным arm64. Масштаб проблемы: по `tasks/task-000/result.md` итоговый debug APK весит ~130MB, а сборка включает нативную C++ компиляцию под `arm64-v8a` (CMake/ninja для React Native/Hermes), что дополнительно нагружает эмулируемое окружение. Отсюда реальный риск, что сборка под QEMU окажется непрактично медленной или не завершится в разумное время — это должно быть проверено спайком до полноценной реализации (см. функциональные требования и рассмотренную альтернативу — сборку на x86_64 CI-runner — ниже).

## Цель

Получить Docker-образ `android-builder`, который из чистого checkout `apps/client` детерминированно собирает debug APK (и, опционально, release APK, дополнительно подписанный отладочным ключом для установки), сохраняет артефакт по документированному пути и поддерживает кэширование Gradle/npm для ускорения повторных сборок.

## Зависимости

- `000` — Expo-клиент `apps/client` существует, npm workspace и generation pipeline настроены, Android debug-сборка воспроизведена локально на host SDK; известен рабочий набор шагов (`expo prebuild` → `gradlew assembleDebug`).
- `infra-001` — из scope `task-infra-001` задаче `task-infra-002` требуется только рабочий **Docker Engine на хосте** (установка провайдера — FR1 в `task-infra-001`). Остальной scope `task-infra-001` — контейнер базы данных, docker-compose runtime-контур, `compose.yml` — для `task-infra-002` не нужен и не является блокером. На момент постановки `task-infra-002` Docker на хосте отсутствует. Реализация `task-infra-002` заблокирована только до появления рабочего Docker Engine, а не до завершения `task-infra-001` целиком. При желании установку Docker-провайдера можно вынести в отдельный микро-шаг вне `task-infra-001` — тогда `task-infra-001` и `task-infra-002` разблокируются полностью независимо друг от друга.

## Пользовательские сценарии

Продуктовых пользовательских сценариев нет — задача инфраструктурная. Потребители результата:

- Infrastructure Agent или разработчик из чистого checkout запускает одну документированную команду и получает собранный APK без ручной установки Android SDK/JDK на хосте;
- CI (если подключается) использует тот же Docker-образ для сборки APK как часть проверки или релиза;
- QA/Frontend Agent получает предсказуемый artifact path для установки APK на Android Emulator, запущенный на хосте.

## Функциональные требования

1. **Обязательный разведочный спайк (выполняется первым, до полноценной реализации).** Собрать минимальный вариант образа `android-builder` (linux/amd64 через QEMU, см. риск в «Контекст и проблема»), выполнить одну сборку debug APK из `apps/client` и замерить фактическое время. Результат зафиксировать в `result.md`. Если время окажется неприемлемым (порог фиксируется по НФТ ниже) — остановиться, вернуться к постановке и рассмотреть альтернативу: сборку APK на x86_64 CI-runner (например, GitHub Actions `ubuntu-latest`) вместо локального Docker на arm64-хосте, где Android SDK build-tools доступны нативно без эмуляции.
2. Подготовить Dockerfile образа `android-builder`: Node.js версии, зафиксированной в `.nvmrc`, JDK, Android SDK cmdline-tools и лицензии, необходимые для non-interactive сборки.
3. Образ должен уметь собрать APK из чистого checkout репозитория: установить npm-зависимости, выполнить `expo prebuild` для генерации каталога `android/` (он generated и не хранится в Git) и запустить Gradle-сборку debug APK.
4. Предусмотреть опциональный режим сборки release APK. Сборка `assembleRelease` без настроенного `signingConfig` производит только промежуточный артефакт `app-release-unsigned.apk`, который нельзя установить на устройство/эмулятор (Android отклоняет APK без валидной подписи). Поэтому для получения устанавливаемого release-артефакта unsigned APK должен быть дополнительно подписан отладочным/одноразовым ключом через `apksigner` — с явной пометкой в README и выводе, что такой артефакт непригоден для распространения. Release signing секретами продакшена остаётся вне scope (см. Non-goals).
5. Сохранять собранный APK в документированный, стабильный artifact path на host (например, через bind mount), не привязанный к внутренним слоям образа.
6. Настроить кэширование Gradle и npm/node_modules между запусками контейнера, чтобы повторная сборка была быстрее первой (см. измеримый порог в НФТ и AC4).
7. Добавить npm script или make-команду верхнего уровня, запускающую сборку одной командой.
8. Обновить README корня проекта: команда сборки, требования (Docker), artifact path, известные ограничения.
9. Опционально подготовить CI-заготовку (workflow step), использующую тот же образ для сборки APK. Существующий `.github/workflows/hexlet-check.yml` помечен «DO NOT DELETE OR EDIT THIS FILE» и не подлежит изменению; заготовка добавляется отдельным новым файлом workflow.

## Нефункциональные требования

- Сборка воспроизводима из чистого checkout без ручной настройки host Android SDK/JDK.
- Multi-stage build там, где это уместно, чтобы не раздувать итоговый образ build-инструментами.
- Версии SDK/JDK/Node зафиксированы явно (не `latest`), чтобы сборка не менялась непредсказуемо со временем.
- Секреты для release signing не встраиваются в образ — signing вне scope этой задачи.
- Сборка не требует доступа к Android Emulator или запущенному runtime-контуру (web/api/postgres).
- Хост проекта — Apple Silicon (arm64); Android SDK build-tools (`aapt2`, `zipalign`, `d8`) под linux-aarch64 Google не публикует, поэтому образ `android-builder` собирается и запускается под `--platform linux/amd64` (QEMU-эмуляция). Это ожидаемое и документированное ограничение, а не дефект образа.
- До начала полноценной реализации должен быть заранее оговорён и зафиксирован бюджет времени сборки (холодной и тёплой) — конкретные пороговые значения согласуются на этапе `adr.md`/`plan.md` по итогам спайка (FR1). Фактически измеренное время холодной и тёплой сборки обязательно фиксируется в `result.md`. Если время выйдет за согласованный бюджет — это блокирующая находка, требующая возврата к постановке (см. риск в «Контекст и проблема» и альтернативу с x86_64 CI-runner).

## API impact

`NONE` — задача не меняет HTTP-контракт, backend или domain.

## Acceptance criteria

1. Из чистого checkout одна документированная команда собирает Docker-образ `android-builder`.
2. Контейнер на основе этого образа собирает debug APK из исходников `apps/client` без ручной настройки host toolchain.
3. Собранный APK сохраняется по документированному artifact path и доступен на host после завершения контейнера.
4. В `result.md` зафиксированы абсолютные значения времени холодной сборки (без кэша Gradle/npm) и тёплой сборки (с прогретым кэшем). Тёплая сборка укладывается в минимальный порог ускорения относительно холодной — не медленнее половины времени холодной сборки (тёплая ≤ 0.5 × холодной). Если порог не достигнут, это фиксируется как известное ограничение с объяснением причины.
5. README содержит точные команды сборки, artifact path и явные ограничения (нет release signing, нет iOS, эмулятор — на хосте).
6. Собранный APK устанавливается (`adb install`) и запускается на Android Emulator, запущенном на хосте (smoke-проверка). Unsigned APK установить невозможно: Android требует валидной подписи, и `adb install` для `app-release-unsigned.apk` вернёт `INSTALL_PARSE_FAILED_NO_CERTIFICATES` — поэтому артефакт для smoke-проверки обязан быть подписанным. Основной вариант: debug APK со встроенным JS-бандлом — подписывается автоматически debug-keystore, который Gradle генерирует сам, устанавливается и запускается без Metro dev server на хосте. Альтернативный вариант: release APK, дополнительно подписанный отладочным/одноразовым ключом через `apksigner` (см. FR4) — с явной пометкой, что такой артефакт не пригоден для распространения.
7. Задача явно фиксирует зависимость от рабочего Docker Engine (часть scope `task-infra-001`) и не подменяет текущий статус остального scope `task-infra-001` (runtime-контур web/api/postgres остаётся отдельно).

## Non-goals

- release signing и публикация APK в Google Play или другие сторы;
- сборка iOS-приложения — остаётся на macOS/Xcode toolchain хоста, вне Docker;
- runtime-контейнеры web/api/postgres и docker-compose для локального рантайма — отдельная задача `task-infra-001`;
- запуск Android Emulator внутри Docker;
- CI pipeline целиком — за пределами опциональной заготовки одного шага сборки;
- изменение HTTP-контракта, backend или domain-логики.
