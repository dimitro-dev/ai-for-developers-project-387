# TASK-FRONT-GUEST-002 — Гостевой сценарий: четыре экрана и сквозная проверка

## Контекст и проблема

Гостевая ветка UISpec пересобрана `task-front-ui-002` по макету дизайн-отдела: четыре экрана (12–15), восемь гостевых компонентов, шесть новых helpers, типизированные route-параметры. В `apps/client` реализации нет ни одного гостевого экрана.

Задача образована **слиянием бывших `front-guest-002`…`front-guest-006`** (решение пользователя 2026-08-12): одна фича одним куском вместо пяти задач-экранов. Причины слияния:

- те пять брифов описывали гостевые спеки `front-ui-001`, которые `front-ui-002` заменил, — начинать по ним нельзя (`task-front-ui-002/result.md`, «Известные ограничения», п. 8);
- guest-flow черновик и ключ идемпотентности пронизывают все четыре экрана; разрезание по экранам делит одну сущность между задачами;
- альтернативные пути макета (кадр 8 — слот заняли, кадр 9 — обрыв сети) проверяемы только на собранном сценарии и только против реального API.

Реализация ведётся **этапами внутри одной задачи**: этап = экран, плюс финальный этап сквозной проверки.

## Цель

Реализовать в `apps/client` гостевой сценарий целиком по четырём спекам `front-ui-002` — каталог встреч, выбор даты и времени, данные гостя, подтверждение — на фундаменте `front-guest-001`, и подтвердить его сквозным прогоном на web и Android против реального API, включая конфликт слота и повтор после обрыва сети.

## Зависимости

- `front-ui-002` — источник истины по внешнему виду, состояниям, действиям и путям входа: `12-public-event-types`, `13-public-slots`, `14-guest-booking-form`, `15-booking-confirmation`, восемь гостевых компонентов, `navigation.uispec.xml`, `api-bindings.xml`. `front-ui-001` — историческая база кита, его гостевые спеки заменены.
- `front-guest-001` — фундамент: дизайн-система и токены, `EXPO_PUBLIC_API_BASE_URL` + явный `client.setConfig`, обвязка generated SDK, use-cases и DTO→view-model маппинг четырёх операций, маппер ошибок в канонический корень `$error` с полем `transport`, guest-flow черновик формы и UUID-ключ идемпотентности, гостевая навигация по типизированным route'ам.
- `infra-004` — Prism-мок на `:4010`: база для покомпонентной разработки этапов Э1–Э4.
- `back-001` + `infra-003` — реальный API на `:3001`, открытый для браузера (`Access-Control-Allow-Origin: *`). Обязателен для Э5: мок не хранит состояние, поэтому конфликт слота (кадр 8) и идемпотентный повтор (кадр 9) на нём непроверяемы, а тела 4xx мока — плейсхолдеры, надёжен только HTTP-статус. Backend реализован полностью (12/12 операций контракта `0.2.0`), но хранилище in-memory — состояние живёт до рестарта процесса. Данные гостевого сценария сидируются setup/admin-операциями контракта (без auth): настройка календаря и типы встреч — обычными запросами; контроль бронирований — `GET /admin/bookings`.

## Пользовательские сценарии

**Основной путь.** Гость открывает каталог → видит имя владельца и типы встреч → выбирает тип → выбирает дату в полоске и слот в сетке → «Продолжить» → заполняет имя, email и необязательный комментарий → «Подтвердить встречу» → видит подтверждение с типом, датой, интервалом, timezone и своими контактами.

**Слот заняли (кадр 8).** На «Подтвердить встречу» сервер отвечает `SLOT_UNAVAILABLE` → гость возвращается на экран слотов, слоты перезагружены, прежний выбор снят, показан алерт «Этот слот только что заняли» → выбирает другое время; введённые имя, email и комментарий сохранены.

**Обрыв сети (кадр 9).** Ответа от сервера нет вовсе → экран сообщает, что данные сохранены → «Повторить» отправляет **тот же** ключ идемпотентности и ту же нагрузку → сервер отдаёт уже созданную бронь, второй встречи не возникает.

## Функциональные требования

Каждый этап реализуется по своей спеке; спека — источник истины по составу элементов, набору состояний, путям входа и acceptance criteria экрана. Брифу не положено их пересказывать.

### Сквозное — иконки (согласованное расширение фундамента)

- FR0.1. Подключается `@expo/vector-icons` (входит в Expo SDK, новой внешней зависимости не добавляет); `AppIcon` фундамента получает реальные глифы для всех имён, используемых гостевыми спеками (`cloud-off`, `calendar-x`, `event-type`, `info` и остальные из спек 12–15), плейсхолдер удаляется. Это закрытие долга п.1 `task-front-guest-001/result.md`, согласованное настоящим brief как расширение scope фундамента (правило 8 `AGENTS.md`).

### Э1 — Каталог встреч (`guest.event-types`)

- FR1.1. Экран по [`12-public-event-types.screen.md`](../../../../docs/ui-spec-kit/specs/ui/screens/12-public-event-types.screen.md): состояния `loading`, `content`, `empty`, `error`.
- FR1.2. **Два** чтения при монтировании: `loadPublicCalendar` (`getPublicCalendar` → `displayName` в заголовке) и `loadPublicEventTypes` (`getPublicEventTypes`). Переходом состояний владеет второе; «Повторить» перезапускает пару целиком.
- FR1.3. Компонент `PublicEventTypeCard` с `accentIndex` из helper `eventTypeAccentIndex(id)` — детерминированный индекс акцента из `EventType.id`, не поле контракта. Owner-овский `EventTypeCard` не переиспользуется.
- FR1.4. `selectEventType` → `GuestSlots` с четырьмя параметрами route: `eventTypeId`, `eventTypeName`, `durationMinutes`, `eventTypeDescription`.

### Э2 — Выбор даты и времени (`guest.slots`)

- FR2.1. Экран по [`13-public-slots.screen.md`](../../../../docs/ui-spec-kit/specs/ui/screens/13-public-slots.screen.md): **семь** состояний — `loading`, `dateSelection`, `slotSelection`, `slotUnavailable`, `empty`, `unavailable`, `error`.
- FR2.2. Компоненты этапа: `DateStrip`, `DateChip`, `SlotGrid`, `SlotItem` (переписан `front-ui-002`: props `startAtUtc`/`endAtUtc`/`selected`/`onPress`), `InlineAlert` (здесь `variant="warning"`, переиспользуется на Э3).
- FR2.3. Полоска дат и сетка слотов выбранной даты — из одного набора `Slot[]` через helpers `availableDates`, `slotsOnDate`, `fullDateLabel`. Доступность и `endAtUtc` считает сервер; клиент только форматирует UTC-моменты в `$system.timeZone` гостя.
- FR2.4. Второе действие `refreshPublicSlots` (та же операция `getPublicSlots`) — диспатчится контейнером **при возврате** на экран; распознаёт конфликт через `selectedSlotMissing($result, $state.selectedSlot)` и ведёт в `slotUnavailable`. Неудачный фоновый refresh состояние не меняет (`preserveContent`).
- FR2.5. `continueToForm` недоступна без выбранного слота и передаёт в форму серверные `startAtUtc`/`endAtUtc`. `openCatalog` — `navigation.reset`, не `push`.

### Э3 — Данные гостя (`guest.booking-form`)

- FR3.1. Экран по [`14-guest-booking-form.screen.md`](../../../../docs/ui-spec-kit/specs/ui/screens/14-guest-booking-form.screen.md): `editing`, `validationError`, `submitting`, `serverValidationError`, `networkError` — три разных состояния ошибки вместо одного.
- FR3.2. Валидация — **на submit**: CTA активна при пустых и невалидных полях, подсказки появляются после нажатия (`before="validateGuestForm"` → `onConflict="validationError"`). `$validation.invalid` в `disabledWhen` не используется. Клиентская валидация не заменяет серверную (`MANUAL.md` §9).
- FR3.3. Компонент `BookingSummaryCard` (сводка слота из параметров route + `$system.timeZone`); ссылка «Изменить» в карточке и кнопка «Выбрать другое время» — **одно** действие `chooseAnotherTime` (`navigation.back`).
- FR3.4. Payload — плоский контрактный `CreateBookingRequest`: `eventTypeId`, `startAtUtc`, `id` (ключ идемпотентности из фундамента, `initBookingKey` при монтировании — до первой попытки) и вложенный `guest` (`name`, `email`, `note?`). Поле комментария называется `note`. `endAtUtc` в запросе не участвует.
- FR3.5. Форма при монтировании берёт значения из guest-flow черновика; черновик переживает и возврат к слотам, и обрыв сети. Ни одно поле формы не уходит в параметры навигации.
- FR3.6. `SLOT_UNAVAILABLE`, `SLOT_OUTSIDE_WINDOW`, `SLOT_NOT_ALIGNED` возвращают на **существующий** экран слотов стека (pop, не второй `push`); сам конфликт распознаёт Э2 через FR2.4.
- FR3.7. Серверная ошибка валидации — общим сообщением в `InlineAlert variant="error"` над формой, без подсветки поля; текст — человекочитаемое сообщение маппера `$error` по коду ошибки, сырой английский `message` сервера не показывается (в согласии с acceptance criterion Э5): `ErrorResponse {code, message}` по-полевых данных не даёт (`GAP-004`, open, non-blocking). Иллюстрация `$asset.network-error` отсутствует в пакете — placeholder-компонент с `TODO-ASSET`; вырезать её из PNG макета нельзя.

### Э4 — Подтверждение (`guest.booking-confirmation`)

- FR4.1. Экран по [`15-booking-confirmation.screen.md`](../../../../docs/ui-spec-kit/specs/ui/screens/15-booking-confirmation.screen.md): `content` и `error`.
- FR4.2. Компонент `ConfirmationDetails` — шесть строк кадра 7. Все значения из полей ответа `createPublicBooking` (`Booking`), включая **`eventTypeName`**: из навигации название не берётся, дополнительного запроса нет, `endAtUtc` не вычисляется.
- FR4.3. Состояние `error` — контейнер-guard при открытии экрана без параметра `booking` (deep-link, восстановление стека). Действия, которое переводит в `error`, нет.
- FR4.4. Возврат к каталогу — `navigation.reset`: системное «назад» после подтверждения не возвращает в форму созданной брони.

### Э5 — Сквозная проверка

- FR5.1. Основной путь сценария целиком против **реального API** (`:3001`) на web и на Android-эмуляторе (base URL `10.0.2.2`).
- FR5.2. Путь кадра 8: занять слот сторонним `POST /bookings`, затем подтвердить его из клиента — возврат на слоты, снятый выбор, перезагруженные слоты, алерт; введённые данные сохранены.
- FR5.3. Путь кадра 9: обрыв связи на submit, затем «Повторить» после восстановления — тот же ключ и та же нагрузка, ровно одна бронь в `GET /admin/bookings`. Способ эмуляции обрыва не должен терять состояние API-процесса (блокировка запроса, offline-режим клиента, приостановка процесса — но не рестарт: in-memory хранилище стирается вместе с календарём, типами и бронями); конкретный протокол шагов фиксируется в `plan.md`.
- FR5.4. `App.tsx` не содержит шаблонный текст Expo; первый экран приложения — гостевой каталог.

## Нефункциональные требования

- TypeScript strict, без `any` в новых модулях; web и Android обязательны, iOS — локально при доступном toolchain.
- Новые helpers и state-логика покрываются юнит-тестами, переходы состояний экранов (включая `slotUnavailable` и три состояния ошибок формы) и ключевые компоненты — тестами `@testing-library/react-native` (v14, полностью асинхронный API) — по образцу тестов фундамента; всё в гейте `npm test -w @minical/client`.
- Адаптив — правило раскладки из UX rules экранов каталога и слотов (ширина контента ≤ 760 dp, две колонки от 768 dp, сетка слотов не меньше двух колонок), а не отдельная платформа и не отдельный экран; у экранов формы и подтверждения собственных правил раскладки в спеках нет.
- Никаких ручных правок generated-пакетов; обращения к API — только через generated SDK.
- Изменения фундамента `front-guest-001` — только внутри его согласованного scope; расширение — отдельным согласованием, а не молча в коде (правило 8 `AGENTS.md`).

## API impact

`NONE`. Задача реализует контракт `0.2.0` как есть; `GAP-004` остаётся открытым и не блокирует.

## Acceptance criteria

**По этапам** — acceptance criteria соответствующей спеки выполнены целиком:

1. Э1: четыре состояния реализованы и достижимы по таблице путей входа; имя владельца из `PublicCalendarResponse.displayName`; один и тот же `EventType.id` всегда даёт один и тот же акцент; tap передаёт четыре параметра; пустой каталог и ненастроенный календарь для гостя выглядят одинаково.
2. Э2: семь состояний реализованы и достижимы; в полоске только даты со свободными слотами по возрастанию, выбранная ровно одна; сетка — хронологически, ≥ 2 колонок; «Продолжить» недоступна без слота и передаёт серверные `startAtUtc`/`endAtUtc`.
3. Э3: пять состояний реализованы и достижимы; CTA активна при пустых полях и блокируется только во время `submitting`; ошибки связаны с полями через `target`; данные сохраняются и при возврате к слотам, и при обрыве сети.
4. Э4: два состояния реализованы, возврат к каталогу доступен из обоих; показаны все шесть строк кадра 7; «назад» не возвращает в форму созданной брони.
5. Э5: основной путь пройден на web и Android против реального API; кадр 8 воспроизведён — прежний выбор снят, показан алерт, введённые данные на месте; кадр 9 воспроизведён — повтор по тому же ключу даёт **одну** бронь; ошибки показаны человекочитаемым текстом маппера, а не сырым `message` или статусом.

**Сквозные:**

6. Реализация не расходится со спеками: набор состояний, id действий, `operationId` через `api-bindings.xml`, имена и типы route-параметров, имена полей контракта, пути импорта компонентов и helpers по `components.registry.xml` — как в ките. Расхождение оформляется задачей `front-ui`, а не правкой кода (правило 8 `AGENTS.md`).
7. `npm run uispec:validate` зелёный (обязателен при изменениях UI-кода `apps/client/`).
8. Обязательные проверки `AGENTS.md` зелёные: `contracts:format:check`, `generate:check`, `typecheck`, `npm test`, `uispec:validate` и клиентский гейт `npm test -w @minical/client`. Плюс `expo export --platform web` без ошибок.
9. `AppIcon` рендерит реальные глифы для всех имён из гостевых спек; плейсхолдера в гостевом сценарии не остаётся.

## Non-goals

- Изменение UISpec Kit — только через задачи `front-ui`.
- Owner-ветка (`front-owner-001`), auth, роли.
- Персистентность и БД: сквозная проверка идёт против in-memory backend `back-001`.
- Изменение фундамента `front-guest-001` вне его согласованного scope; единственное согласованное расширение — иконки (FR0.1).
- E2E-автотесты и закрытие `GAP-004`; иллюстрация кадра 9 остаётся `TODO-ASSET`.
