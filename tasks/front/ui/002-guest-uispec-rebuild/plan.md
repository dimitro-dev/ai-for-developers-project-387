# План TASK-FRONT-UI-002

Объём работ ограничен разделом «Затронутые компоненты» [`adr.md`](adr.md). Каждый пункт ссылается на
решение ADR (`Р1`…`Р16` и «Решения по вопросам (harness, 2026-08-08)», далее `Реш.1`…`Реш.7`) и на
требование [`brief.md`](brief.md) (`FR*`, `AC*`). Решения ADR план не пересматривает: он превращает их
в исполнимую последовательность.

Ключевое ограничение порядка (Р15): канон правится **до** первой спеки, которая его использует, а
каждая спека выпускается вместе со своей записью в `api-bindings.xml`/`contract-gaps.xml`. При таком
порядке `uispec:validate` зелёный после каждого пункта — красного «по построению» в этой задаче нет;
что именно краснеет при разрыве пар, показано в разделе «Порядок и зависимости».

Нулевая отметка снята прогоном на момент написания плана: `Validated 31 files; errors=0`,
`approved=26, draft=5`, `--lint` молчит, `run_tests.py` — 17 кейсов PASS. Целевая отметка после
задачи: **38 файлов** (+7 компонентов), `errors=0`, `approved=26, draft=12`, `--lint` молчит,
`run_tests.py` — 18 кейсов PASS.

## Порядок и зависимости

```text
P01 → P02 → P03 → P04 → P05 → P06 → P07 → P08 → P09 → P10 → P11 → P12 → P13 → P14 → P15 → P16 → P17 → P18
 │      └──── канон ────┘     └─ токены и реестр ─┘   └ комп. ┘   нав.   └──── экраны + их записи ────┘   │      └── приёмка ──┘

                                                                                                 P16 удаление форка

Цепочка последовательная: параллельных ветвей нет. Разрешённые перестановки ровно две:
P05/P06 ↔ P07 (токены и реестр независимы), перенос PNG из P15 — в любой момент до P16.
```

- **P01 — строго первым.** Снимок снимается до любой правки; снятый после первого редактирования
  ничего не доказывает (AC9).
- **P02 → P03 → P04 — канон до спек.** Порядок ADR (Р15 шаг 2): MANUAL, затем allowlist валидатора,
  затем фикстура. Обратный порядок запрещён по смыслу: инструмент, разрешающий то, чего нет в MANUAL,
  делает канон вторичным по отношению к коду. Строка `uispec-language.md:11` идёт вместе с
  валидатором, а не с MANUAL, — она указывает именно на allowlist (отличие от порядка Р15 шага 2
  косметическое: оба файла — документация, ни один не читается валидатором).
- **P05 → P06 → P07 → P08/P09 — снизу вверх.** Компонент не может ссылаться на токен, которого нет
  (`unknown token/reference`), и на тег, которого нет в реестре (`unregistered tag`). P06 обязан
  предшествовать P08: выбранные `DateChip` и `SlotItem` используют именно guest-токен, а не
  `action.primary`.
- **P10 → P11.** Параметры route — источник данных карточки сводки (FR11); экран формы (P13) их
  читает, экран каталога (P11) их передаёт.
- **P11 → P12 → P13 → P14 — по экрану за пункт, каждый со своей записью в реестрах.** Это главное
  уточнение относительно Р15 шага 4, который группирует всё в один атомарный шаг: атомарность нужна
  не для всех четырёх экранов сразу, а для пары «экран + его новая запись». Поэтому
  `<Binding loadPublicCalendar>` выпускается вместе с экраном 12, `<Binding refreshPublicSlots>` — с
  экраном 13, `GAP-004` — с экраном 14. Порядок между экранами задан связями переходов: 12 толкает в
  13, 13 — в 14, 14 — в 15.
- **P15 после P14**: гостевой раздел `FRAME_MAP.md` ссылается на конечные имена состояний. Перенос
  PNG внутри P15 — единственная операция пункта, которую допустимо выполнить раньше (см. ниже).
- **P16 — последняя правка кита.** До этого момента `specs/guest/**` остаётся под рукой как источник
  содержания: тексты кадров, состав props, присланная карта кадров. Удалять раньше — значит писать
  спеки по памяти.
- **P17 → P18**: сначала инструмент подтверждает кит, потом корневые гейты и сверка снимка. Обратный
  порядок дал бы отчёт по неподтверждённому состоянию.

### Что происходит с `uispec:validate` между пунктами

При описанном порядке **кит валиден после каждого пункта**: красного «по построению» в этой задаче
нет. Это не случайность, а свойство парного выпуска — и ровно поэтому порядок нельзя менять.

| После пункта | `uispec:validate` | Что означает красный |
|---|---|---|
| P01 | зелёный, 31 файл, `approved=26 draft=5` | нулевая отметка; расхождение — грязная рабочая копия |
| P02 | зелёный, 31 файл | валидатор MANUAL не читает; красный = случайная правка спек |
| P03 | зелёный, 31 файл, **ни одного нового WARN** | правка задела существующие проверки, а не расширила их |
| P04 | зелёный + `run_tests.py` 18/18 | см. блокер B1 |
| P05, P06 | зелёный, 31 файл | объявленный, но не использованный токен валидатор не проверяет |
| P07 | зелёный, 31 файл | запись реестра без пользователя ошибкой не является (проверено, Р15 шаг 3) |
| P08 | зелёный, 35 файлов | пропущенный токен (P05/P06), незарегистрированный тег (P07) или корень `<Repeat item=>` вне `REF_PREFIXES` (Р16) |
| P09 | зелёный, 38 файлов | то же; плюс ни одной записи P07 без пользователя (AC2) |
| P10 | зелёный, 38 файлов | навигационные `<Param>` валидатор не читает; красный = правка задела owner-часть файла |
| P11 | зелёный | настоящий дефект спеки: V1/V3/V6/V11 |
| P12, P13, P14 | зелёный | то же |
| P15, P16 | зелёный, 38 файлов | `FRAME_MAP.md` и `specs/guest/**` вне разбора валидатора — красный означает задетые спеки |

**Чем красный был бы, если разорвать пары** (перечислено, чтобы исполнитель не «оптимизировал»
порядок и не принял ложную красноту за дефект):

| Разрыв | Что краснеет |
|---|---|
| Все биндинги одним пунктом до экранов | `V1: Binding "loadPublicCalendar" не соответствует ни одному api-action`, то же для `refreshPublicSlots` — два ERROR, живущих до последнего переписанного экрана |
| Все экраны до биндингов | зеркально: `V1: api-action "loadPublicCalendar" имеет 0 Binding`, `refreshPublicSlots` — то же |
| Экран 14 до записи `GAP-004` | `V9: маркер GAP-004 не зарегистрирован` |
| Спеки до P03 | `WARN V7: неизвестный атрибут onErrorWhen=`, `WARN unknown token/reference $error.code` (нарушение AC4) и `V5` про route-сироту `GuestSlots` |
| Спеки до P05–P07 | 14 × `unregistered tag`, `unknown token/reference` по пяти размерам, V8 по шести helpers |

Единственное промежуточное несоответствие, **невидимое валидатором**: `reference:
../assets/guest-mobile-flow.png` во frontmatter экранов P11–P14 указывает на файл, который приезжает
в `specs/ui/assets/` только в P15. Валидатор пути `reference` не проверяет (проверено), поэтому
прогон остаётся зелёным — но состояние не сдаваемое. Устраняется либо выносом переноса PNG перед
P11, либо выполнением P15 сразу после P14; в любом случае перенос обязан предшествовать P16, иначе
удаление `specs/guest/` унесёт макет.

## Блокеры и открытые вопросы

**B1. Правка валидатора (P03) может сломать негативные фикстуры.** `run_tests.py` держит 17 кейсов,
из которых `V7-unknown-kind`, `V6-unknown-state`, `V6-unknown-route` и `V8-unknown-helper-warn`
проверяют ровно те механизмы, которые правит P03 (allowlist атрибутов, разбор ветвей, словарь
корней). Признаки проблемы: кейс перестал падать; изменился текст, который кейс ищет в выводе;
`base-ok` начал выдавать предупреждения. Порядок действий при расхождении: **не** ослаблять и не
переписывать существующий кейс, чтобы «стало зелено». Сначала определить, что именно изменилось в
поведении; если решение Р4 действительно требует изменить смысл существующей проверки, это правка
канона за пределами ADR — `adr.md` возвращается в `черновик` (правило 8), а не подгоняется тест.
Аддитивность правки (новый элемент в двух множествах и обобщение одного цикла на второй атрибут)
делает такой исход маловероятным, но именно поэтому его нельзя закрывать молча.

**B2. Перенос макета в `specs/ui/assets/` (P15) меняет `ASSETS.md`, на который ссылаются
owner-спеки.** Файл — общий: его четыре строки (`$asset.setup-check`, `$asset.calendar-share`,
`$asset.event-types`, `visual reference | owner-mobile-flow.png`) обслуживают owner-экраны 01, 05, 06.
Риск — соблазн «привести таблицу в порядок под два макета»: переименовать строку owner-макета,
переставить столбцы, переписать нижний абзац про placeholder'ы. Любая из этих правок — нарушение AC9
(owner-строки в общих файлах не изменены), и именно её поймает `diff` в P18. Допустимо ровно две
добавленные строки.

**B3. Brief `task-front-guest-001…006` останутся с устаревшим содержанием до отдельного прохода.**
Переписывание в scope не входит (non-goal brief), поэтому после этой задачи в репозитории
одновременно живут актуальный кит и шесть brief, описывающих замещённые черновики: группировку слотов
по датам вместо полоски дат, одно состояние `error` вместо трёх, `EventTypeCard` вместо
`PublicEventTypeCard`, одно чтение каталога вместо двух. Практическое следствие: начинать
`front-guest-002…005` по их текущим brief нельзя — получатся экраны, не соответствующие ките.
Единственная страховка, которую даёт эта задача, — адресный перечень расхождений в `result.md`
(P18); сам проход по brief должен быть отдельной задачей и, по правилу 11, заново согласован.

**B4. Id и значения guest-токена выбранного состояния ADR не фиксирует (P06).** Реш.7 задаёт
требование (аддитивный токен, контраст ≥ 4.5:1 к тексту, owner-строки неизменны), но ни имени, ни
пары «светлая/тёмная» в ADR нет — в отличие от девяти токенов Р12, значения которых уже измерены.
План фиксирует ограничения и оставляет подбор исполнителю: имя по конвенции файла, значение
измеряется и записывается в `result.md` вместе с расчётом. Вторая половина Реш.7 остаётся в силе как
единственный допустимый fallback: если синий замысел кадров 2/3 при ≥ 4.5:1 недостижим, фиксируется
ограничение с измеренным значением и именем токена, его вызывающего, — и токен не заводится. Выбор
между «завёл токен» и «зафиксировал ограничение» делается по измерению, а не по вкусу, и обязан быть
показан числом.

**B5. `clearSelectedSlot` — свободная метка или объявленное действие?** Р11 задаёт
`selectDate ... after="clearSelectedSlot"`, но самого `clearSelectedSlot` в перечне действий ADR нет.
План исходит из того, что это **свободная метка хука**, как `before="validateGuestForm"`: MANUAL
прямо пишет, что валидатор такие значения не резолвит ни в один реестр. Если исполнитель предпочтёт
объявить полноценный `<Action id="clearSelectedSlot" kind="local.update">`, это допустимо и не
противоречит ADR, но тогда действие обязано попасть в `<Actions>` и в таблицу путей входа — и надо
помнить, что связь `after=` → действие валидатором не проверяется в обе стороны.

**B6. Удаление `specs/.DS_Store` и `specs/ui/.DS_Store` — расширение буквы FR1 до буквы AC10.** FR1
называет `.DS_Store` только внутри `specs/guest/`, а AC10 требует, чтобы `.DS_Store` в ките не
осталось вовсе; в ките их сейчас три. P16 удаляет все три: файлы не относятся ни к owner-спекам, ни к
снимку P01, на валидацию не влияют, и оставлять два из трёх ради буквального чтения FR1 значит не
выполнить AC10. Если reviewer считает это выходом за scope, из P16 снимается ровно один подпункт —
остальная часть задачи не затрагивается.

**B7. Что план проверить не может, и это принято осознанно.** Перечислено, чтобы при сдаче не
выглядело пропуском, и обязано попасть в «Известные ограничения» `result.md` (P18): ветви
`onSuccessWhen`/`onErrorWhen` валидатор не проверяет — опечатка в имени состояния внутри ветви
поймана не будет (Последствие 2, компенсация — таблицы путей входа и проход по AC7 глазами
reviewer'а); три конвенции контейнера (начальный `api.query`, `initBookingKey` при монтировании,
`refreshPublicSlots` при возврате) остаются прозой UX rules, потому что грамматика UISpec триггеров
жизненного цикла не описывает (Последствие 3); guest-flow черновик имени/email/комментария — сущность
вне UISpec (Реш.5); при 7+ типах встреч у одного владельца цвета акцентов повторяются — осознанный
предел палитры из шести (Реш.4); возврат по конфликту как pop, а не второй push, опирается на решение
реализующего агента (Последствие 6); `<Prop type=>` компонентов валидатор не типизирует вовсе —
типы в восьми гостевых компонентах остаются документацией.
