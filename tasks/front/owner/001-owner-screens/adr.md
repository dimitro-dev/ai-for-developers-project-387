# Architecture decision

## Контекст

`front/owner/001` добавляет в `apps/client` второй пользовательский флоу — owner (11 экранов,
табовая навигация), рядом с реализованным гостевым. Контракт и backend не меняются (API impact
`NONE`); все решения — о том, как owner-флоу встраивается в существующий клиент. Спеки приведены
к актуальному состоянию задачей `front/ui/003`: sheets — компоненты экранов, GAP-002 снят,
макеты покрывают все экраны.

## Решение

1. **Точка входа — env-режим.** `EXPO_PUBLIC_APP_MODE=guest|owner`, значение по умолчанию —
   `guest`. App.tsx по режиму монтирует либо текущий гостевой корень, либо owner-корень.
   Обращение к переменной — только статическое (`process.env.EXPO_PUBLIC_APP_MODE`), иначе Expo
   её не инлайнит. Обе платформы поддерживают оба режима: owner-флоу проверяется и в web, и на
   Android.
2. **Навигация owner** — корневой стек `SetupCheck → OnboardingStack → OwnerTabs`;
   `OwnerTabs` — `@react-navigation/bottom-tabs` (новая зависимость клиента), вкладки «Встречи»
   и «Настройки», вложенные native-stack'и. Кастомный таб-бар — компонент `BottomNavigation`
   по спеке кита (системный не соответствует токенам). Param lists — ручные файлы по образцу
   `GuestStackParamList`; черновик профиля онбординга передаётся параметром навигации
   (linking выключен — в URL/history ничего не попадает). `headerShown: false` — экраны рисуют
   свой `AppHeader`.
3. **Bottom-sheets — компоненты экранов, не route.** `AddWorkingHoursSheet` (экраны 03/07) и
   `BookingDetailsSheet` (экран 05) открываются состоянием родителя, данные — пропсами
   (интервал для префилла / `BookingView`); базовый компонент `BottomSheet` на RN `Modal`
   (`transparent`, `onRequestClose` закрывает по системной «назад»).
4. **Сквозного owner-состояния нет.** Аналог `GuestFlowProvider` не заводится: единственные
   межэкранные данные — черновик онбординга (параметр навигации) и данные для sheets (пропсы).
   Состояние экрана — локальная машина состояний: чистый редьюсер + discriminated union
   (паттерн guest-триады Screen/State/View).
5. **Данные и ошибки** — generated SDK через существующую обёртку `runOperation`
   (`UseCaseResult`), канон `$error` с owner-словарём сообщений; серверный `message`
   пользователю не показывается. Название типа в списке встреч — `Booking.eventTypeName`,
   без запроса словаря типов.
6. **Настройки — read-modify-write.** Контракт даёт только full-replace PUT: экраны правки
   загружают полный `CalendarSettingsResponse`, меняют свои поля и отправляют весь
   `SetupRequest` (GAP-003 workaround, зафиксирован в спеках).
7. **Структура кода** — `features/owner/` зеркалит guest: `model/` (view-model + мапперы DTO),
   `usecases/`, `lib/` (чистые хелперы: `formatAvailabilitySummary`, генерация публичного id,
   работа с интервалами), `screens/` (триада на экран), `components/` (owner-композиты).
   Общие компоненты дизайн-системы — в `design-system/components|layout` (BottomSheet,
   SelectField, TimeField, WeekdaySelector, ConfirmationDialog, ProgressHeader,
   BottomNavigation, `rightActions` в AppHeader); акцент типа — существующий
   `eventTypeAccentIndex`. Токены `tokens.ts` синхронизируются с китом (включая фикс
   `color.action.primary` dark из `front/ui/003`).

## Затронутые компоненты

- `apps/client` — App.tsx (выбор корня по режиму), `src/navigation/` (owner-стеки и табы),
  `src/features/owner/**` (новое), `src/design-system/**` (новые компоненты, токен-синк,
  `rightActions`), `package.json` (`@react-navigation/bottom-tabs`).
- Не затрагиваются: `apps/api`, `packages/*` (generated не перегенерируется), гостевой флоу
  (кроме общих компонентов дизайн-системы — обратная совместимость обязательна, jest-гейт
  клиента целиком зелёный).

## Последствия и компромиссы

- Env-режим прост и не трогает гостевой web-экспорт, но переключение режима локально требует
  перезапуска бандлера с `--clear` (известная грабля EXPO_PUBLIC_*).
- Sheets-компоненты убирают shared-route и типизацию параметров, но обработку системной «назад»
  берёт на себя `BottomSheet` (RN Modal), а не навигатор — поведение проверяется на Android явно.
- Read-modify-write оставляет теоретическую гонку «последняя запись побеждает» при параллельных
  правках настроек — принято: владелец один, среда учебная (GAP-003 non-blocking).
- Список встреч без пагинации — принято для учебного объёма (non-goal).
- Кастомный таб-бар дороже системного, но обязателен по токенам и спеке `bottom-navigation`.

## Рассмотренные альтернативы

- **Точка входа**: разделение по платформе (Android=owner, web=guest) — отвергнуто: лишает
  быстрой проверки owner-флоу в браузере и ломает гостевой сценарий на Android; стартовый
  экран-селектор — отвергнуто: экран вне UISpec и лишний шаг для гостя по publicUrl.
- **Sheets как route** (shared modal на уровне Root + типизированные Param) — отвергнуто:
  больше обвязки, механизм передачи полного `BookingView` через параметры дублирует состояние,
  системная «назад» — единственное преимущество, закрывается `onRequestClose`.
- **OwnerFlowProvider** по образцу guest — отвергнуто (YAGNI): сквозного состояния,
  переживающего навигацию, в owner-флоу нет.
- **Иконка/цвет типа по выбору владельца** — отвергнуто ранее решением FR4 путь (б)
  `contract/001`; остаётся детерминированный акцент из `id` и единый глиф.

## Совместимость и миграция

Поведение по умолчанию (без переменной окружения) — гостевой флоу, байт-в-байт совместимо с
текущими сборками. Данных для миграции нет. Изменение общего архитектурного контура —
только добавление второго флоу клиента; после завершения задачи владелец при желании отражает
режимы запуска в `README.md` (пункт плана).
