# Architecture decision — TASK-CONTRACT-001

## Контекст

`brief.md` согласован и фиксирует вход: FR1–FR12 (FR8 снят), API impact `CHANGE`, 13 acceptance
criteria (AC8 снят), non-goals. FR4 решён пользователем — путь (б), контракт по иконке и цвету не
меняется вовсе. ADR решает то, что brief намеренно оставил открытым: форму раскрытия имени владельца,
форму названия типа встречи в брони, механику идемпотентности `POST /bookings`, значение
`info.version`, состав правки контрактного гейта, судьбу записей реестра гапов и перечень возврата
документов `task-back-001`.

Исходное состояние контракта: 8 маршрутов, 11 операций, 11 моделей ошибок, эмиттер `@typespec/openapi3`
на default → `openapi: 3.0.0`, `info.version: 0.1.0`. Все три гостевые операции отдают только данные
типов встреч, слотов и брони; `displayName` живёт исключительно в `SetupStateResponse` и
`CalendarSettingsResponse`.

Самое рискованное место задачи — FR3: OpenAPI 3.0 должен выразить два разных 2xx у одной операции, и
до проверки было неизвестно, доезжает ли это до generated SDK и Zod-схем без потерь. Поэтому решения
принимались не по памяти: полный набор правок применён к копии репозитория в scratchpad, прогнаны
`tsp format --check`, `npm run generate`, `npm test` (`uispec:validate` + контрактный гейт),
`npm run typecheck` и Prism-мок. Факты ниже получены этим прогоном.

| Факт | Проверка | Результат |
|---|---|---|
| Два 2xx у одной операции компилируются | `tsp compile` на union из `201` и `200` с телом `Booking` | успешно, formatter доволен без правок |
| Форма в generated OpenAPI | `paths./bookings.post.responses` | отдельные ключи `'200'` и `'201'`, у каждого `$ref: Booking`, разные `description` от эмиттера |
| Frontend SDK | `packages/api-client/src/generated/types.gen.ts` | `CreatePublicBookingResponses = { 200: Booking; 201: Booking }`; `CreatePublicBookingResponse` сворачивается в `Booking`; статус доступен клиенту — `RequestResult` содержит `response: Response` |
| Backend Zod | `zod.gen.ts` | один `zCreatePublicBookingResponse = zBooking` — оба статуса валидируются одной схемой, потому что тела совпадают |
| Что было бы при разных телах 2xx | тот же прогон с `EventType` в `200` | `zCreatePublicBookingResponse = z.union([...])`, в типах `200: EventType; 201: Booking` — потери нет, но появляется объединение, разбирать которое пришлось бы каждому потребителю |
| `@minItems(1)` доезжает до Zod | `zAvailabilityRule` | `daysOfWeek: z.array(zDayOfWeek).min(1)`; `safeParse({daysOfWeek: []})` → `false` |
| `@minLength(1)` доезжает до Zod | `zGetPublicSlotsQuery`, `zCreateBookingRequest` | `z.string().min(1).max(100)`; `safeParse` с `''` → `false` в обеих схемах |
| `ValidationError` в 400 | generated OpenAPI | `completeAdminSetup` — `$ref: ValidationError`; `updateAdminSettings` — `anyOf[ValidationError, CalendarNotConfigured]` |
| Prism над новым документом | `prism mock … -p 4011` | `/health` и `/calendar` отвечают 200; `POST /bookings` по умолчанию отдаёт **200**, `201` запрашивается `Prefer: code=201` |
| Контрактный гейт | `npm test` после правки двух списков | зелёный; `expectedErrorCodes` менять не потребовалось |
| UISpec-валидатор | `npm run uispec:validate` | зелёный, `errors=0`; V9 требует лишь **регистрации** гапа, а не статуса `open`, поэтому `resolved` при сохранённых маркерах на экранах допустим; V11 сверяет поля `source="api"`-моделей как **подмножество** схемы, поэтому новое поле `Booking` спеки не ломает |
| Число Zod-схем | `grep -c '^export const z'` | 44 → 46 (`zPublicCalendarResponse`, `zGetPublicCalendarResponse`) |

Прогон повторён поверх незакоммиченных конфигов генерации из `task-infra-005` (`input: './…'`,
`plugins: [{ includeInEntry: true }]`, `module: { extension: null }`) — все перечисленные факты
сохраняются, `baseUrl` из `client.gen.ts` при этом исчезает (эффект `infra-005`, не этой задачи).

## Решение

Общая рамка (`lean-code`): каждая правка обязана быть либо прямым требованием brief, либо тем, без
чего требование не выполняется. Ни одного поля «на будущее», ни одного нового файла `.tsp`, ни одной
конструкции, имитирующей то, что OpenAPI 3.0 не выражает.

### Р1. FR1 — отдельная публичная операция `getPublicCalendar`, а не обёртка ответа `getPublicEventTypes`

```tsp
/** Publicly visible identity of the calendar … */
model PublicCalendarResponse {
  @maxLength(200)
  displayName: string;
}

@route("/calendar")
@get
op getPublicCalendar():
  | { @statusCode _: 200; @body body: PublicCalendarResponse }
  | { @statusCode _: 400; @body body: CalendarNotConfigured };
```

Модель кладётся в `models/owner.tsp` рядом с `CalendarSettingsResponse` (это публичная проекция
профиля владельца), операция — в `operations/public.tsp`. Новых файлов нет.

Цена двух путей, посчитанная по кадрам макета:

| | (а) `GET /calendar` | (б) обёртка `{ owner, eventTypes }` у `getPublicEventTypes` |
|---|---|---|
| Кадр 1 — список типов | 2 запроса (`/calendar` + `/event-types`) | 1 запрос |
| Кадры 2, 4 — слоты (адресуемы ссылкой) | 2 запроса (`/calendar` + `/slots`) | 2 запроса, причём второй — весь список типов ради одной строки |
| Кадр 7 — подтверждение (адресуемо ссылкой) | 1 запрос (`/calendar`); бронь уже в руках после `POST` | 1 запрос — снова весь список типов ради строки |
| Форма ответа существующей операции | не меняется | **breaking**: массив → объект; ломает generated тип `GetPublicEventTypesResponses`, Prism-примеры, `Data`-модель `guest.event-types`, P10 `back-001` |
| Симметрия с `getAdminEventTypes` | сохраняется (оба — массив `EventType`) | теряется: одна и та же коллекция в двух формах |
| Списки гейта | `expectedRoutes` 8→9, `expectedOperations` 11→12 | количества не меняются |
| Prism | новый маршрут монтируется автоматически (проверено) | форма примера меняется |

Путь (а) дороже ровно на один маленький запрос на первом кадре и на две строки в списках гейта, а
путь (б) экономит этот запрос, но на трёх из четырёх кадров заставляет тянуть коллекцию ради подписи
и ломает форму существующего ответа. Требование brief «не зависит от точки входа» путь (б) выполняет
только через вырожденное использование операции «список типов встреч» как операции «имя владельца» —
это обход, а не решение. Выбран (а).

Публично раскрывается ровно `displayName`. `timeZone` владельца не добавляется: макет показывает
таймзону **гостя** (кадр 1: `Europe/Prague · GMT+2`), FR1 прямо запрещает считать её следствием, а
самостоятельного требования на таймзону владельца в brief нет. `onboardingCompleted` тоже не
добавляется — состояние onboarding публично выражено ответом `400 CALENDAR_NOT_CONFIGURED`, второй
способ сказать то же был бы дублированием `getAdminSetup`.

### Р2. FR2 — обязательное поле `eventTypeName` в модели `Booking`, snapshot на момент бронирования

```tsp
model Booking {
  id: Uuid;
  @maxLength(100) eventTypeId: string;

  /**
   * Event type name captured at booking time.
   * Snapshot: later renames of the event type do not change bookings already made,
   * and the value survives deletion of the event type.
   */
  @minLength(1)
  @maxLength(200)
  eventTypeName: string;
  …
}
```

Поле в `Booking`, а не отдельная модель ответа. `Booking` в контракте — уже transport-DTO (не
доменная сущность, `docs/domain-model.md` §13) и встречается только в ответах: `201`/`200`
`createPublicBooking` и `200` `getAdminUpcomingBookings`. Значит одно поле в одной модели закрывает
оба случая FR2 **одной и той же формой** — требование «разные формы для одного класса данных
недопустимы» выполняется по построению. Отдельный `BookingResponse extends Booking` продублировал бы
восемь полей и создал бы вторую модель брони без единого потребителя, которому нужна первая.

Ограничения повторяют `guestName` (`@minLength(1)`/`@maxLength(200)`) — это тот же класс snapshot'а
и то же поле-источник (`EventType.name` имеет `@maxLength(200)`).

**Snapshot, а не текущее название.** Причины, в порядке весомости:

1. Поле обязательное. При «текущем значении» его нечем заполнить для брони, чей тип встречи удалён, а
   `docs/domain-model.md` §5 прямо говорит: «Удаление EventType не отменяет существующие Booking (они
   сохраняют ссылку на id/имя для отображения)». Текущее значение сделало бы обязательное поле
   незаполнимым в сценарии, который доменная модель уже разрешает.
2. `Booking` в этой же модели уже хранит snapshot'ы `guestName`/`guestEmail`/`guestNote` (§8, I13).
   Название типа — данные того же рода: то, как встреча называлась, когда её бронировали.
3. Гость получил подтверждение с конкретным названием (кадр 7). Переименование типа владельцем не
   должно переписывать историю уже подтверждённой встречи.

Следствие для реализации, которое контракт задаёт, но проверить не может: значение на
`getAdminUpcomingBookings` обязано читаться из сохранённого snapshot'а, а не досчитываться join'ом с
текущими типами встреч, иначе поведение при переименовании разойдётся между двумя операциями.

### Р3. FR3 — ключом идемпотентности остаётся существующее поле `id` тела, и оно остаётся опциональным

Ни нового поля, ни заголовка `Idempotency-Key`. Обоснование: `docs/domain-model.md` §7.5 уже
называет клиентский `id` идемпотентностью — значит контракт не вводит новый механизм, а начинает
соответствовать доменной модели; поле уже существует, уже `Uuid`, уже опционально (`lean-code`,
ступень 6 — точечная правка вместо новой конструкции). Отдельный заголовок дал бы **два** канала для
одного смысла: `id` в теле осталось бы с неопределённой ролью, а его удаление — breaking-правка
запроса без выигрыша.

Опциональность сохраняется. Сделать `id` обязательным значило бы отменить «`id` генерируется
сервером» из §7.5, то есть скрыто изменить доменную модель через форму контракта (запрет
`contract-agent.md`). Цена решения названа прямо в doc-комментарии: без `id` повтор дедуплицировать
нечем, поэтому клиент, которому нужна безопасная кнопка «Повторить» (кадр 9), обязан сгенерировать
`id` **до** первой попытки. Это требование к клиенту, а не к контракту.

### Р4. FR3 — идемпотентный повтор отвечает `200`, первое создание — `201`

```tsp
op createPublicBooking(@body body: CreateBookingRequest):
  | { @statusCode _: 201; @body body: Booking }   // создано
  | { @statusCode _: 200; @body body: Booking }   // повтор: ничего не создано
  | … девять существующих ответов ошибок
```

Клиент различает ситуации по HTTP-статусу; поле-признак в теле не вводится. `201 Created` у запроса,
который ничего не создал, — ложь на уровне протокола, а различимость нужна по существу: `AC3` требует,
чтобы контракт **документировал** успешный повтор, а не только упоминал его прозой. При едином `201`
машиночитаемая часть контракта о повторе не знала бы ничего.

Тела обоих 2xx **обязаны совпадать** (`Booking`), и это не косметика: при совпадении Zod-плагин
выдаёт один `zCreatePublicBookingResponse = zBooking`, которым проверяются оба ответа, а
`CreatePublicBookingResponse` в SDK остаётся `Booking`. При разных телах появляются `z.union([…])` и
объединение в типах, которое пришлось бы разбирать каждому потребителю (проверено, см. «Контекст»).

Что решение требует от `task-back-001`: use-case `createBooking` больше не может возвращать просто
`Booking` — обработчику нужно знать, какой статус ставить. Возврат становится различающим
(`{ booking, replayed: boolean }` или эквивалент), и это единственная точка, где решение выходит за
пределы контракта. Успешный повтор — не ошибка, поэтому механику `throw DomainError` (Р3 `back-001`)
он не использует.

Ограничение, принятое сознательно: Prism теперь по умолчанию отвечает на `POST /bookings` статусом
`200`, а не `201` — мок выбирает наименьший 2xx (проверено). Штатный `Prefer: code=201` возвращает
прежнее поведение. Клиент, разрабатываемый против мока, обязан трактовать любой 2xx как успех — это и
так правильное поведение по FR3.

### Р5. FR3 — код `DUPLICATE_BOOKING_ID` сохраняется с суженной семантикой

Код не удаляется и не переименовывается: НФТ brief требует стабильности кодов, non-goals запрещают
косметические переименования, а `expectedErrorCodes` (11 кодов) остаётся нетронутым. Меняется
смысл, зафиксированный doc-комментарием модели:

```text
было:  Booking с таким id уже существует (idempotency conflict) → любой повтор = 409
стало: ключ id принадлежит существующей брони, полезная нагрузка которой отличается от запроса;
       повтор с эквивалентной нагрузкой ошибкой не является — он даёт 200 с существующей бронью
```

Три ситуации FR3 различимы так: успешный повтор — статусом `200`; несовпадение тела — `409` + `code:
"DUPLICATE_BOOKING_ID"`; настоящая занятость слота от **другого** ключа — `409` + `code:
"SLOT_UNAVAILABLE"`. Идемпотентность не маскирует конфликт: сравнение по ключу выполняется до
проверки занятости и только для того ключа, который пришёл в запросе.

Правило эквивалентности нагрузки схемой OpenAPI 3.0 не выражается и потому живёт в doc-комментарии
операции, а не в фиктивных ограничениях: нагрузки эквивалентны, когда `eventTypeId`, `startAtUtc` и
**каждое** поле `guest` равны как разобранные значения, а не как исходные строки (один и тот же
instant, записанный `…Z` и `….000Z`, — одна и та же нагрузка). Поле `id` в сравнении не участвует —
оно и есть ключ. Проверяется backend-тестами `task-back-001`.

### Р6. FR5, FR6, FR7 — точные правки ограничений

| FR | Файл | Правка | Что видно в generated |
|---|---|---|---|
| FR5 (G1) | `operations/admin.tsp` | `completeAdminSetup`: новый вариант `400 ValidationError` | `'400'` → `$ref: ValidationError` |
| FR5 (G1) | `operations/admin.tsp` | `updateAdminSettings`: `400 ValidationError` рядом с существующим `400 CalendarNotConfigured` | `'400'` → `anyOf[ValidationError, CalendarNotConfigured]` |
| FR6 (G2) | `models/owner.tsp` | `@minItems(1)` на `AvailabilityRule.daysOfWeek` | `minItems: 1`; Zod — `z.array(zDayOfWeek).min(1)` |
| FR7 (G4) | `operations/public.tsp` | `@minLength(1)` на query-параметр `getPublicSlots.eventTypeId` | `schema.minLength: 1`; `zGetPublicSlotsQuery` — `.min(1)` |
| FR7 (G4) | `models/booking.tsp` | `@minLength(1)` на `CreateBookingRequest.eventTypeId` | `minLength: 1`; `zCreateBookingRequest` — `.min(1)` |

Все пять доезжают до generated Zod и проверяются прямым `safeParse` (см. «Контекст»). Порядок
`@minLength`/`@maxLength` и `@minItems` перед объявлением поля — как у соседних полей; formatter
изменений не потребовал.

Симметричные ограничения на **ответных** полях (`EventType.id`, `Slot.eventTypeId`,
`Booking.eventTypeId`) не добавляются: FR7 называет ровно два поля, оба входные, и ужесточение схемы
ответа не защищает никого — сервер и так обязан отдавать то, что создал. Наблюдение зафиксировано,
чтобы асимметрия не выглядела пропуском.

### Р7. FR9 — `info.version: 0.2.0`

Правило, которым задача пользуется и которое остаётся в силе для следующих контрактных задач: пока
мажор равен нулю, **breaking → минор** (`0.y` → `0.y+1.0`), совместимое дополнение или уточнение
документации → патч (`0.y.z+1`). Изменение содержит breaking-правки (Р2, Р4, Р5, FR6, FR7), поэтому
`0.1.0` → `0.2.0`. Мажор `1.0.0` не берётся: контракт ещё не реализован ни одним потребителем, и
объявлять стабильность нечему.

### Р8. FR10 — контрактный гейт

Фактические значения после правок:

```ts
const expectedRoutes = [          // 8 → 9
```

| # | Проверка | Закрывает |

| 4 | `400` у `completeAdminSetup` и `updateAdminSettings` ссылается в том числе на `ValidationError` | AC5 |

### Р9. FR11 — реестр гапов: GAP-002 расширяется до обоих флоу и закрывается

GAP-002 — единственная запись, которую задача закрывает. Обход `eventTypeName` на
`guest.booking-confirmation` не заводится отдельной записью, а включается в GAP-002: brief сам
называет его «тем же классом расхождения», а запись, рождённая сразу `resolved`, документировала бы

## Последствия и компромиссы

Положительные:

- все девять кадров макета реализуемы без клиентских обходов: имя владельца берётся одним маленьким
  запросом на любом экране, название типа встречи приходит в ответе брони, кнопка «Повторить»
  безопасна;
- потерянный ответ больше не превращает созданную бронь в ошибку — гость видит номер брони и
  подтверждение, а не `409`;
- каждый ответ, который backend обязан отдавать (`400 VALIDATION_ERROR` на setup-операциях),
  документирован; расхождение G1 закрывается вместе с его причиной, а не описывается как ограничение;
- транспортные ограничения согласованы: пустая ссылка на `eventTypeId` отвергается там же, где
  отвергается создание пустого id;
- GAP-002 закрывается для обоих флоу одной формой; в реестре остаётся один открытый гап (GAP-003) с
  полноценным обходом;
- шесть новых проверок гейта делают AC1, AC2, AC3, AC5, AC6, AC7 машинно защищёнными от регрессии, а
  не подтверждёнными однократным чтением YAML.

Компромиссы и принятые ограничения:

1. Гостевой клиент делает на первом кадре два запроса вместо одного (Р1). Кэшируемо и мало; цена
   выбрана осознанно против ломки формы ответа `getPublicEventTypes`.
2. Prism по умолчанию отвечает на `POST /bookings` статусом `200`, а не `201` (Р4). Прежнее поведение
   — `Prefer: code=201`. Документированное в `task-infra-004/result.md` наблюдение становится
   исторически неточным.
3. Семантика идемпотентности схемой не выражена: правило эквивалентности нагрузки живёт в
   doc-комментарии и в backend-тестах (`AC3`, НФТ brief). Контракт гарантирует только набор статусов и
   моделей — на уровне схемы `200` и `201` неотличимы по телу.
4. `id` остаётся опциональным, поэтому безопасность повтора — обязанность клиента: без ключа повтор
   по-прежнему даёт `409 SLOT_UNAVAILABLE`. Контракт этого не может потребовать, не отменив «id
   генерируется сервером» из доменной модели.
5. Обязательное `eventTypeName` — breaking для любого производителя ответа. Цена сейчас низкая
   (реализации нет), но `Booking` перестаёт быть заполнимым из одного `CreateBookingRequest` без
   чтения типа встречи — впрочем, `endAtUtc` этого и так требовал.
6. Snapshot названия означает, что список владельца может показывать устаревшие названия после
   переименования типа. Это выбранное поведение (Р2), а не дефект; отображение «текущего» названия
   осталось бы возможным client-side join'ом, который экраны 05/11 уже умеют.
7. Двенадцатая операция и девятый маршрут расширяют публичную поверхность API. Она остаётся
   анонимной и отдаёт одну строку; жёсткие списки гейта обязаны обновиться в этом же изменении,
   иначе `npm test` красный по построению.
8. Экраны 05, 11 и 15 продолжают жить с обходами, которые контракт уже сделал ненужными. Осознанно:
   правка `approved`-экранов вернула бы `front-ui-001` в `черновик` (правило 8), а экран 15 всё равно
   заменяется `front-ui-002`.
9. Задача трогает артефакты трёх ролей (`.tsp` и generated — Contract Agent; гейт — согласование с
   QA Agent; реестр гапов — реализация решения пользователя). Зафиксировано в НФТ brief, поэтому это
   не скрытое нарушение правила 10, но и не норма: следующая контрактная задача, которой понадобится
   тронуть четвёртый артефакт, обязана обосновать это заново.

## Рассмотренные альтернативы

**Обёртка `{ owner, eventTypes }` у `getPublicEventTypes` вместо новой операции (Р1).** Отклонена:
breaking-правка формы существующего ответа, потеря симметрии с `getAdminEventTypes`, и на трёх кадрах
из четырёх — загрузка всей коллекции типов ради одной строки. Экономия в один запрос только на первом
кадре.

**`displayName` в ответы всех трёх гостевых операций (дублирование).** Отклонено: три места, где
поле нужно синхронно поддерживать, и ответ `getPublicSlots` (массив слотов) пришлось бы завернуть в
объект — то же breaking-изменение, что и в предыдущей альтернативе, только трижды.

**Публичный `GET /calendar`, отдающий `timeZone` владельца вместе с именем.** Отклонено: макет
показывает таймзону гостя, FR1 запрещает выводить таймзону владельца как сопутствующую правку, а
самостоятельного требования нет. Добавить позже дешевле, чем убрать раскрытое поле.

**Отдельная модель ответа `BookingResponse extends Booking` с `eventTypeName` (Р2).** Отклонена:
дублирует восемь полей и создаёт вторую модель брони; `Booking` в контракте и так transport-DTO, а
обе booking-операции возвращают именно его — одно поле в одной модели закрывает оба случая FR2.

**`eventTypeName` как текущее название типа встречи, а не snapshot (Р2).** Отклонено: обязательное
поле стало бы незаполнимым для брони с удалённым типом встречи, что `docs/domain-model.md` §5 прямо
допускает, и переписывало бы уже выданное гостю подтверждение при переименовании.

**Опциональное `eventTypeName?` вместо обязательного.** Отклонено: экран подтверждения обязан быть
самодостаточным (FR2), а опциональное поле возвращает клиенту ту же ветку «названия нет» и тот же
обход через состояние навигации, который задача закрывает.

**Заголовок `Idempotency-Key` вместо поля `id` (Р3).** Отклонён: два канала для одного смысла; `id`
в теле остался бы с неопределённой ролью, а его удаление — breaking-правка запроса без выигрыша.
Доменная модель уже называет клиентский `id` идемпотентностью.

**Сделать `id` обязательным (Р3).** Отклонено: отменяет «`id` генерируется сервером» из
`docs/domain-model.md` §7.5, то есть скрыто меняет доменное правило формой контракта.

**Единый `201` и для создания, и для повтора (Р4).** Отклонён: `201 Created` у запроса, который
ничего не создал, неверен по протоколу, а машиночитаемая часть контракта не документировала бы
успешный повтор вовсе — AC3 держался бы только на прозе. Плюс альтернативы: Prism сохранил бы
прежний дефолтный статус.

**Признак повтора полем в теле (`replayed: boolean` в `Booking`).** Отклонён: поле-мета в доменном

## Вопросы к brief

Brief согласован и не правится. Ниже — то, что при проектировании оказалось за его рамками; Q1 и Q2
требуют явного решения пользователя, Q3 и Q4 — подтверждения выбора.

**Q1. `docs/domain-model.md` расходится с контрактом после Р2, Р4 и Р5, но правка этого файла вне
границ Contract Agent.** Три места: §7 «Поля» не перечисляет `eventTypeName` (хотя §5 уже говорит,
что Booking «сохраняет ссылку на id/имя для отображения», — то есть модель это подразумевала); §11
«Шаг 3» описывает единственный успешный ответ `→ Booking (201 Created)`; §12 каталог трактует
`DuplicateBookingId` как «Booking с таким id уже существует (при идемпотентности)». Brief FR12
перечисляет только документы `back-001` и про `docs/**` молчит, а роль Contract Agent этот файл
менять не вправе. Предложение: включить в план три минимальные правки (строка поля в §7, второй
успешный ответ в §11, уточнение семантики в §12) как явно санкционированное исключение — иначе
источник правды по доменной модели останется расходящимся с контрактом, что по
`docs/sources-of-truth.md` является дефектом. Альтернатива — отдельная задача владельца документа.

**Q2. Судьба `tasks/task-infra-004/result.md`.** Задача завершена, её `result.md` согласован и
фиксирует «все 11 операций» и «валидный `POST /bookings` → `201`». После этого изменения оба факта
исторически неточны. Отзывать согласование завершённой задачи по `tasks/README.md` — тяжёлая
процедура (запись в каталоге помечается/удаляется), а факты были верны на момент проверки.
Предложение: не менять статус, а добавить в `result.md` `infra-004` одну строку-примечание со ссылкой
на `task-contract-001` (12 операций; дефолтный 2xx у `POST /bookings` — `200`, `201` через
`Prefer`). Требуется решение: примечание или возврат статуса.

**Q3. Статус идемпотентного повтора — `200` (Р4).** Решение принято в пользу различимости и
протокольной честности, но выбор близок к монетке: единый `201` не менял бы ни generated-типы, ни
дефолт Prism. Цена выбранного варианта названа в «Последствиях» (п. 2). Подтверждение желательно
до реализации, потому что после регенерации откат снова затрагивает generated и `back-001`.

**Q4. Шесть дополнительных проверок гейта (Р8) — согласование с QA Agent.** НФТ brief требует
согласовывать правку `tests/contract-validation.test.ts`; для двух списков это очевидно, для шести
новых ассертов — нет. Проверки прогнаны и проходят, но их состав — предмет договорённости с QA
Agent, а не единоличного решения Contract Agent. Если состав сокращается, сокращается и защита AC1,
AC2, AC3 от регрессии.

### Решения по Q1–Q4 (harness, 2026-08-08)

Пользователь делегировал ревью и фиксацию решений на время ночного прогона. Решения приняты и входят в состав задачи.

**Q1 — включить три правки `docs/domain-model.md` в план как санкционированное исключение.** Оставлять источник правды расходящимся с контрактом нельзя: по `docs/sources-of-truth.md` это дефект, а не отложенная работа. Правки минимальны и являются прямым следствием этого изменения: строка поля `eventTypeName` в §7, второй успешный ответ в §11, уточнение семантики `DuplicateBookingId` в §12. Дополнительный аргумент — §5 того же документа уже утверждает, что Booking сохраняет имя типа для отображения, то есть правка §7 приводит документ в согласие с самим собой. Исключение фиксируется в `result.md` явно, отдельная задача не заводится: разрыв между контрактом и доменной моделью не должен жить неопределённое время.

**Q2 — примечание в `result.md` задачи `infra-004`, без отзыва согласования.** Факты «11 операций» и «валидный `POST /bookings` → `201`» были верны на момент их проверки, поэтому отзывать согласование завершённой задачи не за что. Добавляется одна строка-примечание со ссылкой на `task-contract-001`: 12 операций, дефолтный 2xx мока — `200`, прежнее поведение — через `Prefer: code=201`. Историческая запись остаётся честной, тяжёлая процедура возврата не запускается.

**Q3 — статус идемпотентного повтора остаётся `200`.** Выбор подтверждён. `201 Created` у запроса, который ничего не создал, — неверное утверждение на уровне протокола, а AC3 требует, чтобы повтор был документирован машиночитаемо, а не только прозой. Цена (Prism по умолчанию отвечает `200`) принята: клиент обязан трактовать любой 2xx как успех независимо от этого решения.

**Q4 — все шесть дополнительных проверок гейта сохраняются.** Роль QA в этом прогоне исполняет harness; ревью состава выполнено. Каждая из шести закрывает acceptance criteria, которое иначе подтверждается однократным чтением generated YAML и после задачи ничем не защищено — сокращать состав значит сознательно снимать защиту AC1, AC2 и AC3 от регрессии. Проверки прогнаны против собранного документа и проходят.

**Q5. Наблюдение без требования решения.** Реестр задач (`tasks/README.md`) уже содержит тип
`contract` и строку `contract-001` — замечание в конце brief («реестр требует расширения») выполнено.
Осталось после задачи обновить в реестре статусы `contract-001` и `back-001`, снимок «Где мы сейчас»
и абзац «Плана разработки» про G1/G2/G4; это работа `result.md`, а не отдельное решение.
