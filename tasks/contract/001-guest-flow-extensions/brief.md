# TASK-CONTRACT-001 — Расширение контракта под гостевой макет и закрытие расхождений, найденных в `task-back-001`

## Контекст и проблема

Задача собирает в один контрактный проход два независимых источника изменений: макет гостевого
флоу от дизайн-отдела и расхождения самого контракта, найденные при проектировании
`task-back-001`. Обе группы правок затрагивают одни и те же файлы `packages/contracts/src/**/*.tsp`
и одну и ту же регенерацию, поэтому разделение их на две задачи означало бы два `generate:check`,
два обновления контрактного гейта и два возврата документов `task-back-001` в `черновик`.

### Макет гостевого флоу (9 кадров, принят пользователем 2026-08-07)

Четыре элемента макета требуют данных, которых в контракте нет. Все четыре пользователем приняты;
ниже — факт расхождения, а не предложение формы.

1. **Имя владельца недоступно гостю.** Кадр 1 — «Запланировать встречу **с Дмитрием**». Сейчас
   `displayName` существует только в `SetupStateResponse` и `CalendarSettingsResponse`, то есть
   исключительно в admin-операциях; все три гостевые операции (`getPublicEventTypes`,
   `getPublicSlots`, `createPublicBooking`) имени владельца не отдают, а `guest.event-types`
   (`docs/ui-spec-kit/specs/ui/screens/12-public-event-types.screen.md`) выводит статический
   заголовок «Типы встреч». Рядом макет показывает `Europe/Prague · GMT+2` — по макету это
   таймзона **гостя**, вычисляемая на устройстве, поэтому таймзона владельца из этого кадра не
   следует.
2. **Название типа встречи отсутствует в ответе создания брони.** Кадр 7 показывает
   «Консультация», а модель `Booking` (`packages/contracts/src/models/booking.tsp:39`) содержит
   только `eventTypeId`. Тот же класс расхождения уже зарегистрирован для owner-флоу как
   **GAP-002** (`docs/ui-spec-kit/specs/ui/bindings/contract-gaps.xml`): экраны
   `owner.upcoming-meetings` и `owner.booking-details` получают название client-side join'ом через
   `getAdminEventTypes`. В гостевом флоу текущая спека `guest.booking-confirmation`
   (`screens/15-booking-confirmation.screen.md`) обходится иначе — держит `eventTypeName` как
   property состояния, приходящую из навигации, и в реестре гапов это не зарегистрировано. Оба
   обхода означают одно: экран подтверждения не самодостаточен, при входе по ссылке или после
   перезагрузки web-клиента название взять негде.
3. **Повтор `POST /bookings` по контракту небезопасен.** Кадр 9 («Ошибка сети») даёт кнопку
   «Повторить». `CreateBookingRequest.id` — опциональный UUID, и повтор с тем же `id` по контракту
   даёт `409 DUPLICATE_BOOKING_ID` **без тела брони**. Значит при потерянном ответе бронь создана,
   а гость видит ошибку и не может ни узнать номер брони, ни отличить эту ситуацию от настоящего
   конфликта. При этом `docs/domain-model.md` §7 (инвариант 5) прямо называет клиентский `id`
   идемпотентностью — контракт документирует противоположное поведение, и `task-back-001/adr.md`
   (Q5) вынужденно зафиксировал трактовку «повтор = конфликт».
4. **Иконка и цвет типа встречи в контракте отсутствуют.** Кадры 1, 2, 4, 7 показывают у каждого
   типа встречи цветной значок; `EventType` и `CreateEventTypeRequest` таких полей не имеют.
   Текущий `event-type-card.component.md` рисует фиксированный `<Icon name="event-type"
   color="$color.action.primary" />`, то есть в спеках уже реализован вырожденный вариант «единая
   иконка, единый цвет»; палитры акцентных цветов в `tokens/colors.tokens.xml` нет вовсе.
   Различение типов между собой — новое требование в любом случае, но цена у двух путей разная, и
   выбор пути определяет, меняется ли контракт (см. FR4).

### Расхождения контракта, найденные при проектировании `task-back-001`

Источник — `tasks/task-back-001/adr.md`, раздел «Совместимость и миграция», таблица «Contract
gaps», и таблица подтверждений пользователя (2026-08-07: «зафиксировать, не чинить здесь»).

- **G1.** `completeAdminSetup` не документирует ответ 400 вовсе; `updateAdminSettings` документирует
  400 только как `CalendarNotConfigured`. При этом backend обязан валидировать их тела generated
  Zod-схемами и выполнять доменные проверки (кратность `slotIntervalMinutes` числу 60,
  `startLocal < endLocal`, непустой `daysOfWeek`, валидность IANA-зоны в ICU), то есть фактически
  отдаёт недокументированный `400 VALIDATION_ERROR` — что запрещено ролью Backend Agent.
- **G2.** `AvailabilityRule.daysOfWeek` (`packages/contracts/src/models/owner.tsp:6`) — массив без
  `@minItems(1)`: пустой список проходит транспортную валидацию и даёт правило расписания, которое
  никогда не срабатывает.
- **G4.** У `CreateEventTypeRequest.id` есть `@minLength(1)`
  (`packages/contracts/src/models/event-type.tsp:26`), а у полей, ссылающихся на этот id —
  query-параметра `getPublicSlots.eventTypeId` и `CreateBookingRequest.eventTypeId` — только
  `@maxLength(100)`. Создать тип события с пустым id нельзя, сослаться на пустой — можно. Из-за
  этого первый пример AC5 brief `task-back-001` («пустое `eventTypeId` → `400 VALIDATION_ERROR`»)
  недостижим: запрос отдаёт `404 EVENT_TYPE_NOT_FOUND`.

### Артефакт генерации: `baseUrl: 'packages'`

`packages/api-client/src/generated/client.gen.ts:16` создаёт клиент с
`createConfig({ baseUrl: 'packages' })`. **Диагноз уточнён 2026-08-07 (`task-infra-005/adr.md`, Ф23):
причина не в отсутствии `@server`, а в bare-относительном `input` в конфигах генерации.** Генератор
парсит `packages/contracts/generated/openapi.yaml` как URL, и первый сегмент пути становится host;
префикс `./` устраняет артефакт полностью — подтверждено тремя прогонами генерации, различающимися
только значением `input`. Правка выполняется в `task-infra-005` (её решение Р6, подтверждено
пользователем) и контракта не касается. Для этой задачи артефакт — контекст, а не предмет работы:
см. снятый FR8.

## Цель

Привести HTTP-контракт в состояние, при котором (1) все девять кадров гостевого макета
реализуемы без клиентских обходов и без второго запроса ради подписи, (2) повтор создания брони
после потерянного ответа безопасен и отличим от настоящего конфликта, (3) каждый ответ, который
backend обязан отдавать по FR3 `task-back-001`, документирован, и (4) транспортные ограничения
согласованы между полем-владельцем идентификатора и полями, которые на него ссылаются. Всё, что
выражается схемой OpenAPI 3.0, живёт в `.tsp`; всё, что не выражается (семантика идемпотентности),
описано в doc-комментариях операции и остаётся предметом backend-тестов, а не имитируется
фиктивными ограничениями.

## Пользовательские сценарии

Новых доменных сценариев задача не вводит: владелец один, гость по-прежнему не регистрируется,
операции остаются в границах MVP. Меняется состав данных существующих сценариев.

### Гость (кадры макета)

1. Гость открывает публичный календарь и видит, **с кем** он планирует встречу, — имя владельца
   доступно на экранах, где макет его показывает, независимо от того, с какого экрана гость вошёл
   (в web-клиенте экран слотов и экран подтверждения адресуемы ссылкой).
2. Гость выбирает тип встречи, различая типы визуально (значок и цвет).
3. Гость отправляет форму, теряет ответ из-за сети и нажимает «Повторить»: повтор либо
   подтверждает уже созданную бронь, либо создаёт её, но не превращает успешное бронирование в
   ошибку.
4. Гость видит экран подтверждения с названием типа встречи, взятым из ответа сервера, а не из
   состояния навигации.

### Владелец

5. Владелец отправляет некорректные настройки (`slotIntervalMinutes: 25`, пустой `daysOfWeek`,
   `endLocal` раньше `startLocal`, несуществующая зона) и получает **документированный** ответ
   `400 VALIDATION_ERROR` — вместо ответа, которого в контракте нет.
6. Если ADR выберет путь (а) в FR4 — владелец задаёт цвет и иконку при создании типа встречи. Это
   влечёт отдельную задачу owner-флоу, в scope настоящей задачи UI не входит.

## Функциональные требования

**FR1. Имя владельца доступно гостю.** Публичная часть контракта должна позволять гостевому
клиенту получить отображаемое имя владельца (`displayName`) на экранах, где макет его показывает
(кадры 1, 2, 4, 7), без обращения к admin-операциям и без зависимости от точки входа в флоу.
Ограничение: публично раскрывается **только** имя; `availabilityRules`, `slotIntervalMinutes` и
`publicUrl` в гостевые ответы не попадают ни целиком, ни по частям — «имя владельца» не должно
превратиться в публикацию `CalendarSettingsResponse`. Форма (новая публичная операция против
расширения ответа существующей операции) — решение `adr.md`. Таймзона владельца из макета **не**
следует; если `adr.md` решит её добавить, это должно быть обосновано самостоятельным требованием,
а не сопутствующей правкой.

**FR2. Название типа встречи доступно из ответа с бронированием.** Ответ операции создания брони
должен позволять отрисовать название типа встречи без второго запроса и без переноса значения
через состояние навигации. Решение обязано закрывать **оба** случая согласованно: гостевой (кадр 7,
`createPublicBooking`) и owner-флоу (GAP-002: `getAdminUpcomingBookings`, экраны
`owner.upcoming-meetings` и `owner.booking-details`) — разные формы для одного класса данных
недопустимы. Форма (поле в модели `Booking` против отдельной модели ответа) — решение `adr.md`;
`adr.md` обязан зафиксировать, является ли значение snapshot'ом на момент бронирования или
текущим названием типа, поскольку от этого зависит поведение при переименовании типа.

**FR3. Повтор `POST /bookings` идемпотентен и отличим от конфликта.** Требования к поведению,
которые контракт должен выразить статусами, моделями ответов и doc-комментарием операции:

1. повтор с тем же ключом идемпотентности и тем же телом возвращает **успешный** ответ с той же
   бронью (тело `Booking` присутствует), а не ошибку;
2. повтор с тем же ключом и **другим** телом остаётся отказом и отличим по полю `code` от
   ситуации 1 и от ситуации 3;
3. занятость слота, возникшая из-за **другого** ключа, по-прежнему даёт `409 SLOT_UNAVAILABLE` —
   настоящий конфликт не маскируется идемпотентностью.

`adr.md` решает: остаётся ли ключом существующее поле `id` или вводится отдельное поле/заголовок;
какой статус у идемпотентного повтора (200 против 201) и как он отличается от первого создания;
сохраняется ли код `DUPLICATE_BOOKING_ID` с новой семантикой (несовпадение тела) или удаляется. Это
изменение семантики существующего кода ошибки — оно обязано быть отражено в разделе про
совместимость `adr.md` и порождает переделку в `task-back-001` (FR12).

**FR4. Иконка и цвет типа встречи: явный выбор пути.** `adr.md` обязан выбрать один из двух путей и
назвать его цену:

| Путь | Что меняется в контракте | Что тянет за собой |
|---|---|---|
| (а) значения задаёт владелец | поля появляются в `EventType` и `CreateEventTypeRequest`, то есть в ответах `getAdminEventTypes`, `createAdminEventType`, `getPublicEventTypes` и в теле создания | владельцу нужен UI выбора: `screens/10-create-event-type.screen.md` (сейчас `status: approved`, форма из четырёх полей) возвращается в `draft`, меняются `event-type-card.component.md` и `tokens/colors.tokens.xml`, реализация — отдельная задача owner-флоу. Контракт не должен получить поля, которые ни один owner-экран не умеет заполнить |
| (б) значение выводится детерминированно (цвет из `id`, единая иконка) | контракт **не меняется вовсе** | правка целиком в UISpec: палитра акцентных токенов, правило вывода, проп компонента; задача `front-ui-002` |

Палитра акцентных цветов и набор иконок нужны в обоих путях и в обоих случаях остаются работой
UISpec, а не контракта, — различие только в том, кто определяет значение.

**Решено пользователем 2026-08-07: путь (б).** Цвет выводится детерминированно из `id`, иконка одна
для всех типов. Следствия: в `.tsp` по этому требованию **не вносится ни одной правки**, поля
`icon`/`color` в `EventType` и `CreateEventTypeRequest` не появляются, `10-create-event-type.screen.md`
остаётся `approved`, отдельная задача owner-флоу не заводится. Палитра акцентных токенов, правило
вывода цвета и проп компонента — работа `task-front-ui-002`. Для настоящей задачи FR4 закрыт этим
решением и требований к контракту не порождает.

**FR5 (G1).** Добавить `ValidationError` в ответ 400 операций `completeAdminSetup` и
`updateAdminSettings`, чтобы транспортная и доменная валидация их тел имела документированный ответ.

**FR6 (G2).** Добавить `@minItems(1)` на `AvailabilityRule.daysOfWeek`.

**FR7 (G4).** Добавить `@minLength(1)` на query-параметр `getPublicSlots.eventTypeId` и на
`CreateBookingRequest.eventTypeId`, приведя их к ограничению `CreateEventTypeRequest.id`.

**FR8 — снят 2026-08-07.** Пункт формулировался как лечение артефакта `baseUrl: 'packages'`, но
диагноз оказался неверным (см. раздел «Артефакт генерации» выше): причина в конфигах генерации и
устраняется задачей `task-infra-005`. Самостоятельной ценности у объявления `@server` в MVP не
остаётся: базовый адрес приходит клиенту из runtime-конфигурации (`client.setConfig`, FR2
`task-front-guest-001`), Prism монтирует маршруты от корня документа, а URL с path-сегментом,
наоборот, сломал бы и мок, и списки маршрутов контрактного гейта. Перенесено в non-goals. Номер
сохранён пустым, чтобы ссылки на FR9/FR10 из `plan.md` не разъехались.

**FR9.** Поднять `info.version` (`packages/contracts/src/main.tsp`, сейчас `0.1.0`): состав
операций и семантика кода ошибки меняются, потребители должны различать версии. Конкретное
значение — решение `adr.md`.

**FR10. Регенерация и контрактный гейт в том же изменении.** После правки `.tsp` выполняется
`npm run generate`, и обновлённые `packages/contracts/generated/**`,
`packages/api-client/src/generated/**`, `packages/backend-contract/src/generated/**` входят в тот же
коммит — иначе `npm run generate:check` красный. Если решение меняет набор маршрутов, операций или
кодов ошибок, в этой же задаче обновляются жёстко зашитые списки
`tests/contract-validation.test.ts`: `expectedRoutes` (8 маршрутов), `expectedOperations`
(11 операций) и `expectedErrorCodes` (11 кодов) — первые два проверяются двусторонне с равенством
количеств, поэтому расхождение роняет `npm test`. Это требование, а не побочный эффект.

**FR11. Реестр гапов.** Записи `contract-gaps.xml`, закрытые этой задачей, переводятся в
`status="resolved"` с датой, обновлённым `<Workaround>` (по образцу GAP-001: «Не нужен: поле есть в
контракте…») и ссылкой на задачу в `<Task>`. GAP-003 (частичное обновление настроек,
`PATCH /admin/settings`) в scope не входит и остаётся `open`. Незарегистрированный обход
`eventTypeName` в `screens/15-booking-confirmation.screen.md` (см. контекст, пункт 2) должен быть
либо закрыт решением FR2, либо зарегистрирован как gap — молча остаться необъяснённым он не может.

**FR12. Согласование зависимой задачи `task-back-001`.** По `tasks/README.md` («Возврат к
предыдущему этапу») задача обязана: остановить зависимую задачу, зафиксировать в её документах
ссылку на это изменение и вернуть первый затронутый документ в `черновик`. Затронуты как минимум:
`brief.md` — FR2 (таблица операций), FR4 (таблица `код → статус` и достижимость кодов), AC5 (первый
пример становится достижимым); `adr.md` — Р3 (таблица `ERROR_STATUS`), Р5 (шаг 5 порядка проверок
`createBooking`), Р9 (реестр `ROUTES`), Q2, Q5, таблица contract gaps и таблица подтверждений;
`plan.md` — пункты P07, P08, P09, P11, P12, P13, P17. Конкретный перечень фиксируется по факту
принятого `adr.md`.

## Нефункциональные требования

- Контракт правится **только** в `packages/contracts/src/**/*.tsp` (правило 5); generated-артефакты
  обновляются исключительно запуском pipeline, вручную не редактируются (правило 6).
- Конструкции, доступные только в OpenAPI 3.1, не используются: эмиттер работает на default и
  выдаёт `openapi: 3.0.0` (`docs/contract-pipeline.md`).
- `operationId` и коды ошибок существующих операций остаются стабильными; любое переименование
  классифицируется как breaking и перечисляется в `adr.md` вместе с затронутыми потребителями.
- Ужесточение ограничений не отвергает данные, валидные сегодня, **кроме** двух намеренных случаев:
  пустой `eventTypeId` (FR7) и пустой `daysOfWeek` (FR6) становятся невалидными — это и есть смысл
  правок.
- Семантика идемпотентности (FR3) схемой OpenAPI 3.0 не выражается. Машинно проверяемая часть — набор
  статусов и моделей ответов; сама семантика фиксируется doc-комментарием операции в `.tsp` и
  проверяется backend-тестами `task-back-001`. Фиктивных ограничений, имитирующих поведение, в
  контракте не появляется.
- Задача затрагивает артефакты трёх ролей, и это фиксируется явно, чтобы не выглядеть скрытым
  нарушением правила 10: `.tsp` и generated — Contract Agent; `tests/contract-validation.test.ts` —
  правка согласуется с QA Agent (обязанность из `.opencode/agents/contract-agent.md`);
  `contract-gaps.xml` — реестр, чей собственный заголовок предписывает, что решение принимает
  пользователь, а реализует Contract Agent по `docs/contract-pipeline.md`.
- Все пять обязательных проверок (`contracts:format:check`, `generate:check`, `typecheck`, `test`,
  `uispec:validate`) проходят; `npm run mock:prism` поднимается над обновлённым OpenAPI и отвечает
  на тех же базовых путях.

## API impact

`CHANGE` — в отличие от `back-001`, `infra-004` и `infra-005`. Следствия:

- порядок изменения — по `docs/contract-pipeline.md`: `.tsp` → `contracts:build` → полная
  генерация → просмотр generated diff → фиксация contract impact;
- generated diff входит в тот же коммит (FR10);
- `adr.md` обязан классифицировать breaking changes. Заведомо breaking: изменение семантики
  повтора `POST /bookings` (FR3) и, при выборе соответствующей формы, обязательное новое поле в
  `Booking` (FR2) или новая обязательная публичная операция (FR1). Ужесточение `@minItems`/
  `@minLength` (FR6, FR7) breaking для клиентов, отправлявших пустые значения, — по построению;
- фактическая цена breaking changes сейчас низкая: единственные потребители generated-пакетов —
  документы `task-back-001` (реализация не начата) и Prism-мок; клиентская реализация
  (`front-guest-001…006`) не начата. Это аргумент выполнить задачу до реализации `back-001`, а не
  после.

## Acceptance criteria

1. Гостевой клиент может получить `displayName` владельца из публичной части контракта, не обращаясь
   к `/admin/**`, и не зависит от того, через какой гостевой экран он вошёл; ни один публичный
   ответ не содержит `availabilityRules`, `slotIntervalMinutes` или `publicUrl`.
2. Ответ операции создания брони позволяет отрисовать название типа встречи без второго запроса;
   то же решение применено к `getAdminUpcomingBookings` (GAP-002); `adr.md` фиксирует, snapshot это
   или текущее значение.
3. Контракт документирует все три ситуации FR3: успешный идемпотентный повтор с телом брони,
   отличимый по `code` отказ при несовпадении тела, `409 SLOT_UNAVAILABLE` при конфликте от другого
   ключа. Doc-комментарий операции описывает семантику, включая выбранный статус повтора.
4. Путь (б) FR4 соблюдён: в `.tsp` нет ни одной правки, связанной с иконкой и цветом типа встречи;
   `EventType` и `CreateEventTypeRequest` этих полей не получают;
   `screens/10-create-event-type.screen.md` остаётся `approved`. Палитра и правило вывода цвета — вне
   этой задачи (`task-front-ui-002`).
5. `completeAdminSetup` и `updateAdminSettings` документируют `400 ValidationError` (generated
   OpenAPI: 400 у обеих операций ссылается в том числе на `ValidationError`).
6. `AvailabilityRule.daysOfWeek` в generated OpenAPI имеет `minItems: 1`.
7. `getPublicSlots.eventTypeId` и `CreateBookingRequest.eventTypeId` имеют `minLength: 1`; пустая
   строка отвергается generated Zod-схемами (`zGetPublicSlotsQuery`, `zCreatePublicBookingBody`) —
   проверяемо прямым `safeParse`.
8. **Снят вместе с FR8 (2026-08-07).** Критерий проверял `servers` в generated OpenAPI и отсутствие
   `baseUrl: 'packages'` в `client.gen.ts`. Артефакт устраняется задачей `task-infra-005` правкой
   `input` в конфигах генерации, `servers` для этого не нужен. Номер сохранён, чтобы нумерация
   остальных критериев не сдвинулась.
9. `info.version` в generated OpenAPI отличается от `0.1.0`.
10. `tests/contract-validation.test.ts` соответствует фактическим наборам маршрутов, операций и
    кодов ошибок; `npm test` зелёный.
11. `contract-gaps.xml`: закрытые задачей записи имеют `status="resolved"`, обновлённый
    `<Workaround>` и ссылку в `<Task>`; GAP-003 не тронут; обход `eventTypeName` на экране
    подтверждения либо снят решением FR2, либо зарегистрирован; `npm run uispec:validate` зелёный.
12. Документы `task-back-001` возвращены в `черновик` со ссылкой на эту задачу и перечнем
    затронутых FR/AC/решений/пунктов плана.
13. `npm run contracts:format:check`, `npm run generate:check`, `npm run typecheck`, `npm test`,
    `npm run uispec:validate` — без ошибок; `npm run mock:prism` отвечает на порту 4010 на `/health`
    и на все маршруты контракта по тем же базовым путям.

## Non-goals

- Auth, роли, несколько владельцев, любые сущности вне MVP (правило 2). Публичные операции остаются
  анонимными, гость аккаунта не создаёт.
- Публикация настроек владельца гостю сверх минимума FR1 — прямой запрет, а не умолчание.
- GAP-003 (`PATCH /admin/settings`, частичное обновление настроек): остаётся `open`,
  read-modify-write на клиенте — полноценный обход.
- G3 из `task-back-001/adr.md` (`404 NOT_FOUND` и `500 INTERNAL_ERROR` вне контракта): оба ответа
  относятся к ситуациям, которых контракт не описывает вовсе (неизвестный URL, необработанный сбой);
  осознанное расхождение фиксируется в `result.md` `back-001`, в контракт не вносится.
- Реализация: backend (`task-back-001`), клиент (`task-front-guest-001…006`), новые гостевые
  UISpec-экраны и токены по макету (`task-front-ui-002`).
- `@server` в `.tsp` (снятый FR8): артефакт `baseUrl: 'packages'` порождается конфигами генерации, а
  не контрактом, и устраняется в `task-infra-005`. Объявление сервера может понадобиться позже как
  описание реального окружения — тогда это отдельное решение с собственным обоснованием, а не
  лечение симптома.
- Переписывание `screens/05-upcoming-meetings.screen.md` и `screens/11-booking-details-sheet.screen.md`
  для отказа от client-side join: обход остаётся рабочим и после появления поля, а правка
  `approved`-экранов завершённой `front-ui-001` вернула бы её документы в `черновик` (правило 8).
  Работа передаётся задаче, которая владеет этими экранами.
- UI выбора иконки и цвета владельцем — отдельная задача owner-флоу, даже если FR4 выберет путь (а).
- Пагинация, rate limiting, отмена и перенос бронирований, `PATCH`-семантика где-либо ещё.
- Косметические переименования существующих `operationId` и кодов ошибок.
