# Architecture decision — TASK-006

## Контекст

`task-003` закрыла часть рисков контракта (S3/S4 — string constraints на моделях, `Booking.id → Uuid`), но явно оставила остаток: числовые поля без границ, коллекция без минимального размера, слишком узкий regex таймзоны, незащищённый query-параметр, gate-скрипт с функциональными дефектами и implementation drift (`server.ts`, README). Нужно решение о том, где живёт каждый вид ограничения и что считать «закрытым».

## Решение

1. **Единственный источник истины для schema-выразимых ограничений — `.tsp`.** Всё, что можно выразить средствами OpenAPI-схемы (`minValue`/`maxValue`, `minItems`, `pattern`, `maxLength`, набор допустимых error responses, расположение моделей, `info.version`), добавляется в TypeSpec-исходники и попадает в generated-артефакты через штатный pipeline (`contracts:build` → `generate`). Ручная правка `generated/**` не допускается.
2. **Невыразимые ограничения остаются вне схемы и перечисляются явно**, а не имитируются в OpenAPI фиктивными способами:
   - кратность `slotIntervalMinutes` числу 60 (например, 25 — валидно по `@minValue(15)`/`@maxValue(60)`, но не является делителем 60) — не выразимо стандартными JSON Schema keyword'ами OpenAPI 3.0, проверяется backend/domain тестом;
   - 14-дневное окно генерации слотов — окно фиксируется сервером (в контракте нет `from`/`to`), корректность самого вычисления — backend/domain тест (см. `task-003/result.md`, п.1 «Contract vs Implementation»);
   - глобальное отсутствие пересечений `Booking` — вопрос конкурентного состояния и PostgreSQL exclusion constraint, схемой не доказывается (там же, п.5–6).
   Список не заменяет, а продолжает соответствующий раздел `task-003/result.md` — он не дублируется здесь полностью, а только явно подтверждается, что новые числовые ограничения не пытаются его закрыть.
3. **Query-параметры — тот же класс user input, что и поля моделей.** Риск S3 (`task-003`) был закрыт только для полей моделей; `eventTypeId` в `getPublicSlots` — request input с той же природой риска (unbounded string → storage/parsing атака на транспортном уровне) и должен получить то же ограничение (`@maxLength(100)`, как у `EventType.id`/`CreateEventTypeRequest.id`).
4. **Gate-скрипт из `task-003` должен реально проверять то, что заявляет.** Вакуумная проверка (assert, который не резолвит `$ref` и потому всегда проходит) хуже отсутствия проверки — создаёт ложное чувство покрытия. Чинится: резолвинг `$ref` перед проверкой полей, объявление зависимости `yaml` в `package.json`, добавление `npm run test`, сбор всех несоответствий вместо остановки на первом (иначе один найденный дефект маскирует остальные в том же прогоне).
5. **Implementation drift устраняется, а не документируется как limitation.** `apps/api/src/server.ts` — не полноценный backend (реализация вынесена в отдельные задачи), но раз он существует и отвечает на `/health`, его ответ обязан соответствовать `HealthResponse` и `ErrorResponse` буквально, иначе smoke-проверка вводит в заблуждение относительно формы контракта.
6. **Документационная точность.** `README.md` — первый источник, который читает разработчик; несоответствие заявленной версии OpenAPI (3.1 vs фактические 3.0) и отсутствие пояснения про негитовские `docs/`/`tasks/`/`.opencode/` — небольшие, но реальные источники путаницы, исправляются в этой же задаче как малозатратные.

## Последствия и компромиссы

Положительные:

- одна декларация ограничения (в `.tsp`) вместо разрозненных проверок в тестах/backend;
- gate-скрипт даёт реальный, а не мнимый сигнал о регрессиях контракта;
- явное разделение schema-level и domain-level инвариантов снижает риск повторной попытки «дотянуть» невыразимое ограничение фиктивным способом в OpenAPI.

Компромиссы:

- ужесточение схемы потенциально отклоняет ранее принимавшиеся (хоть и невалидные по смыслу) значения — учтено как намеренное сужение, не breaking change для корректных клиентов;
- перечень невыразимых ограничений требует ручной синхронизации с `task-003/result.md`, если тот документ снова изменится.

## Рассмотренные альтернативы

### Проверять числовые/коллекционные ограничения только тестами backend, не трогая контракт

Отклонено: противоречит принципу «контракт — единственный источник истины» и решению, уже принятому в `task-003` для string constraints (симметрично применяется к numeric/array constraints).

### Сузить `IanaTimeZone.pattern` до explicit-списка зон (enum)

Отклонено: список IANA-зон велик и меняется (например, из-за исторических переименований); регулярное выражение, допускающее корректную структуру идентификатора, достаточно для транспортного уровня — семантическая валидность (существование зоны в базе IANA) остаётся задачей backend.

### Оставить gate-скрипт как есть, зафиксировав дефекты как known limitation

Отклонено: скрипт создаёт ложную уверенность («проверка PASS»), что хуже открытого gap — исправление дешёвое (несколько функций), а цена молчаливо неработающего гейта растёт с каждой новой задачей, которая на него полагается.

## Совместимость и миграция

Runtime-поведение для валидных данных не меняется. Клиенты, отправлявшие значения вне новых границ (например, `slotIntervalMinutes: 1000000` или таймзоны в старом узком формате, для новых — наоборот, ранее отклонявшиеся валидные зоны теперь приняты), получат иной результат валидации; это ожидаемое ужесточение, отдельной миграции данных не требует, так как ограничения применяются к request/response schema, а не к уже сохранённым данным вне scope этой задачи.
