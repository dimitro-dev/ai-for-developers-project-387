# Architecture decision — TASK-001

## Контекст

Нужно зафиксировать доменную семантику до появления transport и persistence моделей.

## Решение

1. Рассматривать `CalendarOwner` как singleton aggregate root для профиля и настроек календаря, но не как authenticated user.
2. Рассматривать `AvailabilityRule` и `GuestDetails` как value objects.
3. Рассматривать `EventType` как отдельную entity со стабильным публичным id.
4. Рассматривать `Slot` как вычисляемый value object, который не хранится как подтверждённая занятость.
5. Рассматривать `Booking` как entity, фиксирующую подтверждённый интервал и snapshot данных гостя.
6. Не создавать отдельную persistent entity Guest в MVP.
7. Разделять domain model, TypeSpec DTO и database records; последующие слои отображают доменные понятия, но не обязаны копировать структуру один к одному.

## Последствия и компромиссы

Положительные:

- API и БД проектируются от согласованных понятий;
- Slot нельзя ошибочно превратить в заранее сохранённую бронь;
- отсутствие Guest account остаётся явным решением;
- инварианты занятости не зависят от Event Type.

Ограничения:

- повторяющиеся контактные данные гостя хранятся в нескольких Booking;
- singleton owner упрощает MVP, но не масштабируется на multi-owner без нового решения;
- доменный документ сам по себе не обеспечивает runtime-проверки.

## Рассмотренные альтернативы

### Хранить Slot как строку базы данных

Отклонено: доступность меняется при создании Booking и вычисляется из правил/занятости.

### Создать отдельную Guest entity

Отклонено: нет регистрации, профиля гостя и сценариев управления им.

### Использовать API DTO как доменную модель

Отклонено: transport-форма не должна определять бизнес-границы и persistence.
