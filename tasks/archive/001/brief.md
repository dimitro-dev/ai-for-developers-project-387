# TASK-001 — Доменная модель и публичный сценарий

## Контекст и проблема

До проектирования HTTP-контракта нужно однозначно определить основные понятия MiniCal, их ответственность, связи и бизнес-инварианты. Иначе TypeSpec зафиксирует случайную transport-модель вместо согласованного домена.

## Цель

Описать доменные сущности и value objects: владелец календаря, тип события, слот, бронирование, данные гостя и публичный сценарий бронирования.

## Зависимости

- `000` — структура проекта и документации подготовлена.

## Пользовательские сценарии

### Владелец

- существует как один заранее заданный профиль без регистрации и входа;
- задаёт имя, timezone и рабочее расписание;
- создаёт типы событий;
- просматривает единый список предстоящих бронирований.

### Гость

1. Открывает публичный список типов событий.
2. Выбирает тип события.
3. Получает свободные слоты на ближайшие 14 локальных дат владельца.
4. Выбирает слот.
5. Передаёт имя, email и необязательный комментарий.
6. Создаёт бронирование без аккаунта.

## Функциональные требования

Подготовить `docs/domain-model.md`, в котором описаны:

1. `CalendarOwner` — singleton-владелец и его calendar settings.
2. `AvailabilityRule` — рабочий интервал владельца как часть настроек.
3. `EventType` — создаваемый владельцем вид встречи.
4. `Slot` — вычисляемый доступный временной интервал; не самостоятельная запись владельца.
5. `Booking` — подтверждённая занятость с UTC start/end и ссылкой на Event Type.
6. `GuestDetails` — snapshot контактных данных внутри Booking, а не аккаунт и не отдельный пользователь.
7. Связи и кардинальности между понятиями.
8. Инварианты:
   - глобальная занятость для всех Event Type;
   - `[startAt, endAt)`;
   - `endAt` вычисляется сервером;
   - Slot должен находиться в 14-дневном окне и рабочем расписании;
   - Slot не гарантирует резервирование до создания Booking.
9. Пошаговый публичный сценарий гостя и состояния успеха/ошибки.
10. Границы между domain model, API DTO и persistence model.

## Нефункциональные требования

- Термины должны использоваться единообразно во всех последующих задачах.
- Документ не должен зависеть от конкретного backend framework или ORM.
- Неописанные поля не следует добавлять «на будущее» без объяснения инварианта или сценария.

## API impact

`NONE` — задача создаёт доменный источник для последующего API design, но не меняет TypeSpec.

## Acceptance criteria

1. Все перечисленные понятия имеют определение, ответственность и жизненный цикл.
2. Явно указано, что Slot вычисляется, а Booking хранится.
3. Явно указано, что GuestDetails — snapshot внутри Booking.
4. Описана глобальная занятость между разными Event Type.
5. Описан полный публичный сценарий гостя и основные ошибки.
6. Документ согласован с `docs/domain-rules.md` либо изменения в правилах вынесены на согласование.
7. `docs/sources-of-truth.md` и `AGENTS.md` обновлены ссылкой на доменную модель после её создания.

## Non-goals

- TypeSpec и OpenAPI;
- проектирование HTTP routes/status codes;
- таблицы PostgreSQL и миграции;
- UI-макеты;
- реализация Slot Engine.
