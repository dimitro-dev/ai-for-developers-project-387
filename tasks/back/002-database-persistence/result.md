# Результат back/002

## Итог

Постоянное хранилище PostgreSQL реализовано и включается одной переменной `DATABASE_URL`;
без неё приложение работает как раньше (in-memory) — контракт запуска «Dockerfile + PORT»
не изменился. Инвариант пересечений (I2) впервые защищён на уровне СУБД exclusion
constraint-ом и подтверждён конкурентным тестом на реальной PostgreSQL. Выполнены все пункты
P01–P10: MR #16 влит, опубликованный DockHost-инстанс переведён на PostgreSQL 2026-08-20 —
настройки и брони переживают рестарт и передеплой (AC5).

## Что изменено

- `packages/database` — зона активирована: пакет `@minical/database` с миграцией
  `001_initial-schema.sql` (таблицы `owner`, `event_types`, `bookings`; singleton владельца
  структурно; exclusion constraint `bookings_no_overlap` — глобально, без фильтра по типу),
  forward-only раннер (`schema_migrations`, advisory lock с `lock_timeout`, транзакция на файл,
  повторный прогон — no-op), CLI-вход для `make db-migrate`, integration-тесты против
  `minical_test` со skip без `TEST_DATABASE_URL`.
- `apps/api` — `store/postgres.ts` (`createPgStore`): SQL руками, вставка брони без
  предварительного SELECT, маппинг `23P01`/`40P01` → `SLOT_UNAVAILABLE`, `23505` →
  `DUPLICATE_*`; `config.ts` — `databaseUrl` (trim, только `postgres://`/`postgresql://`,
  мусор = отказ старта, значение в ошибке не печатается — секрет); `server.ts` — выбор store,
  миграции до `listen`, строка режима в логе, fail-fast при заданной строке и недоступной базе,
  обработчик ошибок пула; сид — только на пустом хранилище (`maybeSeedDemoCalendar`).
- Корневой `Dockerfile` — манифест, исходники и миграции `@minical/database` в цепочке
  рантайм-этапа; образ несёт оба режима.
- `infra` — сервис `api` в compose за профилем `app` (build из корня, healthcheck по `/health`,
  `depends_on: postgres healthy`); цели `db-migrate`, `db-test`, `up-app`; `db-*`-цели уважают
  переопределения `POSTGRES_*` из `infra/.env`; `.env.example` дополнен `SEED_DEMO`.
- CI — job `compose` получил Node и обязательный прогон `make db-test` (площадка, где
  skip-механика не срабатывает).
- Документация — `apps/api/README.md`, `apps/api/architecture.md`, `infra/README.md`,
  `docs/architecture.md`, зональные `AGENTS.md` (database, infra), корневой `README.md`
  приведены к фактическому состоянию.

## Контракт и generated-артефакты

## База данных и миграции

Схема — `packages/database/migrations/001_initial-schema.sql`; применение — на старте процесса
в Postgres-режиме и вручную целью `make db-migrate`. Направление forward-only: откат — новая
корректирующая миграция; локальный полный сброс — `make db-reset`. Destructive-миграций нет.
Инварианты I1, I2, I3, I11, I12, I15 закрыты constraints; конкурентная гонка проверена тестом
(два параллельных INSERT пересекающихся интервалов → ровно один успех, второй `23P01`/`40P01`).

### Публикация (P10)

Управляемой услуги БД CLI DockHost не предоставляет (`project`/`container`/`volume` — весь
набор), поэтому по запасному варианту Р10 ADR поднят контейнер `minical-db` (`postgres:18`,
256 MiB) с volume `minical-db-data` (1 GiB, hdd); данные переживают пересоздание контейнера.
Изоляция NFR5: инстанс базы выделен только этому приложению, база `minical`, пользователь
`minical_app`, пароль — 48-символьный случайный hex (URL-безопасный), живёт только в
переменных контейнеров DockHost; публичного маршрута к 5432 нет — доступ только из внутренней
сети проекта. Переменные приложения заданы полным набором (`DATABASE_URL`, `PUBLIC_WEB_URL`,
`SEED_DEMO=true`) — гоча платформы про стирание незаданных учтена.

## Отклонения от brief / ADR / plan

Отклонений от согласованных brief и ADR нет. Находка ревью «`make db-test` в CI не входит в
`make gates` (правило «одна команда»)» отклонена: это осознанное решение согласованного ADR
(Р8) по прецеденту compose-валидации — Docker-зависимые проверки живут в CI-job `compose`,
локальный `make gates` остаётся зелёным без Docker.

## Известные ограничения и риски

- Volume базы — 1 GiB hdd на поресурсной оплате: следить за балансом DockHost вместе с
  остальными ресурсами; бэкапов платформа для контейнерной БД не делает (learning-проект,
  принято).
- Сид из трёх независимых записей не атомарен: падение процесса между ними оставит постоянное
  хранилище полунаполненным, и guard дальше будет пропускать сид. Окно — миллисекунды,
  инстанс один; принято как ограничение MVP.
- `GET /event-types` в Postgres-режиме упорядочен по `id`, in-memory — в порядке вставки:
  первая карточка гостя при переключении режима может смениться (порядок не контрактен).
- PostgreSQL нормализует uuid к нижнему регистру: эхо `201` для клиентского ключа
  идемпотентности в верхнем регистре разойдётся с последующими чтениями (HTTP-путь реальных
  клиентов шлёт lowercase).
- Вне HTTP-пути (без Zod-границы) PgStore может отдавать сырые ошибки СУБД на входах, которые
  in-memory принимает; на документированные операции не влияет.

## Описание для MR

### Summary

Задача `back/002`: постоянное хранилище PostgreSQL. Приложение двухрежимно: `DATABASE_URL`
задана → Postgres (миграции на старте, exclusion constraint как последняя защита от двойного
бронирования), не задана → прежний in-memory; контракт запуска «Dockerfile + PORT» не изменён.

### Changes

- `packages/database`: миграция начальной схемы, forward-only раннер (advisory lock,
  `schema_migrations`), CLI, integration-тесты (конкурентная гонка, идемпотентность, unique,
  singleton, checks).
- `apps/api`: `createPgStore` (маппинг `23P01`/`40P01`/`23505` → доменные ошибки),
  `DATABASE_URL` в конфиге, выбор store и миграции в `server.ts`, guard демо-сида,
  контракт-тесты Store на реальной PostgreSQL.
- `Dockerfile`: цепочка `@minical/database` в рантайм-этапе.
- `infra`: сервис `api` за профилем `app` с healthcheck, цели `db-migrate`/`db-test`/`up-app`,
  учёт `POSTGRES_*`-переопределений в `db-*`-целях.
- CI: обязательный `make db-test` в job `compose`.
- Документация четырёх зон и корня приведена к фактическому состоянию.

### Verification

`make gates` — зелёный целиком; `make db-test` — database 7/7, api 111/111; smoke образа:
PORT-only (in-memory), персистентность через рестарт контейнера, повторный сид — пропуск без
дублей; fail-fast на недоступной базе — exit 1. Код-ревью high: 9 находок исправлено, 1
отклонена решением ADR, остальные — в known limitations.

### Known limitations

Опубликованный инстанс переводится на PostgreSQL пост-merge шагом P10 (сервис БД + переменные
на DockHost). Сид не атомарен (окно в миллисекунды, один инстанс). Порядок `event-types` и
регистр uuid между режимами могут различаться (не контрактны).
