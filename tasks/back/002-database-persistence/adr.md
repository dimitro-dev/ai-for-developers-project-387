# Architecture decision — back/002

## Контекст

Brief задачи требует постоянного хранилища PostgreSQL с сохранением контракта запуска
(двухрежимность по FR4) и exclusion constraint как последней линии защиты I2. Отправные точки,
которые ADR не выбирает, а наследует:

- Интерфейс store уже спроектирован под PostgreSQL: три репозитория, все методы асинхронные,
  предикаты занятости внутри store (`apps/api/src/store/repositories.ts`). Точка замены
  зафиксирована архитектурой зоны: `store/memory.ts` → `store/postgres.ts` плюс одна строка
  сборки deps в `server.ts` (`apps/api/architecture.md`, «Слои и правила границ»).
- Граница зон: схема, миграции и constraints принадлежат `packages/database/`, вызывающий их
  код — `apps/api/` (`apps/api/AGENTS.md`); форму строки подключения и момент миграций выбирает
  эта задача, контур предоставляет только `POSTGRES_*`, порт и имена баз (`infra/AGENTS.md`).
- Контур `infra/compose.yml` — `postgres:18` с volume и двумя базами: `minical` (разработка)
  и `minical_test` (создаётся init-скриптом для проверок этой задачи).
- Ограничения рантайма: Node 26 strip-only, зависимости ставятся из корня workspace, сборки нет;
  образ ставит только цепочку `apps/api` (`npm ci --omit=dev -w apps/api`), пересборки образа
  задача не требует (ADR `infra/009`, «Совместимость и миграция»).
- Персистентная модель может отличаться от доменной; для `AvailabilityRule` домен допускает
  «JSON-колонка или отдельная таблица» (`docs/domain-model.md` §13).

## Решение

### Р1. Доступ к БД: драйвер `pg`, рукописный SQL, без ORM

`pg` (node-postgres, `Pool`) становится runtime-зависимостью `apps/api`. Реализация
`createPgStore(pool)` в `apps/api/src/store/postgres.ts` пишет SQL руками — восемь методов
интерфейса, по запросу на метод. ORM и квери-билдеры не вводятся: контракт валидируют
generated Zod-схемы, доменная модель уже отделена от persistence, а вторая машинерия
(кодоген моделей, engine-бинарники) повторила бы то, что проект сознательно не завёл
(прецедент: Express без схемной машинерии, CORS без пакета `cors`).

### Р2. Конфигурация: одна переменная `DATABASE_URL`

`config.ts` получает поле `databaseUrl: string | null`:

- переменная отсутствует или пуста → `null` → in-memory режим (контракт запуска, NFR1 brief);
- задана → обязана парситься как URL со схемой `postgres:` или `postgresql:`, иначе отказ
  старта — та же политика «мусор = exit 1», что у `PORT` и `PUBLIC_WEB_URL`;
- задана, но база недоступна или миграция упала → отказ старта, **не** тихий откат в память:
  молчаливый переход в эфемерный режим при настроенной персистентности — потеря данных.

Одна переменная вместо набора `PG*` — меньше точек стирания при обновлении контейнера DockHost
и стандарт PaaS-платформ. Составные части (`POSTGRES_*` контура) склеивает в строку тот, кто
управляет окружением: compose-сервис и make-цели — сами, DockHost — владелец один раз.

### Р3. Сборка deps: выбор режима в `server.ts`, явная строка лога

`server.ts` собирает store по конфигу: `databaseUrl` задан → `createPgStore` (после успешных
миграций), нет → `createMemoryStore()`. Сразу после выбора печатается строка режима:
`MiniCal API: хранилище postgres` либо `MiniCal API: хранилище in-memory — данные не переживут
рестарт`. Это FR4: откат из-за стёртой переменной виден в логах платформы первой строкой.

### Р4. Схема: три таблицы, инварианты — constraints

`packages/database/migrations/*.sql`, snake_case, timestamptz (UTC — I «хранить как UTC»):

```text
owner        id boolean PK DEFAULT true CHECK (id)          — singleton I1: вторую строку
             display_name text NOT NULL                        вставить невозможно
             time_zone text NOT NULL
             availability_rules jsonb NOT NULL                — VO замещается целиком (§3),
             slot_interval_minutes int NOT NULL                 адресация к отдельному правилу
               CHECK (slot_interval_minutes >= 15               не нужна → jsonb, не таблица
                      AND 60 % slot_interval_minutes = 0)
             onboarding_completed boolean NOT NULL

event_types  id text PK                                      — I11 (уникальность)
             name text NOT NULL
             description text
             duration_minutes int NOT NULL CHECK (> 0)

bookings     id uuid PK                                      — идемпотентный ключ
             event_type_id text NOT NULL REFERENCES event_types(id)
             event_type_name text NOT NULL                   — snapshot I15
             start_at_utc timestamptz NOT NULL
             end_at_utc timestamptz NOT NULL CHECK (end_at_utc > start_at_utc)
             guest_name text NOT NULL CHECK (guest_name <> '')   — I12
             guest_email text NOT NULL CHECK (guest_email <> '')
             guest_note text
             created_at_utc timestamptz NOT NULL
             EXCLUDE USING gist
               (tstzrange(start_at_utc, end_at_utc) WITH &&) — I2 + I3: диапазон по умолчанию
                                                                полуоткрытый [), соседние брони
                                                                не конфликтуют
```

Exclusion constraint глобальный — без `event_type_id` в выражении, поэтому расширение
`btree_gist` не требуется: gist по встроенному range-типу входит в ядро PostgreSQL.

### Р5. Ошибки: маппинг кодов PostgreSQL → DomainError в PgStore

`create` — одиночный `INSERT` без предварительного `SELECT` (запрет `apps/api/AGENTS.md`);
неделимость даёт сама СУБД. Отказы транслируются по `code` и имени constraint:

- `23P01` (exclusion_violation) → `DomainError('SLOT_UNAVAILABLE', …)`;
- `23505` (unique_violation) на PK bookings → `DUPLICATE_BOOKING_ID`, на PK event_types →
  `DUPLICATE_EVENT_TYPE_ID`.

Проверки use-case (окно, сетка, `isBusy`) остаются первой линией и дают те же коды до записи;
constraint ловит только гонку — ровно поток из `docs/architecture.md`, шаги 5–7. Многошаговых
транзакций не появляется: каждый метод store — один statement (`owner.save` — upsert
`ON CONFLICT (id) DO UPDATE`).

### Р6. Миграции: SQL-файлы + собственный мини-раннер, прогон на старте

`packages/database` активируется как workspace-пакет `@minical/database`: каталог
`migrations/NNN_<слаг>.sql` и раннер `runMigrations(pool)` (~60 строк): сортировка файлов по
номеру, `pg_advisory_lock`, таблица `schema_migrations` (имя + применён когда), каждая миграция
в транзакции, применение только непримененных — повторный прогон no-op (AC4). Готовые раннеры
(node-pg-migrate, dbmate) отклонены ниже.

Момент прогона — старт процесса в Postgres-режиме, до `listen` (у DockHost нет release-фазы,
отдельный шаг деплоя было бы негде запустить). Ручной прогон и локальная эксплуатация — цель
`db-migrate` (делегат в корне по образцу `db-*`). Направление — forward-only: откат = новая
корректирующая миграция; локально допустим `make db-reset`. Destructive-миграций задача
не содержит.

### Р7. `SEED_DEMO`: сид только на пустом хранилище

`server.ts` перед сидом проверяет `store.owner.get()`: владелец уже есть → строка лога
«демо-сид пропущен: хранилище уже настроено», процесс продолжает работу. На пустом — прежнее
наполнение через use-cases. Это закрывает FR6 для обоих режимов одной механикой: на Postgres
сид отработает один раз за жизнь базы, реальные данные не затираются и не дублируются;
для in-memory поведение фактически не меняется (на старте память всегда пуста).

### Р8. Тесты: критический список brief, две площадки

- `packages/database` (свой Makefile → зона входит в фан-аут gates автоматически):
  integration-тесты схемы и раннера чистым `pg` против `minical_test` — конкурентные `INSERT`
  пересекающихся интервалов (ровно один проходит, второй — `23P01`), пересечение разными
  event type, unique, singleton owner, идемпотентность раннера.
- `apps/api/src/store/postgres.test.ts`: контракт `Store` на PgStore — те сценарии, что уже
  покрывают `memory.test.ts`, плюс маппинг ошибок Р5.
- Выбор режима по конфигурации — юнит в `config.test.ts`, без БД.

Обе БД-группы читают `TEST_DATABASE_URL`; переменная не задана → **явный skip** с печатью
причины (`node:test` skip), поэтому `make gates` из чистого чекаута без Docker остаётся
зелёным — прецедент зоны infra (Docker-проверки вынесены в CI-job `compose`). Обязательный
прогон: CI-job `compose` расширяется шагами «прогнать db-тесты против контура» (цель
`db-test`, она же держит локальный дефолт `TEST_DATABASE_URL` на `minical_test`); локально —
фаза «Проверка», команда фиксируется в `result.md` (DoD зоны database).

### Р9. Compose: сервис `api` за профилем

В `infra/compose.yml` добавляется сервис `api`: build из корня репозитория (корневой
Dockerfile), `depends_on: postgres (service_healthy)`, `DATABASE_URL` на базу `minical`,
`PORT=3001`. Сервис получает compose-профиль (`app`): жизненный цикл БД (`db-up`/`db-down`,
CI-проверки контура, db-тесты) не тянет сборку образа приложения; полный контур поднимается
своей целью зоны infra. Отдельный сервис `web` не нужен — образ раздаёт оба web-бандла тем же
процессом (решение `infra/009`); обязанность зоны «web, API и PostgreSQL через Compose»
закрывается двумя сервисами.

### Р10. DockHost: сервис БД платформы, выделенные база и пользователь

На DockHost поднимается PostgreSQL (managed-услуга платформы; если её нет или она дороже
поресурсного контейнера — контейнер `postgres:18` с volume в том же проекте, выбор
фиксируется в `result.md` по факту). База и пользователь — выделенные для инстанса, доступ
пользователя ограничен своей базой (NFR5 brief). `DATABASE_URL` задаётся в переменных
контейнера приложения — полным набором вместе с `PUBLIC_WEB_URL` и `SEED_DEMO` (гоча
платформы). Порядок перевода — в «Совместимость и миграция».

## Затронутые компоненты

- `packages/database/` — активация зоны: `package.json`, `migrations/*.sql`, раннер,
  integration-тесты, `Makefile` (typecheck/test/gates — зона входит в фан-аут корневого
  `gates` автоматически).
- `apps/api/` — `config.ts` (+`databaseUrl`), `server.ts` (выбор store, миграции, строка
  режима, guard сида), `store/postgres.ts` (+тесты), `package.json` (+`pg`,
  +`@minical/database`).
- `infra/` — `compose.yml` (сервис `api` за профилем), `Makefile` (цели `db-migrate`,
  `db-test`, запуск полного контура), `README.md` (режимы, изоляция NFR5, раздел про
  опубликованный инстанс).
- Корневые `Makefile` (делегаты новых целей), `Dockerfile` (манифест и файлы
  `packages/database` в цепочке `apps/api`), `.github/workflows/ci.yml` (шаги db-тестов в job
  `compose`).
- `docs/architecture.md` — актуальное состояние: зона database в фан-ауте, API двухрежимный.
- Не затрагиваются: TypeSpec-контракт, generated-пакеты, `apps/client`, доменные правила,
  список routes/операций.

## Последствия и компромиссы

- Две реализации `Store` живут параллельно. Цена ограничена: интерфейс из восьми методов,
  контрактные сценарии переиспользуются между `memory.test.ts` и `postgres.test.ts`.
  In-memory остаётся дефолтом запуска без конфигурации — это удерживает контракт запуска
  и скорость существующих тестов.
- `make gates` без Docker проходит со skip БД-тестов: локальный зелёный gates сам по себе
  не доказывает БД-инварианты. Компенсация: обязательный прогон в CI на каждом PR (job
  `compose`) и явная команда в фазе «Проверка» с фиксацией в `result.md`.
- Миграции на старте: недоступная база даёт рестарт-цикл контейнера на платформе — приемлемо
  (лог называет причину первой строкой) и честнее старта без персистентности.
- Forward-only раннер: нет down-миграций; откат — корректирующая миграция вперёд. Для учебного
  однопользовательского сервиса дешевле, чем поддержка парных down-скриптов.
- Собственный раннер — свой код, который надо тестировать (покрывается интеграционным тестом
  идемпотентности); взамен — ноль новых зависимостей в рантайм-образе сверх `pg`.

## Рассмотренные альтернативы

- **ORM / квери-билдер (Prisma, Drizzle, Knex)** — вторая модель данных и кодоген рядом с
  generated Zod, engine-артефакты в образе; для восьми SQL-методов машинерия дороже пользы.
- **postgres.js вместо `pg`** — сопоставим по возможностям; `pg` выбран как самый
  распространённый драйвер с наибольшей базой материалов — «скучный» выбор для учебного
  проекта.
- **Готовый раннер миграций (node-pg-migrate, dbmate, postgres-migrations)** — используемая
  доля (сортировка файлов, таблица учёта, lock) меньше собственных ~60 строк; dbmate — ещё и
  внешний бинарь вне npm-цепочки. Прецедент проекта: CORS/security без `cors`/`helmet`.
- **Набор переменных `PG*` вместо `DATABASE_URL`** — больше переменных = больше точек стирания
  при обновлении контейнера DockHost; нестандартно для PaaS.
- **Fail-fast при отсутствии `DATABASE_URL`** — ломает контракт запуска (NFR1 brief):
  проверяющий с `PORT`-only получил бы падающий контейнер. Отклонено ещё на уровне brief.
- **`btree_gist` + `event_type_id` в exclusion** — запрет пересечений глобальный (I2),
  сужение по типу противоречило бы домену; без скалярных колонок расширение не нужно.
- **Отдельная таблица `availability_rules`** — VO замещается целиком при каждом изменении
  настроек (§3 domain-model), реляционная адресация не нужна; jsonb проще и в точности
  повторяет форму домена.
- **БД-тесты внутри обязательного `make gates` (Docker всегда)** — сломало бы зелёный gates
  на машинах без Docker и удлинило критический путь CI-job `checks`; прецедент infra уже
  разводит Docker-проверки в отдельный job.

## Совместимость и миграция

- **Образ**: структура не меняется — добавляются манифест и файлы `@minical/database` в слои
  цепочки `apps/api`; `pg` приезжает тем же `npm ci --omit=dev -w apps/api` через корневой
  lockfile (как и предсказывал ADR `infra/009`). In-memory путь работает в том же образе без
  единой новой переменной.
- **Контракт**: TypeSpec, generated-пакеты и список операций не тронуты; `apps/client` не
  меняется.
- **Поведение сида**: единственное видимое отличие — на непустом хранилище сид теперь
  пропускается со строкой лога, а не валит процесс; для нынешнего in-memory сценария это
  недостижимая ветка, поведение эксплуатации не меняется.
- **Перевод DockHost** (порядок значим): поднять сервис БД → создать базу/пользователя →
  задать переменные приложения полным набором (`DATABASE_URL`, `PUBLIC_WEB_URL`,
  `SEED_DEMO=true`) → push в `main` → миграции применяются на старте → проверить строку
  режима в логах и AC5 (создать бронь, передеплой, бронь на месте). Накопленное in-memory
  состояние не переносится (non-goal brief).
- **Аварийный откат**: убрать `DATABASE_URL` из переменных контейнера → приложение вернётся
  в in-memory (данные в базе сохраняются и ждут возврата переменной); откат кода — обычный
  revert MR, схема БД обратно-совместима (только новые объекты).
