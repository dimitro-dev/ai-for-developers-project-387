# back/002 — Персистентность: схема БД, миграции и exclusion constraint

## Контекст и проблема

Backend хранит всё состояние — настройки календаря, Event Types, бронирования — в памяти процесса
(`apps/api/src/store/memory.ts`). Любой перезапуск контейнера стирает данные; на опубликованном
инстансе DockHost перезапуск случается при каждом push в `main` (автодеплой), при падении процесса
или обслуживании платформы — календарь возвращается к демо-состоянию сида. Ограничение
зафиксировано в `infra/README.md` («Данные не переживают перезапуск») и в result `infra/009` как
принятое: деплой осознанно сделан раньше персистентности (решение владельца 2026-08-18), чтобы
добавление базы потом не переписывало образ.

Инфраструктурная половина подготовлена заранее: локальный контур `infra/compose.yml` содержит
сервис `postgres:18` с named volume — его данные переживают рестарт и `down`, стираются только
целью `db-reset`. Но к базе никто не подключён: в `apps/api` нет драйвера и строки подключения,
зона `packages/database/` пуста и по своему `AGENTS.md` активируется именно этой задачей.

Кроме потери данных, in-memory ограничивает глубину защиты правила проекта №3 (пересекающиеся
Booking запрещены глобально): сейчас последняя линия — неделимая проверка пересечения внутри
store одного процесса. Database-level exclusion constraint, который держит инвариант при любом
числе соединений и процессов, без базы недостижим.

Отдельное внешнее условие: проект проходит проверку курса, чей контракт запуска — «образ
собирается по Dockerfile из корня и запускается с одной переменной `PORT`». Появление базы не
должно этот контракт сломать.

## Цель

Постоянное хранилище PostgreSQL: схема и миграции в `packages/database`, реализация store на
Postgres в `apps/api`, exclusion constraint как последняя линия защиты от пересечения
бронирований. Настройки владельца и брони гостей переживают рестарт и передеплой — локально и на
DockHost.

## Зависимости

- `infra/001` — локальный compose-контур PostgreSQL с volume (завершена).
- Граница совместимости — ADR `infra/009`, раздел «Совместимость и миграция»: образ не
  переписывается, `pg`-зависимость приезжает тем же `npm ci` с workspace-фильтром; на деплое
  добавляются сервис БД платформы и переменная подключения.

## Пользовательские сценарии

1. Владелец настроил календарь, гости записались; приложение передеплоили (push в `main`) или
   контейнер перезапустился — все настройки и брони на месте.
2. Два гостя одновременно подтверждают один и тот же интервал — создаётся ровно одна бронь;
   второй получает контрактный 409 `SLOT_UNAVAILABLE` и существующее понятное сообщение в UI,
   даже если запросы обрабатываются конкурентно.
3. Проверяющий курса собирает образ и запускает контейнер, передав только `PORT` (без строки
   подключения), — приложение поднимается и полностью работает, как до задачи (in-memory),
   и лог явно называет режим хранилища.

## Функциональные требования

- **FR1.** Схема БД и миграции живут в `packages/database` (зона активируется). Состав таблиц
  покрывает сущности `docs/domain-model.md`: настройки календаря, Event Type, Booking; timestamps
  в UTC; snapshot данных гостя внутри Booking; публичный id Event Type уникален.
- **FR2.** Пересечение активных бронирований запрещено на уровне базы exclusion constraint —
  глобально, независимо от Event Type.
- **FR3.** Store `apps/api` получает реализацию на PostgreSQL за существующим интерфейсом
  репозиториев; use-cases и HTTP-слой не меняются.
- **FR4.** Хранилище выбирается конфигурацией окружения один раз, в момент старта процесса, и на
  лету не переключается: строка подключения задана — Postgres, не задана — текущий in-memory.
  Задаёт её тот, кто управляет окружением запуска: на DockHost — владелец в переменных контейнера
  (один раз, автодеплои её наследуют), локально — цели make через параметры compose-контура;
  внешний проверяющий не задаёт ничего и получает рабочий in-memory. Режим объявляется одной
  явной строкой в логе старта — защита от молчаливого отката (DockHost стирает незаданные
  переменные при обновлении контейнера).
- **FR5.** Миграции применяются к чистой базе воспроизводимо и повторно (идемпотентно); момент
  прогона — старт приложения или отдельная команда — выбирает ADR.
- **FR6.** Поведение `SEED_DEMO` при постоянном хранилище определено и безопасно: сид не затирает
  и не дублирует реальные данные (механику — идемпотентность, ограничение режимом in-memory,
  отключение — выбирает ADR).
- **FR7.** Локальный контур: сервис приложения добавляется в `infra/compose.yml` и подключается к
  postgres по параметрам, которые контур уже предоставляет (`infra/README.md`, «Расширение
  контура»).
- **FR8.** Опубликованный инстанс DockHost переведён на постоянное хранилище: сервис БД,
  переменная подключения, обновление контейнера полным набором переменных; после передеплоя
  данные на месте.
- **FR9.** Источники правды обновлены: `infra/README.md` (раздел «Что нужно знать про
  опубликованный инстанс», контур), `docs/architecture.md` (актуальное состояние API и
  `packages/database`).

## Нефункциональные требования

- **NFR1.** Контракт запуска не меняется: сборка по корневому Dockerfile и запуск с одной
  переменной `PORT` остаются достаточными для полностью рабочего приложения.
- **NFR2.** HTTP-контракт и generated-пакеты не меняются; точный список routes/операций
  (`tests/contract-validation.test.ts`) не тронут.
- **NFR3.** Новые автотесты — только на критическое, полная матрица существующих API-тестов на
  Postgres не дублируется: (а) конкурентное пересечение бронирований на реальном Postgres —
  инвариант держит exclusion constraint, в том числе для разных Event Type; (б) идемпотентность
  миграций — повторный прогон на той же базе; (в) выбор режима хранилища по конфигурации.
  Существующие тесты остаются зелёными.
- **NFR4.** In-memory реализация остаётся рабочей и покрытой существующими тестами — это режим по
  умолчанию при запуске без строки подключения.
- **NFR5.** Изоляция данных инстанса: один деплой = один владелец = одна выделенная база.
  Подключение выполняется под пользователем БД с доступом только к базе своего инстанса — чужой
  инстанс физически не может прочитать не свои данные. Строка подключения — секрет окружения:
  не хранится в git и в образе, не попадает в клиентский бандл (не `EXPO_PUBLIC_*`-переменная).
  Правило эксплуатации фиксируется в `infra/README.md` (FR9).

## API impact

`NONE` — хранилище остаётся деталью реализации за интерфейсом store; операции, модели и коды
ошибок контракта не меняются.

## Acceptance criteria

- **AC1.** Локально без базы: образ собран по корневому Dockerfile, контейнер запущен только с
  `PORT` — гостевой сценарий проходит целиком, как до задачи; в логе явная строка режима
  in-memory.
- **AC2.** Локально с базой: приложение работает на Postgres; созданные настройки и брони
  переживают перезапуск контейнера приложения.
- **AC3.** Конкурентная попытка занять пересекающийся интервал (в том числе другим Event Type)
  даёт ровно одну бронь и 409 второй — подтверждено тестом на Postgres, где инвариант держит
  exclusion constraint.
- **AC4.** Миграции применяются к чистой базе одной командой (цель make); повторный прогон
  идемпотентен.
- **AC5.** DockHost: после передеплоя (push в `main`) созданные ранее брони и настройки на месте.
- **AC6.** `SEED_DEMO` в Postgres-режиме безопасен по FR6; сценарий подтверждён на опубликованном
  инстансе или локальном эквиваленте.
- **AC7.** `make gates` зелёный целиком, включая `lint-docs` после обновления README и
  architecture.

## Non-goals

- Auth, роли, несколько владельцев (правило 2 корневого `AGENTS.md`).
- Изменение HTTP-контракта, слотов и доменных правил.
- Выделение slot-engine в пакет (`back/003`).
- Бэкапы, репликация, перенос накопленных демо-данных: содержимое in-memory прошлых запусков не
  мигрируется.
- Цели `deploy-*` поверх dockhost CLI (отклонено в `infra/009` как YAGNI).
- Смена платформы публикации.
