# Полный трек (full)

Четыре документа, четыре гейта. Трек по умолчанию для содержательных задач; критерии выбора и
облегчённый трек — в [`lite.md`](lite.md).

Ниже `task X` — сокращение от `scripts/task X`; полная таблица команд — в
[`../AGENTS.md`](../AGENTS.md).

## Гейты

Гейт — именованная точка согласования владельцем, привязанная к документу. Статусы гейтов
(`черновик` / `согласовано`) хранятся только в `task.yaml` и меняются только через CLI; в самих
`.md` статуса нет.

| Гейт | Документ | На что отвечает | Согласование |
|---|---|---|---|
| brief | `brief.md` | что и зачем должно быть сделано | `task approve <id> brief` |
| adr | `adr.md` | как: архитектурное решение | `task approve <id> adr` |
| plan | `plan.md` | из каких пунктов состоит работа | `task approve <id> plan` |
| result | `result.md` | что получилось и чем проверено | `task approve <id> result` |

Порядок жёсткий: `brief → adr → plan → result`. Согласовать гейт, пока предыдущий в черновике,
CLI не даст. Активный документ задачи — первый гейт в состоянии `черновик`.

Правило 11 корневого [`AGENTS.md`](../../AGENTS.md) в силе: `approve` выполняется только после
явного «согласовано» от владельца или назначенного reviewer. CLI фиксирует решение, а не
принимает его: одной операцией записывает статус, дату и sha256 согласованного содержимого.

## Стадии

Стадия не хранится — её вычисляет `task status` по гейтам и пунктам плана.

| Стадия | Признак |
|---|---|
| заявлена | есть только `task.yaml`-стаб, документов нет |
| постановка | гейт `brief` в черновике |
| проектирование | `brief` согласован, `adr` или `plan` в черновике |
| реализация | постановочные гейты согласованы, пункты `plan.md` не все «завершено» (прогресс N из M) |
| результат | все пункты завершены, `result` в черновике; сюда входит фаза «Проверка» |
| завершена | все четыре гейта согласованы |

## `brief.md`

Минимальные разделы:

```md
# <id> — Название

## Контекст и проблема
## Цель
## Зависимости
## Пользовательские сценарии
## Функциональные требования
## Нефункциональные требования
## API impact
## Acceptance criteria
## Non-goals
## Связанные документы
```

Brief отвечает на вопрос **что и зачем должно быть сделано**. Он не должен подменяться детальным
планом файлов и коммитов. `<id>` — канонический id задачи (`front/guest/002`).

## `adr.md`

ADR существует внутри каждой задачи. Отдельного глобального каталога ADR нет.

Минимальные разделы:

```md
# Architecture decision

## Контекст
## Решение
## Затронутые компоненты
## Последствия и компромиссы
## Рассмотренные альтернативы
## Совместимость и миграция
```

Если архитектурного изменения нет, файл всё равно заполняется кратко:

```text
Решение: следовать docs/architecture.md без отклонений.
```

Согласованный ADR задачи является решением для её scope. Если он меняет общий архитектурный
контур, в plan должен быть пункт обновления `docs/architecture.md` и других затронутых источников
правды.

## `plan.md`

Каждый пункт декомпозиции содержит как минимум:

| ID | Цель / проблема | Решение | Состояние |
|---|---|---|---|
| P01 | Что требуется решить | Как это будет реализовано | `в плане` |

Допустимые состояния пунктов:

```text
в плане
выполняется
завершено
```

Правила:

- до начала реализации все пункты находятся `в плане`;
- перед работой над пунктом он переводится в `выполняется`;
- `завершено` ставится только после применимых проверок — гейтов затронутой области; полный набор
  откладывается до фазы «Проверка»;
- перевод состояний не трогает гейт `plan`: колонка «Состояние» исключена из его checksum
  (hash-стратегия `ignore-state-column`), поэтому `task check` не считает это правкой плана;
- материальное изменение scope, решения или декомпозиции — правка плана: гейт возвращается
  в черновик (см. «Откаты»).

## Фаза «Проверка»

Часть стадии «результат», выполняется до согласования `result`. Когда все пункты `plan.md`
завершены, полный набор гейтов прогоняется локально одной командой `make gates` (что в него
входит — определено только рецептом этой цели), команды и результаты фиксируются в разделе
«Выполненные проверки» файла `result.md` — только после этого готовится MR.

CI на PR/push в `main` — страховка после push, а не замена фазы: `tasks/` и `docs/` в git,
поэтому в CI выполняется тот же набор целиком. Зелёный CI не отменяет локальный прогон —
он идёт после push, когда фаза уже пройдена.

## `result.md`

Result ведётся во время реализации и становится итоговым отчётом и основой описания MR.

Минимальные разделы:

```md
# Результат <id>

## Итог
## Что изменено
## Контракт и generated-артефакты
## База данных и миграции
## Выполненные проверки
## Отклонения от brief / ADR / plan
## Известные ограничения и риски
## Описание для MR
```

Раздел «Описание для MR» может делиться на подразделы `### Summary`, `### Changes`,
`### Verification`, `### Known limitations` — так сделано в [`_template/full/result.md`](../_template/full/result.md).

Гейт `result` согласуется, когда:

- все обязательные пункты `plan.md` завершены;
- acceptance criteria проверены либо явно отмечены как невыполненные;
- фаза «Проверка» пройдена: `make gates` зелёный целиком, команды и результаты
  зафиксированы;
- описание MR соответствует фактическому diff;
- реестр обновлён: данные задачи актуальны в `task.yaml` (`title`, `depends`, `queue.*` — через
  `task set`), `task registry` перегенерировал `REGISTRY.md`;
- результат принят владельцем или ответственным reviewer.

## Откаты

Изменение согласованного документа возвращает его гейт в `черновик` и инвалидирует зависимые
решения. Выполняет `task draft <id> <гейт>` — каскад применяется автоматически.

| Изменён | Что уходит в `черновик` |
|---|---|
| `brief.md` | `brief`, `adr`, `plan`, `result` |
| `adr.md` | `adr`, `plan`, `result` |
| `plan.md` — материальная декомпозиция | `plan`, `result` |
| `result.md` — отзыв согласования | `result`; после этого перегенерировать реестр (`task registry`) |
| Только фактическое выполнение (состояния пунктов, ведение result) | ничего: согласованные гейты не трогаются |

Правку согласованного документа мимо `draft` ловит `task check` — сравнивает sha256 с записанным
при согласовании (checksum-дрифт).

Если изменение одной задачи меняет входные условия зависимой:

1. остановить зависимую задачу;
2. зафиксировать ссылку на upstream change (в её `brief.md` / `adr.md`);
3. вернуть первый затронутый downstream-гейт в `черновик` (`task draft`);
4. продолжить с нового активного этапа.

Кандидатов на такую инвалидацию подсказывает `task check`: если у upstream-задачи из `depends`
дата согласования свежее, чем у downstream, он выдаёт предупреждение.

## Чек-лист закрытия задачи

1. Все пункты `plan.md` — `завершено`.
2. Фаза «Проверка»: `make gates` зелёный целиком, вывод — в «Выполненные проверки».
3. `result.md` дописан: итог, отклонения, ограничения, описание для MR по фактическому diff.
4. MR открыт, CI зелёный, MR влит.
5. Владелец подтвердил результат → `task approve <id> result`.
6. Уборка рабочего контекста: ветка и worktree удалены (`task approve … result` предупреждает о
   неубранных и вычищает блок `workspace`; `mr` остаётся историей).
7. `task registry` и `task check` — зелёные: реестр отражает завершённую задачу.
