# infra — эксплуатация локального контура

Как поставить Docker-провайдера, поднять локальный контур (PostgreSQL и приложение), сбросить его
данные, запустить мок контракта, собрать образ приложения и опубликовать его. Правила зоны —
в [`AGENTS.md`](AGENTS.md); архитектурный контур проекта —
в [`docs/architecture.md`](../docs/architecture.md).

## Состав контура

```text
infra/
├── compose.yml
├── .env.example
└── postgres/initdb/01-test-database.sh
```

Провайдер — colima + docker CLI + Compose plugin (Homebrew). Имя проекта Compose — `minical`;
project directory — `infra/`, поэтому контур поднимается целями зоны, а не вызовами из корня
репозитория. Сервисов два:

- **`postgres`** — официальный образ `postgres:18`, поднимается всегда;
- **`api`** — приложение целиком, сборка из корневого `Dockerfile` (см. «Образ приложения»).
  Сервис спрятан за профилем Compose `app`, потому что подъём базы не должен тянуть сборку
  образа: `make db-up` и БД-цели поднимают только `postgres`, полный контур — отдельная цель
  `make -C infra up-app`. Остановка, сброс и валидация конфигурации, наоборот, видят оба сервиса.

Строку `DATABASE_URL` сервису `api` собирает сам compose — из тех же переменных `POSTGRES_*`, что
и базе, чтобы их переопределение доезжало до приложения; хост в ней — имя сервиса `postgres`,
а не `localhost`.

## Установка Docker-провайдера

Docker нужен для двух вещей — контура базы и образа приложения; обязательный набор проверок
и запуск API и клиента из исходников от него не зависят и работают на машине без него.

На macOS/arm64 провайдер ставится через Homebrew:

```bash
brew install colima docker docker-compose
```

**Обязательный шаг после установки** — без него плагин Compose не находится и любой вызов падает
с «docker: 'compose' is not a docker command»: добавить в `~/.docker/config.json`

```json
{
  "cliPluginsExtraDirs": [
    "/opt/homebrew/lib/docker/cli-plugins"
  ]
}
```

Запуск VM с явно заданными ресурсами:

```bash
colima start --cpu 4 --memory 4 --disk 20
```

Проверка установки:

```bash
docker version
colima status
make -C infra config   # валидирует compose.yml без запуска: плагин Compose найден и конфигурация цела
```

Версии, проверенные 2026-08-16 на этой машине: colima 0.10.3, docker CLI 29.7.2, Docker Compose
5.4.0, Docker Engine (в VM) 29.5.2, образ `postgres:18`.

## Запуск контура и работа с базой

PostgreSQL слушает `localhost:5432`, приложение полного контура — `localhost:3001`. Цели зоны
и их корневые синонимы:

| Из корня | В каталоге зоны | Что делает |
|---|---|---|
| `make db-up` | `make up` | Поднять `postgres` и дождаться healthy |
| — | `make up-app` | Поднять полный контур (`postgres` + `api`) со сборкой образа и дождаться healthy |
| `make db-down` | `make down` | Остановить контур целиком, данные сохраняются |
| `make db-logs` | `make logs` | Логи PostgreSQL, follow |
| `make db-reset` | `make reset` | Остановить и **удалить volume** — данные теряются безвозвратно |
| `make db-migrate` | `make db-migrate` | Применить миграции к базе разработки |
| `make db-test` | `make db-test` | Прогнать БД-тесты зон `packages/database` и `apps/api` против `minical_test` |
| — | `make config` | Проверить конфигурацию compose без запуска |

- **Готовность:** цель подъёма сама дожидается состояния healthy, отдельно ждать не нужно.
- **Порт:** на хосте `5432`, переопределяется `POSTGRES_PORT`; в контейнере всегда `5432`.
- **Базы:** `minical` (разработка) и `minical_test` (БД-тесты) — создаются при первом запуске
  на пустом volume. Базы разные потому, что прогон тестов чистит схему целиком.
- **Миграции и БД-тесты:** в рантайме миграции применяет сам API на старте, поэтому шага
  развёртывания в контуре нет; `make db-migrate` — ручной прогон того же раннера по базе
  разработки, когда схему обновляют без перезапуска приложения. `make db-test` подставляет
  `TEST_DATABASE_URL` на `minical_test` и гоняет БД-наборы обеих зон: без этой переменной они
  пропускаются сами, так что цель — их единственный настоящий прогон. Её же обязательным шагом
  выполняет CI (job `compose`).
- **Доступ:** пользователь и пароль по умолчанию — `minical`/`minical`. Полный список переменных
  и их дефолтов — в [`.env.example`](.env.example), переопределяются файлом `infra/.env`
  (в `.gitignore`, наружу не публикуется).
- **`psql` на хосте не нужен** — обращения к базе идут изнутри контейнера:

  <!-- lint-docs: allow-raw — разовый исследовательский запрос к контейнеру, проектной командой не является -->
  ```bash
  docker compose -f infra/compose.yml exec -T postgres psql -U minical -d minical -c "\l"
  ```

- **Только для локальной учебной среды:** пароль по умолчанию слабый, auth в MVP нет, контур наружу
  не публикуется.

## Полный сброс данных

```bash
make db-reset   # контур останавливается, volume с данными удаляется безвозвратно
make db-up      # базы создаются заново пустыми
```

Init-скрипты `/docker-entrypoint-initdb.d/` выполняются **только** при инициализации пустого
каталога данных: на существующем volume правка `postgres/initdb/01-test-database.sh` ничего не
изменит и новая база не появится. Изменение набора баз поэтому требует сброса.

## Мок контракта (Prism)

```bash
make mock
```

Мок-сервер поднимается на `http://localhost:4010` по
`packages/contracts/generated/openapi.yaml`, отвечает на все 12 операций контракта и не требует
backend, PostgreSQL или Docker.

- **Режим валидации:** запрос, не соответствующий контракту (пропущенное обязательное поле,
  нарушение `pattern`, типа и т. п.), отклоняется: если операция документирует 4xx-ответ — им
  (для `POST /bookings` фактически `400`), иначе — сгенерированным `422`; детализация —
  в заголовке `sl-violations`. Конкретный не-2xx ответ можно запросить штатным механизмом Prism:
  `curl -X POST http://localhost:4010/bookings -H "Prefer: code=404" ...`.
- **Дефолтный успешный ответ `POST /bookings` — `200`, а не `201`:** контракт документирует
  у этой операции два успешных статуса (`201` — бронь создана, `200` — идемпотентный повтор),
  а Prism выбирает наименьший 2xx. `201` запрашивается тем же механизмом:
  `curl -X POST http://localhost:4010/bookings -H "Prefer: code=201" ...`. Клиент обязан трактовать
  любой 2xx как успех.
- **Ограничение:** error-тела отдаются сгенерированным примером `{"code":"string","message":"string"}`,
  не соответствующим enum-схемам ошибок; статус выбирается верно, точная форма ошибки — нет.
- **Переключение клиента:** generated SDK (`@minical/api-client`) настраивается на мок через
  `client.setConfig({ baseUrl: 'http://localhost:4010' })`; при готовности backend —
  `baseUrl: 'http://localhost:3001'`. Никаких изменений кода кроме конфигурации base URL
  не требуется.

## Образ приложения

Приложение целиком — один образ: этап сборки экспортирует два web-бандла клиента, рантайм-этап
несёт цепочку API и раздаёт эти бандлы тем же процессом. Второго веб-сервера в образе нет, порт
один.

`Dockerfile` и парный `.dockerignore` лежат **в корне репозитория**, а не в этой зоне: внешняя
проверка учебной платформы собирает образ из корня контекста, и это требование сильнее контракта
размещения. Отступление зафиксировано в [`docs/sources-of-truth.md`](../docs/sources-of-truth.md);
владелец обоих файлов — зона `infra/`.

### Переменные окружения

Набор переменных, их дефолты и дисциплина разбора у образа те же, что у процесса API: читает их
всё тот же `config.ts`. Таблица с допустимыми значениями — в
[`apps/api/README.md`](../apps/api/README.md), раздел «Переменные окружения». Специфика образа
только в том, кто эти значения задаёт:

- **`PORT`** на платформе публикации назначает она сама. Локально его задаёт параметр цели, и он
  же становится портом на хосте: внутри контейнера и снаружи порт один и тот же.
- **`PUBLIC_WEB_URL`** на публикации — выданный платформой адрес сервиса (шаг 4 порядка ниже).
  Локально цель подставляет `http://localhost:<PORT>` вместо дефолта конфига
  (`http://localhost:8081` — адрес dev-сервера Expo): в образе гостевую половину раздаёт тот же
  процесс и живёт она на том же порту, что и API, поэтому дефолт конфига здесь неверен всегда.
- **`SEED_DEMO`** цель пробрасывает только заданным и по умолчанию не передаёт вовсе.
- **`DATABASE_URL`** цель не передаёт вовсе: запуск из образа локально остаётся in-memory,
  а постоянное хранилище проверяется полным контуром (`make -C infra up-app`), где строку задаёт
  compose. На платформе публикации переменную задают вручную — см. «Строка подключения и изоляция
  данных».

### Локальная сборка и запуск

| Цель | Что делает |
|---|---|
| `make image-build` | Собрать образ из корня репозитория; имя задаётся `IMAGE` (по умолчанию `minical`) |
| `make image-run` | Запустить собранный образ на переднем плане; контейнер удаляется на выходе |

Обе цели принадлежат этой зоне, а в корневом `Makefile` стоят одноимённые делегаты — вызывать
можно и оттуда, и из `infra/`. Переменные окружения передаются параметрами цели:

```bash
make image-run PORT=4321 SEED_DEMO=true PUBLIC_WEB_URL=https://minical.example.com
```

Контейнер получает имя `minical-<PORT>` — для примера выше это `minical-4321`. Порт в имени
позволяет держать несколько прогонов одновременно; остановить любой из них можно по его имени.
Незаданный `SEED_DEMO` цель не передаёт вовсе: не передать переменную и передать её пустой — для
конфига API разные вещи. Если образ ещё не собран, цель скажет об этом и остановится, а не пойдёт
искать его в реестре.

Что отвечает на выбранном порту:

```text
/         гостевой клиент
/admin    владельческий клиент (без завершающего слэша — редирект на /admin/)
/health   проверка живости
```

Строка запуска живёт только рецептом цели в [`Makefile`](Makefile) этой зоны: сырые вызовы docker
в документации не приживаются — их не пропускает гейт `make lint-docs`.

## Публикация

Платформа — **DockHost** ([dockhost.ru](https://dockhost.ru)): при подключении git-репозитория
сама собирает образ по `Dockerfile` из корня и пересобирает его на каждый push в выбранную ветку.
Оплата поресурсная в рублях; публичный адрес — бесплатный динамический домен третьего уровня
с автоматическим HTTPS-сертификатом. Приложение опубликовано:
<https://6b1y-3d3v-dk6o.gw-1a.dockhost.net>. Исходно платформой был выбран Render, но его
регистрация требует зарубежную банковскую карту — сработал критерий переключения (см. ниже);
решение зафиксировано в `result.md` задачи `infra/009`.

Все шаги выполняются в консоли DockHost (веб-интерфейс; та же настройка доступна их CLI —
[docs.dockhost.ru](https://docs.dockhost.ru)). Порядок существенен целиком — каждый шаг опирается
на состояние, оставленное предыдущим:

1. **Подключить репозиторий**: раздел «Репозитории Git» → «Добавить»: адрес репозитория и ветка;
   Dockerfile и контекст — дефолтные (корень). Ресурсов достаточно минимальных: 1 CPU с резервом
   10–20 % и 256 MiB памяти. Первая сборка стартует сама; контейнер появится в разделе
   «Контейнеры».
2. **Объявить порт контейнера**: «Контейнеры» → контейнер → «Редактировать» → «Порты» → добавить
   `3001` (порт API по умолчанию; `PORT` задавать не нужно — маршрут ведёт трафик прямо на него).
   Без объявленного порта следующий шаг не выполнится: маршруту некуда вести трафик.
3. **Выдать адрес**: «Сетевые сервисы» → «Домены» → «Добавить» динамический домен; затем
   «Маршруты» → «Добавить»: этот домен, путь `/`, тип «Внутренний», сервис контейнера, порт `3001`.
4. **Задать `PUBLIC_WEB_URL`** выданным адресом: «Контейнеры» → «Редактировать» → переменные.
   До создания домена адрес неизвестен, поэтому шаг идёт только теперь; контейнер перезапустится.
   Без этой переменной владелец увидит в настройках ссылку для гостей `http://localhost:8081` —
   дефолт локальной разработки.
5. **Проверить сценарий вручную на пустом хранилище:** пройти онбординг на `/admin`, затем
   забронировать слот на `/`.
6. **Включить `SEED_DEMO=true`** (там же, в переменных контейнера) — только после проверки.
   Переменные при обновлении задаются всем набором: обновление контейнера с одной переменной
   стирает остальные.

**Почему сид включается последним.** С включённым сидом онбординг завершён уже на старте, и
повторный `PUT /admin/setup` штатно отвечает `409 ONBOARDING_ALREADY_COMPLETED` — мастер онбординга
на таком инстансе не показать. Проверить его можно единственным способом: на пустом хранилище, то
есть до шага 4. После шага 4 установившееся состояние ссылки — настроенный демо-календарь, где
посетитель по-прежнему заводит типы встреч, меняет настройки и бронирует слоты.

### Строка подключения и изоляция данных

Постоянное хранилище включается на инстансе одной переменной `DATABASE_URL` — её форма и поведение
процесса описаны в [`apps/api/README.md`](../apps/api/README.md). Два правила эксплуатации:

- **Один деплой — одна выделенная база и свой пользователь БД** с доступом только к ней.
  Владелец в MVP один и auth нет: единственная граница между данными двух инстансов — граница
  базы, и пользователь, видящий чужую базу, эту границу снимает.
- **Строка подключения — секрет окружения.** Она задаётся переменной контейнера на платформе и не
  хранится ни в git, ни в образе. Переменной вида `EXPO_PUBLIC_*` она быть не может: такие
  значения Expo вшивает в web-бандл, который отдаётся каждому посетителю ссылки.

### Что нужно знать про опубликованный инстанс

- **Данные переживают перезапуск и передеплой.** Инстанс работает на PostgreSQL: рядом с
  приложением в том же проекте DockHost подняты контейнер `minical-db` (`postgres:18`,
  выделенные база и пользователь) и volume для данных; `DATABASE_URL` задана переменной
  контейнера приложения, публичного маршрута к порту 5432 нет — база доступна только из
  внутренней сети проекта. Управляемой услуги БД CLI платформы не предоставляет, поэтому
  выбран контейнер с volume (зафиксировано в `result.md` задачи `back/002`). Демо-сид
  (`SEED_DEMO=true`) наполняет только пустую базу — рестарты и деплои его не повторяют.
- **`/admin` публикуется без auth.** Это учебная среда: защиты нет и она не подразумевается —
  правило 9 корневого [`AGENTS.md`](../AGENTS.md) и раздел Security boundary
  в [`docs/architecture.md`](../docs/architecture.md). Путь `/admin` безопасностью не является.
- **Инстанс оплачивается поресурсно и не засыпает.** Тариф DockHost почасовой за выделенные
  ресурсы; при минимальной конфигурации из шага 1 постоянно работающая ссылка стоит порядка
  двухсот рублей в месяц. Холодных стартов, в отличие от бесплатных планов зарубежных платформ,
  нет.
- **Пересборка привязана к ветке.** DockHost пересобирает образ на каждый push в ветку, указанную
  при подключении репозитория. После вливания рабочей ветки задачи ветку в настройках репозитория
  нужно переключить на `main` — иначе деплой перестанет обновляться.

### Выбор платформы и критерий переключения

Порядок в этом разделе описывает фактическую платформу. История выбора: основным вариантом ADR
называл Render (запасным — Railway), но регистрация обеих требует зарубежную банковскую карту —
критерий «оплата или регистрация блокирует» сработал до первого деплоя, и публикация выполнена
на DockHost. Критерий остаётся тем же и дальше: платформа меняется, если она **не собирает
образ**, **не держит приложение** или **блокирует оплату/регистрацию** — то есть сценарий выше
по выданной ссылке не проходится. Отдельного ADR смена не требует: решение и причина фиксируются
в `result.md` задачи, а порядок публикации в этом разделе правится на фактическую платформу.

## Расширение контура

Сервис `api` добавлен задачей `back/002`; дальнейшее расширение — отдельными задачами по очереди
работ ([`tasks/REGISTRY.md`](../tasks/REGISTRY.md)). Что уже решено и не ждёт новой задачи:

- **Отдельного сервиса `web` не будет.** Оба web-бандла раздаёт тот же процесс из того же образа
  (решение `infra/009`), поэтому обязанность зоны «web, API и PostgreSQL через Compose»
  закрывается двумя сервисами.
- **Момент применения миграций** выбран: их прогоняет сам API на старте, отдельного шага в контуре
  и в CI нет.
- **E2E-прогон web на Playwright (`infra/008`)** поднимает этот же контур как предусловие перед
  тестами; сам контур под эту задачу не меняется.
