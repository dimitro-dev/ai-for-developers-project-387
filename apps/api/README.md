# apps/api — запуск и эксплуатация

REST API MiniCal: 12 операций контракта на Express 5, порт `3001` по умолчанию. Сборки нет —
сервер исполняет TypeScript-исходники напрямую, предварительный шаг сборки не нужен.

Устройство зоны — [`architecture.md`](architecture.md), правила зоны — [`AGENTS.md`](AGENTS.md).

## Команды

Из корня репозитория:

| Команда | Что делает |
|---|---|
| `make -C apps/api start` | Запустить API из исходников |
| `make -C apps/api dev` | То же, с перезапуском по изменениям |
| `make -C apps/api test` | Тесты зоны — состав и счётчик в [`architecture.md`](architecture.md) |
| `make -C apps/api typecheck` | Проверка типов зоны — единственное место, где типы проверяются |
| `make -C apps/api gates` | Проверки зоны: типы и тесты |

Изнутри каталога `apps/api/` те же цели вызываются без `-C`: `make start`, `make dev`, `make test`,
`make gates`. `make help` печатает список целей с описаниями.

Зависимости ставятся один раз в корне репозитория — `make setup`. Ставить их внутри `apps/api/`
нельзя: это ограничение strip-only, причина описана в [`architecture.md`](architecture.md).

На старте сервер печатает адрес health-операции: `MiniCal API: http://localhost:3001/health`.

## Переменные окружения

Читаются один раз на старте, в `src/config.ts`; обработчики окружение не читают.

| Переменная | По умолчанию | Смысл и допустимые значения |
|---|---|---|
| `PORT` | `3001` | Порт HTTP-сервера. Целое число в диапазоне `1..65535` |
| `PUBLIC_WEB_URL` | `http://localhost:8081` | Канонический публичный адрес гостевой половины приложения — тот, который владелец раздаёт гостям. Backend отдаёт его полем `publicUrl` в owner-ответах настроек; гостевым операциям это поле не отдаётся. Абсолютный URL со схемой `http` или `https` |
| `SEED_DEMO` | выключен | Наполнить пустое хранилище демо-календарём при старте: владелец, рабочие часы и два типа встреч. Включают `1` и `true`, выключают `0` и `false`. Нужен публичному демо, где пустой календарь встретил бы посетителя ошибкой |
| `DATABASE_URL` | не задана | Строка подключения к PostgreSQL со схемой `postgres://` или `postgresql://`. Не задана — хранилище в памяти процесса, задана — постоянное хранилище (см. «Состояние» ниже). Разбор проверяет только форму строки |

Пустое значение равносильно отсутствию переменной — берётся значение по умолчанию. Мусорное
значение любой из переменных завершает старт: процесс печатает
`MiniCal API: invalid configuration — <причина>` и выходит с кодом `1`. Тихого отката к дефолту нет
намеренно: подменённый `publicUrl` владелец разошлёт гостям и узнает об ошибке от них, а не при
старте.

У `DATABASE_URL` та же дисциплина действует и после разбора: заданная строка означает требование
персистентности, поэтому недоступная база или упавшая миграция тоже завершают старт
(`MiniCal API: migrations failed — <причина>`), а не переводят процесс в память молча.

Переменные передаются перед вызовом цели, окружение доходит до сервера как есть:

```bash
PORT=4000 PUBLIC_WEB_URL=http://localhost:19006 make -C apps/api start
```

## Состояние: два режима хранилища

Режим выбирает единственная переменная — `DATABASE_URL`. `server.ts` собирает по ней либо
in-memory хранилище, либо PostgreSQL-реализацию и печатает выбор строкой в лог: подмена режима
из-за стёртой на платформе переменной иначе замечается только по пропавшим данным.

### По умолчанию — в памяти процесса

`MiniCal API: хранилище in-memory — данные не переживут рестарт`. Эксплуатационные следствия:

- ни база, ни миграции, ни Docker для запуска API не нужны;
- всё, что записано через API — настройки владельца, Event Type, брони, — живёт только в памяти
  процесса и теряется при рестарте: сервер поднимается с пустым состоянием, владельца нет,
  onboarding проходится заново;
- параллельные процессы API состояние не делят: у каждого своё хранилище;
- exclusion constraint как последняя защита от гонки отсутствует — занятость держится проверкой
  в коде.

### С `DATABASE_URL` — PostgreSQL

`MiniCal API: хранилище postgres (применено миграций: <N>)`. Отличия от режима по умолчанию:

- состояние переживает рестарт и общее у всех процессов, подключённых к той же базе;
- миграции пакета `@minical/database` применяются на старте, до приёма запросов: отдельного шага
  развёртывания нет, чистая база доводится до актуальной схемы сама. Прогон идемпотентный —
  повторный старт применяет ноль миграций, а параллельные старты выстраивает в очередь advisory
  lock;
- пересечение бронирований закрывает exclusion constraint: проверка занятости в коде остаётся
  первой, но последней линией при гонке становится СУБД;
- недоступная база и упавшая миграция завершают старт (см. «Переменные окружения»).

Локальный контур PostgreSQL, ручной прогон миграций (`make db-migrate`) и БД-тесты
(`make db-test`) описаны в [`infra/README.md`](../../infra/README.md).

### `SEED_DEMO` в обоих режимах

Сид наполняет только пустое хранилище: настроенный календарь он застаёт и пропускает —
`MiniCal API: демо-сид пропущен — хранилище уже настроено`. Память на старте пуста всегда, поэтому
там рестарт с флагом по-прежнему возвращает демо-календарь; с постоянным хранилищем тот же флаг
после рестарта уже не затирает данные владельца и не двоит типы встреч.

На засеянном инстансе онбординг завершён, и повторный `PUT /admin/setup` отвечает
`409 ONBOARDING_ALREADY_COMPLETED`. Мастер онбординга проверяется до включения флага, на пустом
хранилище.
